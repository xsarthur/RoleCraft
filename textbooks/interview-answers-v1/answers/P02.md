# P02｜工具调用超时，如何避免恢复时重复执行？

答案版本：interview-answers-v1.0.0。完整参考解析；构造示例与计划不代表已执行或真实经历。

工具调用超时只说明调用者没在期限内取得可接受回执，不能推出远端没有执行。它可能尚未接收、正在处理、已产生效果但回执丢失，也可能部分完成。避免重复的核心是：在发送前固定并持久保存逻辑操作身份与准确参数，恢复先核对原操作；只有符合下游去重/无效果证明和当前授权条件时才重发。

### 先分清四种身份

模型消息的`tool_call_id`用于把工具结果回传给这一轮模型；逻辑`action_id`表示用户这一次业务意图；`attempt_id`表示一次物理发送；下游`operation_id`或幂等键让远端识别同一操作。恢复或模型重提可以有新tool_call_id/attempt_id，但必须沿用原action与operation key。不能拿参数哈希独自当意图ID：用户可能确实要创建两条相同正文的工单。用任务目标revision及“唯一工单槽位”等业务约束决定是重提旧意图还是合法新意图。

第一次意图事务保存task/goal revision、槽位、action_id、operation key、工具版本、规范化参数及指纹，并绑定准确批准。数据库对槽位和操作身份设唯一约束；同槽同指纹返回原动作，不同指纹进入冲突/重新批准。规范化规则必须版本化，不能重启后重新生成键或用新规则悄悄重算旧批准。

### 三个持久化边界与状态分支

发送前事务创建attempt、扣预算、消费或绑定批准，将动作标为“可能产生效果/未决”，提交成功后才在事务外发网络。这里即使提交后、网络前崩溃，也不能凭本地状态确定是否发出；加sent=true只是把窗口移动。收到回执后，核operation/指纹/对象并以事件ID去重，原子保存结果与动作状态；结果事务回执丢失时只读回/重交同一事件，不能重新调用业务接口。

| 核对事实 | 恢复动作 |
| --- | --- |
| 成功且操作、对象、参数匹配 | 保存/复用原回执，不再创建 |
| 仍处理中 | 等待，设下次有界核对时间 |
| 权威证明全部已发尝试最终无效果且迟到请求也不可执行 | 依当前权限、批准、预算决定同意图是否重试 |
| 暂未找到、查询超时或最终一致性列表空 | 保持未知，不能换键重做 |
| 已有效果但参数错，或批量只完成一部分 | 分别登记冲突/逐项效果，按业务补偿或人工核对；不重放整个批次 |

### 用丢回执轨迹检验设计

教学轨迹：T1意图A与key K提交→T2 attempt-1提交→T3远端以K创建工单218并把K与效果原子绑定→T4回执丢失，worker崩溃→T5恢复者读到A未决，取得新租约→T6按K查询，第一次因索引延迟暂空，仍等待→T7权威操作查询返回218及原指纹→T8结果事务提交，向新的模型调用回传218。整段不生成新业务键，所以不会把“不知道”变成第二次创建。若结果其实已本地提交、只是事务响应丢失，T5直接读到成功即可。

下游保证有条件：同键同参数去重、同键异参冲突、去重记录与实际业务效果原子关联、并发重复处理规则、键作用域/保留期、错误结果与查询一致性必须明确。客户端outbox或本地锁能保存发送意图，不能独自使网络另一端exactly-once。键已过期、参数不兼容或查询不能证明状态时，停止自动写，保留待核对。

两个恢复者应通过租约epoch/CAS只让当前者提交本地状态；旧worker迟到结果作为观察交当前者核对。仅有本地fence无法阻止不检查它的远端旧请求，所以还要下游原键去重或执行代理的围栏。新的发送前重新核当前权限、取消、deadline、预算与恢复许可；已用批准不是任何新意图的通行证。

验证要在意图前后、发送前后、远端效果后回执前、结果提交后响应前逐点中断，并发启动恢复者。记录发送次数、业务对象数、原key/指纹、账本与回执；多次传输可以合法，但同意图效果须与合同一致。加入暂空查询、过期键、部分成功、撤权、取消和无幂等服务。本文未执行这些故障注入，也未验证真实下游合同，不能宣称已经实现普遍exactly-once。

## 原追问与延伸

**如果下游不支持幂等键怎么办？**

可用业务唯一键/条件创建或强一致操作查询缩小风险，但必须验证其原子性和迟到请求语义；若既无去重又无法可靠核对，暂停自动重放，转人工核对或只生成草稿，不能宣称可保证不重复。

**用户取消任务后还需要查外部结果吗？**

需要。在仍获准的读取范围内核对已发动作，记录成功、部分成功或未知；取消只阻止新动作，不让已发送请求自动撤销，补偿是另一个需授权的动作。
