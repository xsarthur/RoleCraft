# 15 在异步与副作用中保留真实的用户控制

正式先修：07、14。层级：L2—L3。工件：草稿/退款双状态模型、确认绑定、失联核对轨迹。

## 用户控制必须对应真实能力

“可以取消”只有指出取消哪个对象才有意义。取消Draft-17生成，可以停止本地等待并忽略结果；停止等待R-81退款，不能使可能已经发生的退款消失。设计师应同时表达任务是否继续和外部效果是否已知。把二者合成一个红色error，会把未决效果错误地转换成“重试”按钮。

本章所有轨迹为合成，退款¥268 CNY是教学结算，不代表美国站交易应使用人民币。客户端表达能力不保证服务端权限、幂等或撤销；缺必要契约时必须给出安全降级。

## 两个状态模型不能共用成功提示

| 对象维度 | 状态 | 进入证据与可行动作 |
| --- | --- | --- |
| 草稿请求 | idle / clarifying | 未请求，或输入缺损；补条件再生成 |
| 草稿请求 | generating / streaming | 已接请求；展示当前阶段，文本片段仍为未审候选 |
| 草稿证据 | no_match / low_support | 未召回或支持弱；查原文、补证或转人工，不给肯定政策句 |
| 草稿证据 | checking / unsupported / conflicting / stale | 核验中、不支持、冲突、过期分别说明原因；修改/重核 |
| 草稿请求 | unavailable / refused | 服务故障与范围拒绝分开；故障可依契约重试，拒绝要改目标或人工处理 |
| 草稿请求 | cancelled / ignored_late | 本地停止等待；保留编辑，旧响应不得覆盖 |
| 人工接管 | requested / accepted | 请求发出不等于接收；显示队列、接收人和时间 |
| 退款批准 | draft / waiting_approval / approved / invalidated | 内容或策略变更使批准失效，回核对 |
| 退款效果 | not_sent / in_flight / unknown / succeeded / confirmed_no_effect / final_failed | 由发送记录和匹配回执判定；unknown先查，不盲重发 |

## 确认绑定什么

许然批准的是 `t-lotus/T-1042/O-7819/R-81@v4`，金额26800分、币种CNY、原因“破损核验完成”、退回原渠道、政策P-07@v3。确认摘要应显示这些内容，保留审批人及批准时刻，并将不可变字段作为批准指纹的输入。指纹是内容绑定，不是隐私证明或授权本身。

审批前允许编辑，编辑后重核；审批后再改金额、币种、订单、理由或适用政策，应使旧批准invalidated。文案“金额改为¥286 CNY，原批准针对¥268 CNY；请重新核对”比通用“状态已改变”有用，因为用户知道为何不能继续。非关键显示排序变化不必自动失效，关键字段由业务合同定义，设计师不得一概把任何空格变更当重审。

## 一次成功和一次失联的完整轨迹

| 顺序 | 事件 | 界面应表达的事实 | 禁止推断 |
| --- | --- | --- | --- |
| 1 | 林晓提交R-81@v4；许然核对并批准 | 已批准此版本，尚未发送 | 已退款 |
| 2 | 工程持久化原动作身份后发送attempt-1 | 发送中，保留R-81与摘要 | 已到账 |
| 3a | 返回匹配的终态成功回执receipt-81 | R-81成功；金额/币种/版本匹配 | 其他申请也成功 |
| 3b | 发送后本地超时 | 效果未知，先查状态 | 远端未执行 |
| 4b | 用户点“停止等待” | 页面停止等待，R-81仍待核对 | 退款已撤销 |
| 5b | 按R-81查询返回处理中 | 保留unknown/pending，显示上次核对时刻 | 允许另建同目的退款 |
| 6b | 查询得到匹配终态成功回执 | 展示真实效果和凭据，无需再发 | 因页面停止而忽略成功事实 |

如果查询仅返回“已受理”，应显示“已受理，最终结果待核对”；只有服务定义的成功终态才映射succeeded。“到账”还需要到账证据，不能仅凭受理或批准推导。符合原动作、版本、金额的回执才可解unknown；匹配失败时显示“结果与申请不一致，待人工核对”，不能自动采用。

## 恢复决策工件

```text
查询R-81 → 匹配终态成功：展示原回执，禁止再次退款
         → 仍处理中：等待/按有限间隔再查，显示责任和最近时刻
         → 覆盖原操作的“确认无效果”：重核当前权限与批准，再决定受控重发
         → 未找到/查询失败：仍未知，不能等同确认无效果
         → 不支持按动作查询：冻结重发，生成核对工单 H-81
```

稳定业务动作R-81与请求attempt-2不同；新requestId不能洗掉原副作用。服务若提供幂等键，仍要明确键范围、内容冲突、保留窗口、并发和查询一致性。不能凭客户端禁用按钮宣称“恰好一次”。AWS讨论超时、重试和幂等的关系，也指出重试会增加负载；本文采用更保守的“未决先查”界面合同，不假设任一支付方支持。[AWS Builders’ Library](https://aws.amazon.com/builders-library/timeouts-retries-and-backoff-with-jitter/)（查阅2026-10-14）。

自动查询适合有可靠操作查询契约、有限重查预算的服务；缺契约时选择人工核对，代价是处理时间与运营队列。人工核对也不是一句“人工确认”：H-81须携带原动作、所有发送尝试、摘要、外部记录、匹配/不匹配理由、责任人及结论证据。只有能覆盖原操作的无效果证据才允许后续处理。

## 控制的语义与无障碍

“返回检查”关闭审批弹层不发送；“确认执行”会改变业务状态；“停止等待”不撤销。三者不使用同一图标。不可逆步骤的弹层需要按内容选择初始焦点，通常先让人阅读摘要或定位低风险动作；关闭后回原申请。APG提供对话框焦点与返回规则的指导，实际键盘/读屏仍需实现测试。[APG Dialog](https://www.w3.org/WAI/ARIA/apg/patterns/dialog-modal/)（查阅2026-10-14）。

## 分层练习与参考分析

**基础：** “无匹配、低支持、服务不可用、拒答、过期、取消、接管已请求”各写下一步。无匹配可换表达或人工查政策；低支持应展示未支持句；不可用依受控策略重试但不丢草稿；拒答不能原样循环请求；过期保留人工修改并核新源；取消留原请求身份不应用旧结果；接管已请求显示待接收而非已交接。区分它们的原因是恢复依赖不同证据，而不是为了增加状态数。

**迁移：** 已批准后将CNY改USD。即使数值仍268，经济含义已经改变，应使R-81@v4批准失效，生成新内容修订并重审。界面应同时显示旧新币种，禁止用格式变化掩盖。若已发送，不能改原申请模拟没发；创建差异核对任务，并由业务负责人决定补救。

**综合：** 对迟到成功、不可查询、两用户同时重试三种情况设计恢复。迟到成功要绑定原R-81并展示；不可查询要冻结新退款交H-81；并发必须由服务保护动作去重与版本，前端收到冲突则展示已有结果并停止自己的发送。复验注入“远端成功回执丢失”“查询滞后”“键已过期”“取消后成功”，逐次核原动作、实际效果数、显示文字和重发资格。只数按钮点击或无报错不够。若服务只有按订单总额查询，多笔退款无法消歧，仍不得证明R-81无效果，须人工追踪原操作证据。
