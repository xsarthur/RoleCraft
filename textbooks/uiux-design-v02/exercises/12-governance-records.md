# CR-08治理记录参考产物

此记录是第12章的完整教学参考产物，不是已执行的发布、迁移或回滚。全部对象与调用点为合成。

编号约定：`DEF-01`–`DEF-03`表示三条原始缺陷，`CALL-01`–`CALL-05`表示五个调用点；旧稿中的 `C1`–`C3` 与 `C-01`–`C-05`分别对应这两组编号。

角色合同：林晓是 `t-lotus` 客服，只能在 `CALL-01` 读取摘要并提交审批请求；许然是主管，在 `CALL-02` 核对并批准 `R-81@v4`。林晓不能发出批准意图，许然的批准仍须经过授权服务的权限、版本和当前内容检查。

## 提案卡 CR-08

- 问题：ApprovalAction 1.x只有申请ID；旧调用者可将批准当退款完成；租户主题可覆盖危险/焦点。
- 决定：2.0必传refundId/refundRevision、订单、金额币种、理由、政策与权限；采用reviewRequest、confirmApproval、submitted的分层意图；外部结果独立。
- 不变量：R-81 v4批准不能授权v5；未知结果先核对；品牌不替代风险语义；组件不能提供服务端授权保证。
- 不兼容点：缺必需字段的旧调用点不能直接替换；旧approved事件消费必须改写。
- 退路：冻结受影响写入口；保留只读摘要、查询和未决记录；不得回退到无版本批准。

## 身份及事件参数映射

| 字段/事件 | 本工件含义与实例 | 迁移约束 |
| --- | --- | --- |
| refundId / refundRevision | R-81 / 4，即退款申请R-81@v4 | 对应21章actionId及匹配的expectedVersion/approvedVersion；版本改变需重新核对批准 |
| requestId | 一次批准提交、发送或查询请求尝试，如approval-01、send-01、query-02 | 新尝试保留申请身份；不能把它写为R-81或用它生成新申请 |
| attemptId | 21章实际执行尝试的身份 | 与requestId同属尝试层；接口若同时有运输请求与执行尝试，须记录关联，不默认它们是同一字段 |
| 1.x requestId（文稿别名legacyRequestId） | 仅指1.x历史误名字段；本例历史值是R-81 | 核实后映射refundId，不能沿用为2.0 requestId |
| reviewRequest(refundId, refundRevision) | 打开R-81@v4供检查 | 不是一次外部退款 |
| confirmApproval(refundId, refundRevision, reviewedFields) | 对R-81@v4摘要的确认意图 | 授权服务仍检查版本、内容和权限 |
| submitted(refundId, refundRevision, requestId) | 本次批准请求已提交 | 不表示批准成功或外部退款成功 |

退款发送尝试send-01失联后，query-02查询的仍是R-81@v4；查询本身不创建R-82。申请、尝试、草稿及政策版本分别保留，不能因字段改名互相替代。

## 回滚演练脚本

1. 预置R-81 v4已批准、发送结果未知，另有一条确认成功记录和一条历史缺字段记录。
2. 注入新事件消费错误：submitted被显示成已退款。
3. 停止该调用点写操作，切回能显示分层状态的兼容视图。
4. 核对未知仍未知、成功仍有匹配回执、历史缺字段仍只读；不清数据库、不重发外部动作。
5. 修正消费合同后按相同三条记录复验，再由发布责任者决定继续迁移。

预期结果是设计合同；当前未执行组件发布、浏览器演练或真实外部退款。实际执行时应另填日期、版本、执行者、观察与差异，不把此参考答案当结果。
