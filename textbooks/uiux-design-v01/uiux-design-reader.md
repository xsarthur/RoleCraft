## 这本教材要解决什么问题

一个团队对设计师说：“做一个能帮学习者找到答案的 AI 学习工具，界面要简单、聪明、像产品。”这句话不能直接变成页面。它同时隐藏了用户是谁、要完成什么工作、哪些内容可信、AI 什么时候应该追问、答案失败时如何退出，以及工程能否实现这些状态。

本书训练的核心能力是：**把用户的任务和证据转化成可实现、可测试、可解释的交互系统。** UI 是可见的结构、层级、状态和操作；UX 是从问题、目标、流程、反馈到结果的整体体验。两者在工作中经常由同一个设计师承担，但判断对象不同：一个按钮好不好看，不能证明流程可用；一条流程能走通，也不能证明用户能看懂状态。

贯穿案例“灯塔学习工作台”允许用户描述“我想学会如何调试一个失败的 AI 流程”，系统推荐带出处的教材小节。推荐可能无匹配、存在术语歧义、正在计算、来源失配或服务不可用。设计师的任务不是替模型编出答案，而是把这些真实状态做成用户可以理解并能继续行动的界面。

案例默认条件：

- 用户使用桌面或窄屏浏览器，可能没有技术背景。
- 教材有版本和小节标识，检索只可推荐现有内容。
- AI 输出是候选，不是事实；来源核对由系统和内容责任人完成。
- 本书不实现模型服务，也不声称案例已经接入现有应用；接口片段是设计契约示例。

<a id="ch-diagnostic"></a>

## 入门诊断：先确认你要补什么

先做四项小任务，再决定是否跳过基础补学：在 Figma 或等价工具中建立一个可编辑画板；把标题、正文和按钮分成独立图层；把一个按钮从默认改为焦点、禁用和错误状态；读一段简单 HTML，指出标题、表单标签和按钮的层级。如果无法完成，先补工具、文件版本、基础版式和 Web 结构阅读；如果能完成，也要记录设备、工具版本和仍不确定的部分。这里的诊断只决定学习入口，不是能力认证。

固定流程适合步骤、权限和验收条件已知的任务；开放探索适合用户目标相同但路径和表达不确定的任务。AI 产品通常需要两者组合：先用固定输入、来源和权限护栏，再允许用户改写、澄清或转人工。不要因为“AI”这个词就把每个任务画成无限聊天。

<a id="ch-learning-outputs"></a>

## 学习产物和评价方式

全书完成后应有一份可交接案例包：问题与证据表、内容模型和导航、主流程与异常状态、低保真到高保真界面、可复用组件与 token、AI 交互状态、可用性测试记录、工程 handoff、上线后指标计划、作品集页面和 10 分钟答辩稿。每份产物标出假设、来源、版本和未验证项。

评价不按屏幕数量或视觉风格打分，而看五条可追溯关系：用户任务是否明确、信息和操作是否可发现、状态是否能解释且可恢复、交付是否能实现和验证、设计决定是否由证据而非偏好支持。练习参考分析说明推理路径，不授予学习者真实岗位能力。

## 1. 把模糊需求变成可证伪的问题

### 结论和条件

UI/UX 项目的第一份交付物不是首页，而是一个可以被证据推翻的问题陈述。当“做一个简单的 AI 工具”仍可以用任何页面回答时，范围就没有收敛。设计师需要把需求拆成用户、情境、任务、结果和限制，再写出可观察的成功与失败信号。

### 从愿望到任务

将灯塔案例的初始消息拆成五列：

| 维度 | 需要回答      | 教学初值                     | 待核对证据         |
| -- | --------- | ------------------------ | ------------- |
| 用户 | 谁在什么情境下使用 | 刚入行的设计/开发学习者，在遇到概念卡点时查教材 | 真实访谈、设备和术语水平  |
| 任务 | 用户要完成的动作  | 用自己的话描述问题并找到一个能打开的原文小节   | 任务观察、搜索词样本    |
| 结果 | 什么算完成     | 用户能说明“为什么推荐这一节”，并能继续阅读   | 任务后访谈、点击和理解记录 |
| 风险 | 错了会怎样     | 推荐看似相关但不支持问题，用户误以为是正确答案  | 误导案例、内容审校     |
| 限制 | 不能做什么     | 不虚构教材，不暴露私有数据，不把自评当能力认证  | 产品/安全/内容合同    |

“用户想要简单”不是可执行目标。可以先写成假设：`如果学习者在当前页面输入一个带上下文的问题，且结果卡展示来源和下一步动作，那么他们能在一次操作内找到可阅读的小节；若无匹配，用户会选择澄清或回到目录，而不是重复提交同一句话。` 这段话规定了对象、行为、条件和可观察结果，也允许研究把它推翻。

### 证据分级和问题优先级

把信息分成事实、观察、推断和决定。事实如“教材存在版本号”；观察如“两位试用者反复点标题而非来源链接”；推断如“他们可能把卡片标题当答案”；决定如“来源链接必须与推荐理由相邻”。推断不能伪装成事实，决定要有责任人和日期。

优先研究会改变结构的未知项：用户到底是在找定义、找步骤还是评估方案？他们能否区分教材原文和 AI 总结？无匹配时愿意换词还是回目录？颜色、圆角和动效通常晚于这些问题。把优先级写在研究表里，避免把“大家喜欢哪种配色”当作首要风险。

### 练习

将“给新手做一个能回答所有 UI 问题的智能助手”改写为一个问题陈述和三个可证伪假设。为每个假设写最小证据、失败信号和下一步。参考分析：至少应把“所有问题”收窄为一个任务范围，把“回答”拆成查找、理解或执行其中之一；不能用满意度分数证明事实来源可靠。

### 失败模式

- **从竞品截图倒推需求**：看到了布局，却不知道用户任务和约束；表现是每次评审都在争论像不像。处理是回到任务和证据表，重写成功条件。
- **把利益相关者偏好当用户证据**：负责人说“用户肯定想要聊天”；可观察信号只有团队意见。处理是将其标为假设并安排任务测试。
- **把模型能力当产品目标**：模型能生成长答案，不代表用户要读长答案。处理是先定义完成动作、出处和停止条件。

## 2. 从任务建立信息架构，而不是堆菜单

### 结论和条件

信息架构（IA）要让用户在当前任务中回答三件事：我在哪里、这里有哪些可用对象、下一步能回到哪里。分类名称、层级和链接关系必须由内容与任务决定，不能由组织架构或页面数量决定。灯塔案例先区分“查教材”“按路线学习”“查看自己的记录”三类任务，再决定导航。

### 内容模型先于页面

先写内容对象和关系，再画屏幕。一个教学内容卡可定义为：

```text
Lesson { id, version, title, sections[], prerequisites[], sourceHash }
Recommendation { queryId, lessonId, sectionId, reason, excerpt, confidenceLabel, createdAt }
UserState { currentLesson, readSections[], selfMarkedReview[] }
```

这些是设计协作的字段示例，不是现有服务的 SDK 或数据库承诺。`Recommendation` 必须能回指 `Lesson` 的版本与小节；没有 `sectionId` 的“相关内容”不能进入明确的阅读入口。`UserState` 是个人浏览与自记，不能改写成“已掌握”。

### 导航和命名

给每个对象一个用户能预测的名字。若“课程”“知识库”“学习中心”都指向同一集合，用户会在返回时失去位置。灯塔工作台采用“首页（继续学习）—课程—查教材—记录”的任务语言；研发报告和版本说明放到低频设置，不混入日常主导航。这个命名是案例决定，不是通用菜单模板；真实项目需要卡片分类和树测试验证。

判断层级时问：用户是否需要同时比较两个对象？如果需要，可能要并列列表；如果要沿一条路径完成任务，可能要连续步骤；如果是同一对象的不同属性，可能要详情页或分组。面包屑、标签、返回按钮分别传达不同关系，不能互换后只靠说明文字补救。

### 信息架构的可验证交付

交付三张图：内容模型、导航树、关键对象的链接表。链接表至少列出来源、目标、触发动作和返回位置。例如“推荐卡→教材小节”是阅读动作；“查看出处”是证据动作；两者可同时存在，但不能让一个隐蔽链接承担两个目的。以五名陌生参与者进行卡片分类或树测试时，记录他们把“无匹配”放在哪里、是否能预测返回路径；这只是研究样本，不得外推所有用户。

### 练习与失败

把“课程、题库、项目、AI 助手、设置、历史资料”排成一个导航树，并写每项服务的任务。参考判断：如果一个项目只是记录学习证据，不应自动成为第六个学习主入口；如果 AI 助手只查教材，应以当前内容为上下文的辅助入口，而非承诺全知问答。失败是把每个后台对象都升为一级菜单，导致用户先学习系统结构再学习内容。

## 3. 设计有开始、状态、恢复和结束的用户流程

### 结论和条件

流程图不是一串理想路径；它必须表达状态和异常。当一次推荐可能等待、被取消、需要澄清、无匹配或来源失配时，每个分支都要定义用户下一步、数据是否保留、哪些动作不可用以及如何验证恢复。

### 贯穿流程

灯塔“查教材”主流程：

```text
Idle
  -> Submitted(querySnapshot)
  -> Searching
  -> {Results | Clarification | LowConfidence | NoMatch | Unavailable | SourceMismatch}
Results -> OpenLesson -> Read
Clarification -> ChooseMeaning -> Searching
LowConfidence -> AddContext | HumanReview | RetryWithGuard
NoMatch -> EditQuery | BrowseRoute
Unavailable -> RetryWithGuard | ContinueReading
SourceMismatch -> ShowIntegrityError -> BrowseRoute
Searching --Cancel--> Cancelled(queryId) --late response--> Ignored
```

`querySnapshot` 表示提交时的原始表达和当前课程位置；如果用户之后切换页面，迟到的结果不能冒充新页面的查询。设计稿应给每个节点写进入条件、可见状态、主动作、次动作、取消/返回后保留什么。取消等待通常只取消界面订阅，不保证远端请求已撤销；不要在界面上写成“模型已停止”。

### 状态表和恢复

| 状态                | 用户看到          | 可操作                | 必须保留           | 失败信号      |
| ----------------- | ------------- | ------------------ | -------------- | --------- |
| Searching         | 正在查找教材        | 收起、继续阅读、取消本次查看     | 查询草稿和提交上下文     | 超时或服务错误   |
| Results           | 推荐卡、理由、原文和版本  | 打开小节、查看出处、改问法      | queryId、来源版本   | 来源核对失败    |
| Clarification     | 两个可区分含义       | 选择一个、改写问题          | 原始表达           | 选择后仍冲突    |
| LowConfidence     | 低置信原因和待核事实    | 补充条件、查看证据、转人工、受控重试 | 原始表达、候选和原因     | 仍无来源或来源冲突 |
| NoMatch           | 没找到现有内容       | 换词、看目录             | 原始表达           | 重复提交无变化   |
| Unavailable       | 当前服务不可用       | 受控重试、继续读           | 草稿、错误类别        | 重试次数/相同失败 |
| SourceMismatch    | 结果无法核对        | 返回目录、报告问题          | queryId和错误记录   | 任何肯定推荐    |
| Cancelled/Ignored | 已停止等待；迟到响应不展示 | 继续读、重新提交           | 草稿和已提交 queryId | 旧结果覆盖新问题  |

状态文字不是全部设计。等待要有时间关系和收起入口，结果要以来源卡建立关系，错误要靠近可恢复动作；颜色只做补充。低置信必须明确“为什么不确定”和人工核验路径，不用百分比掩盖未知。重试为同一用户意图生成新的 `queryId` 或带幂等键的请求，不能盲目重复可能产生副作用的动作。设计师需将键盘焦点、读屏顺序、200% 缩放和窄屏遮挡一并写入状态说明。

### 流程取舍

如果只允许一个输入框，流程更简短，但用户无法在结果页同时比较多个查询；如果保留历史，则可以回看上下文，也会增加隐私和认知负担。案例先保存当前查询和有限结果，不把它变成长期聊天记忆。这个选择需由产品和数据责任人确认，不能在视觉稿中假设“所有历史都永久保存”。

### 练习

为“用户输入‘React’”画两个澄清分支：前端框架和 Agent 方法。为每一分支写来源核对、返回和超时动作。失败分析必须说明若直接选第一结果会造成什么后果，以及如何在日志中观察该错误；“加一个确认弹窗”不是完整恢复方案。

## 4. 把流程落实成可理解的界面与组件

### 结论和条件

组件的职责是稳定地表达对象、操作和状态。先有流程和状态，再抽取组件；一开始就搭建一套“万能卡片”会把所有语义压成同一种外观。对灯塔案例，结果卡至少区分标题、推荐理由、原文摘录、出处、版本和行动，而不是只显示一段模型文本。

### 低保真到高保真的交付链

保真度应由当前不确定性决定，而不是固定流水线。如果最大未知是任务顺序、导航或错误分支，先用纸笔/低保真原型快速改动；如果未知是长文案、状态组合、键盘顺序或跨屏重排，选择能表达真实文本和交互的中保真；如果要验证视觉层级、品牌语义、动效节奏或与工程组件的精确边界，才投入高保真。任务已明确但视觉 token 尚未决定时，可以直接做中保真；视觉已冻结但异常状态未知时，仍应退回低保真状态图。每次升级记录改变了什么假设、保留了什么、用什么证据判断，而不是把“高保真”当作成熟度。

一个结果卡的语义结构示例：

```text
ResultCard
  heading: lesson title + section title
  reason: why this section matches the query
  excerpt: exact source excerpt (optional)
  provenance: version, source path, checkedAt
  primaryAction: 阅读这一节
  secondaryAction: 查看出处 / 换个问法
  state: recommended | source-checking | blocked
```

这是设计交接模型，不是前端组件 API。`blocked` 时不能继续显示可点击的肯定推荐；`excerpt` 缺失时应说明“暂无可展示摘录”，不能填入占位答案。

### 组件状态和内容长度

为按钮、输入框、导航节点、结果卡和错误提示各画至少四种状态：默认、焦点/悬停、不可用、错误或完成。加上长标题、空状态、窄屏和键盘焦点。状态文案用动作和事实：“未找到对应教材，可换个词或打开目录”，不要写“AI 失败”。当文案增长时，组件要允许换行、滚动或折叠；不能用截断隐藏来源。

结果卡的状态必须和第3章状态表一致：`recommended` 只用于来源已核对的结果；`low_confidence` 显示原因和补充/人工动作；`source-checking` 不可显示肯定推荐；`blocked` 对应来源失配或不可用；`cancelled` 保留草稿并忽略旧响应。组件状态不应另造“看起来成功”的别名。

### 反馈和焦点

用户提交后，输入框可保留原文，结果在同一任务区域出现；异步完成不应把焦点强行抢到页面顶部。收起面板再打开时，焦点回到触发控件；关闭对话框后回到原位置。动效如果被系统减少动画设置关闭，状态仍需通过结构、文字和位置表达。具体 aria 属性和键盘行为交给工程按目标框架核对，设计师要先提供可观察语义。

### 练习与失败

画出结果卡的四种状态，并为每种写一个 80 字以内的中文文案。失败模式包括：把 loading、无结果和服务不可用都画成同一个旋转图标；把整张卡设为链接同时放入多个按钮造成双重触发；把“来源”藏进 hover 导致触屏用户无法核验。修正必须说明结构、事件和回焦，而不是只换颜色。

## 5. 让视觉系统表达优先级、响应式和可访问性

### 结论和条件

设计系统的价值是让多个页面在同一语义下保持一致，并让改变有成本可估计。颜色、间距和圆角本身没有意义；它们要绑定到文本层级、交互状态、风险和可读性。设计系统不是组件库截图，也不替代用户研究。

### Token 与语义

先定义语义 token，再映射到具体色值：`text.primary`、`text.muted`、`surface.default`、`state.warning`、`focus.ring`。同一 `state.warning` 可能用于待澄清，不应在另一个页面表示删除危险。将 token、使用条件、禁止事项和对比度验证放进设计系统说明。实际色值需在目标品牌、设备和主题下复核；本书不指定一个通用颜色答案。

排版优先保证内容关系：标题表达对象，副标题说明任务，按钮表达动作，辅助文字解释限制。响应式不是把桌面卡片缩小：路线图可以转为纵向列表，三栏比较可以变为顺序阅读，来源和操作仍需在同一对象附近。为 390px、平板和宽桌面各画关键状态，注明断点不是设备型号承诺而是布局行为的触发条件。

### 无障碍的工程化入口

设计师至少检查键盘顺序、可见焦点、文字/背景对比、非颜色状态、触控目标、错误与恢复文本、表单标签、动态结果的读屏通知和缩放后的重排。可把 [WCAG 2.2](https://www.w3.org/TR/WCAG22/) 作为成功准则的规范入口，但它不替案例提供通过结论；团队仍需按目标一致性级别、浏览器、辅助技术和真实设备复核。交互状态的角色、名称和属性可对照 [WAI-ARIA 1.2](https://www.w3.org/TR/wai-aria-1.2/)，动态结果、折叠和错误区域必须由工程实测，而不是只在设计稿标注 `aria-live`。设计师还要在 200% 缩放下检查内容重排、焦点可见、无横向遮挡和操作顺序；图标若承担动作必须有可见标签或无障碍名称。

设计工具本身的可访问性不等于产物可访问性。若团队讨论作者工具如何帮助生成可访问内容，可参考 [ATAG 2.0](https://www.w3.org/TR/ATAG20/)，但本教材只把它作为工具流程的背景规范，不声称 Figma 文件或案例已经符合 ATAG；网页实现仍按 WCAG/ARIA 和实际读屏、键盘、缩放测试负责。

### 练习与失败

同一推荐卡做桌面、窄屏和 200% 缩放三版，标出信息优先级改变。检查“橙色待澄清”和“绿色成功”在无彩色打印下是否仍可区分。失败是用浅灰文字表达关键错误、用颜色区分状态而没有文字、为满足视觉对齐把按钮做成无法触摸的小图标。修正需说明哪个 token、结构或交互改变，并标出需实测的未知项。

## 6. 为 AI 交互设计不确定性与信任边界

### 结论和条件

AI 介面不是把聊天框放在页面底部。设计师要让用户知道：输入被怎样解释、结果来自哪里、哪些内容已核对、系统什么时候不确定，以及用户可以如何纠正。对灯塔案例，推荐卡的可信度来自可回到版本化原文，而不是一条“AI 为你总结”的口号。

### 输入、候选和证据的分离

将 AI 交互拆成三个对象：用户表达、系统候选、可核验来源。用户表达可以保留原句和页面上下文；候选只提议现有教材目标；来源由内容索引或责任人核验。界面不得把候选直接写成“答案”，也不能用一个总分替代来源。模型未返回或供应商未配置时，要表达“当前无法推荐”而非假装成功。

一个可供工程交接的状态契约（伪代码，未连接真实 API）：

```ts
 type RetrievalState =
   | { kind: 'idle' }
   | { kind: 'pending'; queryId: string; submittedAt: string; cancelRequested: boolean }
   | { kind: 'clarify'; queryId: string; options: { id: string; label: string }[] }
   | { kind: 'low_confidence'; queryId: string; reason: 'missing_context' | 'conflicting_sources' | 'weak_match'; candidateIds: string[] }
   | { kind: 'result'; queryId: string; sourceVersion: string; sectionId: string; excerpt: string }
   | { kind: 'empty'; queryId: string; alternatives: string[] }
   | { kind: 'unavailable'; queryId: string; retryable: boolean; retryCount: number }
   | { kind: 'integrity_error'; queryId: string; expected: string; actual: string }
   | { kind: 'cancelled'; queryId: string; ignoreLateResponses: true };
```

状态契约要求客户端不会把旧 `queryId` 的结果写进新提交，也不会在 `integrity_error` 或 `low_confidence` 未核验时显示肯定推荐按钮。取消只改变客户端状态为 `cancelled`、停止等待并忽略迟到响应，不承诺远端请求已经停止；重试必须递增 `retryCount`、使用幂等键或明确新的 `queryId`，防止重复副作用。它不保证来源永远正确或模型不会产生错误；这些保证要由服务和内容责任人分别提供。

### 流式、低置信、编辑、撤销和人工接管

“正在生成”不应是一个永远转动的图标。若产品确实逐步显示结果，界面要说明当前阶段、已显示内容是否可引用、用户能否暂停或继续阅读，以及网络中断后哪些文字被保留。流式体验未实现时，设计稿应采用一次性结果的等待状态，不能用动画伪造流式行为。


低置信不是给一个百分比就结束。设计师要说明低置信来自什么事实（没有来源、来源冲突、输入缺少条件或模型拒答），让用户选择补充信息、查看证据、编辑候选、重新生成或转人工。编辑后的文本必须标记为用户修改，不能继续显示为模型原文；重新生成不能覆盖旧结果而不留版本；撤销至少要说明撤销的是本地显示、草稿还是已经发送的外部动作。若外部动作已经发生，界面不得承诺撤销成功，必须显示查询结果或人工处理路径。

人工接管是流程的一部分，不是“AI 失败后再想办法”。接管卡应说明何时触发、要把哪些上下文交给人工、用户能否修改或删除这些内容、人工接收后的等待和退出方式。多模态输入（文件、图片或语音）也要沿用同一任务状态：显示已接收的对象、解析失败的位置、替换/删除入口和隐私边界；不能只在气泡旁加一个图标。

### 澄清和拒答

澄清适用于两个候选都合理且选择会改变结果的情况；如果输入完全超出教材范围，显示无匹配并给目录入口。拒答应说明边界和下一步，不训诫用户。多意图问题可拆成两个可选方向，但不能无提示地替用户选其中一个。对敏感任务，设计师还要和产品/安全岗位确认是否应停止推荐、要求授权或隐藏个人数据。

### 练习与失败

为“我想知道改计划后哪些步骤要重做，并帮我写一份新的计划”设计交互。参考分析：当前内容可能支持“哪些步骤需重做”的机制解释，不一定支持代写完整计划；应将两件事分开，先展示可核对的教材位置，再说明未覆盖部分。失败是以聊天长度、拟人语气或动画表达信任，或把引用放在折叠很深的位置让用户无法判断候选依据。

## 7. 用用户研究和可用性测试作判断

### 结论和条件

研究不是在设计完成后找几个人说喜欢。每次研究先写要减少的决策不确定性、目标用户条件、任务、观察指标和停止规则。可用性测试检查用户能否完成给定任务并理解状态；访谈了解经历和语言；二者不能互相替代。

### 任务脚本

灯塔第一次测试只检验“找到可信小节”而非整套学习效果：

1. 给参与者任务：“你正在学习失败的 AI 流程，找到一段能解释如何恢复的教材内容，并告诉我们为什么相信它。”不先解释按钮名称。
2. 记录是否能找到输入、是否读出结果和出处关系、是否在澄清/无匹配时采取合理动作、是否能回到原文。
3. 测试后询问哪一部分是事实、哪一部分是系统推荐、哪个动作最不确定。

记录原始行为和原话，区分观察与解释。不要在测试中替用户点击关键动作，也不要把“测试主持人解释后成功”记成独立成功。样本量、招募来源和设备需写入记录；本书不设一个通用人数阈值。

### 从观察到修订

每条发现写成“触发条件→观察信号→影响→可能原因→改动→复测方式”。例如：参与者点击推荐标题后找不到出处；影响是无法核验；原因可能是卡片层级让标题像答案；改动是将来源和版本放到理由相邻并保留“查看出处”；复测同一任务，比较是否能口头指出证据来源。不要把“用户不喜欢”直接变成改颜色。

### 失败模式

- 把满意度问卷当作可用性证据，无法解释用户在哪里卡住。
- 只测试成功路径，不测等待、错误、无匹配和键盘操作。
- 为了证明方案有效给用户提示，导致设计依赖主持人。
- 将一次成功或失败外推为全体用户规律。

练习要求你写一份 20 分钟远程测试脚本和一张发现卡，标出哪些结论仍需更多样本或定量数据。研究材料未实际执行，不能在作品集写成真实用户验证。

## 8. 与产品和工程共享可实现的设计契约

### 结论和条件

工程 handoff 的目的不是把链接丢给开发，而是减少关于对象、状态、优先级和边界的不同解释。设计师对视觉和交互负责，产品对范围和成功条件负责，工程对实现约束和运行事实负责；三者要共同确认交付契约。

### Handoff 最小包

一份可交接包应包含：

- 目标任务、非目标、用户和假设；
- 页面/组件状态矩阵，包括加载、空、错误、无权限、窄屏和键盘；
- 文案、内容长度、来源字段和不可编造字段；
- 设计 token、断点、交互事件、焦点与回退行为；
- 资产、版本、许可和替代方案；
- 已知无法实现的细节、取舍及由谁决定；
- 验收场景和需要真实测试的证据。

针对结果卡，工程需要知道点击“阅读这一节”带哪些 `queryId`、`sourceVersion` 和 `sectionId`，刷新后是否保留来源，服务不可用时哪一个动作可用。设计师不应凭空定义 API 字段，但可以提供不可误解的行为契约，让后端和客户端补充正式接口。

### 工程限制下的协作

如果工程师说本迭代无法支持实时流式文字，设计方案可退回一次性结果，但不能移除等待和失败状态；如果来源核对需要额外请求，应讨论延迟、缓存和错误边界，而不是在界面上继续假装即时。冲突记录写“约束—影响—决定—替代方案—验证”，不写“开发不配合”。

### 练习与失败

给一个只支持一次性 HTTP 响应、没有真实取消语义的服务写设计交接。参考分析：显示“正在查找”与“可继续阅读”，把取消定义为停止等待并忽略迟到结果；不要写“点击取消后服务器一定停止”。失败是交付一个理想动画但没有超时、重复提交、旧响应覆盖或来源失配的处理。

## 9. 用结果评价设计，而不是用审美偏好

### 结论和条件

指标要对应任务和风险。灯塔的“推荐卡点击率”不能单独证明用户找到可信内容；用户可能误点、无法回到原文或在错误推荐后继续。先定义事件语义和质量护栏，再选择数量指标和定性复核。

### 结果指标的分层

| 层级 | 例子                  | 能回答       | 不能回答      |
| -- | ------------------- | --------- | --------- |
| 行为 | 提交→打开正确小节的比例、返回目录率  | 任务是否走通    | 是否真的理解    |
| 质量 | 来源失配率、错误推荐报告、澄清后改写率 | 系统是否误导    | 用户是否长期受益  |
| 体验 | 任务后能否复述证据、主观负担      | 是否看懂状态    | 商业转化因果    |
| 业务 | 学习任务完成、复访、支持请求      | 是否与业务目标相关 | 设计单独造成的结果 |

事件必须带版本和上下文，例如 `recommend_opened(queryId, sourceVersion, outcome)`；不要把一次页面曝光当完成。实验要先定义主要指标、护栏指标和停止条件，避免为了“显著”反复查看数据。未经统计和实验设计支持，不把差异称为因果。

### 从证据冻结最小体验（MVP）

MVP 不是把状态、来源或人工出口全部删掉的最小页面，而是在当前问题、证据和资源约束下仍能完成任务且可发现失败的最小体验。对灯塔案例，可以先交付“结构化提问→来源核对→打开原文→反馈”的固定路径，把多轮主动建议、语音和跨设备同步列为后续假设。若删掉来源核对会让用户无法判断答案，删掉它就不再是同一个任务的 MVP。

MVP 决策包至少列出：用户任务和不做清单、替代方案、保留的安全/无障碍/恢复状态、未解决风险、需要工程或内容岗位确认的依赖、何时继续或回退。这个包是设计建议，不是产品经理批准；范围、指标和发布决定应由对应责任人签署。

### 失败与复盘

如果打开率上升但来源失配也上升，优先修正卡片层级或召回核对，而非庆祝点击。若等待时间变短但用户在无匹配时重复提交，可能是错误文案不提供可执行替代。复盘记录实际版本、样本范围、未测人群和下一项行动；不能把仪表盘截图当完整证据。

练习：为“增加来源点击”提出一个实验，写出假设、主要指标、两个护栏、分群条件和不应外推的结论。没有真实数据时标注为计划，作品集中不得写成提升了某个百分比。

## 10. 把判断证据组织成作品集

### 结论和条件

作品集不是画面仓库，而是让陌生评审在有限时间内看懂你如何作出、验证并修订设计决定。一个案例应能从问题走到结果，也能诚实指出未完成和未验证项。AI 时代尤其要展示你如何处理不确定性、来源和工程边界，而不是只展示生成前后的图片。

### 案例页面结构

灯塔案例可按以下顺序：

1. **问题和范围**：谁要完成什么任务，明确不做全知聊天和职业认证。
2. **证据**：访谈/观察/内容合同的来源；教学假设单独标注。
3. **关键模型**：内容对象、任务流和状态图，说明为何不直接堆页面。
4. **方案和取舍**：至少两种可实现方案，解释选择和放弃条件。
5. **交互和视觉**：关键界面、异常状态、响应式和无障碍状态。
6. **AI 边界**：候选、来源、澄清、无匹配、不可用和人工覆盖。
7. **协作和交付**：组件、字段、工程限制、版本和验收场景。
8. **结果与缺口**：真实测试或“尚未执行”的明确标注，下一步复验计划。

每张图旁边放一句“这张图证明什么”，不要把五张同样的主屏当成五项能力。示意图、伪数据、未运行状态用标签标出。使用真实项目时先取得数据和视觉资产授权，不能把公司内部界面公开为个人作品。

### 练习

将一个“AI 聊天首页”重写为三张作品集图：问题证据、状态流程、最终界面。每张图写一个可能推翻当前方案的测试。参考分析：如果三张图都只展示最终页面，评审仍不知道你解决了什么问题，作品集应退回补证据而不是增加装饰。

## 11. 用作品回答面试追问

### 结论和条件

面试答辩不是背诵设计术语，而是让面试官沿着你的证据链追问仍能找到输入、判断、实现和结果。公开样本中常见“从研究到上线讲一个项目”“第一方案失败时做什么”“如何处理冲突反馈”“如何与工程协作”“如何把 AI 放进流程以及它哪里会失败”等题型；来源清单按样本 ID 标出，不能解释为任一公司的固定真题或出现频率。

### 五段式答辩

回答一个案例可用五段式：

1. **任务**：用户、情境、目标和限制。
2. **证据**：观察到什么，哪些仍是假设。
3. **决定**：比较了什么方案，为什么选择当前方案。
4. **实现/协作**：交付了哪些状态，如何与产品和工程确认。
5. **结果/反思**：实际测到什么，哪里未验证，下一步怎么复验。

当被问“为什么用卡片式布局”，不要只说“便于信息分组”。应说明内容对象、比较关系、长短文本和响应式条件；如果尚未测试，明确这是方案假设。被问“AI 如何帮助你”，要说明输入、探索、核对、人工修改和来源登记；不能把生成速度写成用户价值。

### 批评和冲突

接受批评时先复述对方观察，再问其影响和证据：“你担心用户找不到下一步，是因为测试中没有点击，还是因为工程限制？”如果反馈冲突，按用户任务、风险和可验证性排序；不以职级或审美偏好决定。与工程冲突时提出最小可行替代，同时保留关键状态，不把不可实现的动画当核心价值。

### 练习

从来源映射中任选 UIUX-3M-047、063、089 或 102，写 90 秒答辩。每段标出事实、假设和未验证项。参考分析：一个诚实的“尚未运行，我会怎样测”比虚构上线指标更可信；面试练习不等于录用证据。

## 12. 综合实作：从发现到可交接的 AI 学习界面

### 任务

为灯塔学习工作台完成一个“查教材”功能的独立设计包。你需要让用户从自然语言问题找到版本化原文，也要让他在歧义、无匹配、服务不可用和来源失配时继续行动。

### 阶段交付

| 阶段         | 交付                | 必须说明              |
| ---------- | ----------------- | ----------------- |
| 1. 问题      | 问题陈述、用户/任务假设、证据计划 | 哪些是真实证据，哪些是假设     |
| 2. 架构      | 内容模型、导航树、术语和返回关系  | 具体对象与版本怎样连接       |
| 3. 流程      | 主流程、四类异常、取消/恢复    | 旧响应和来源失配怎样处理      |
| 4. 界面      | 线框、结果卡、输入、详情和窄屏版  | 每个动作、状态、焦点和长文本    |
| 5. 系统      | token、组件状态、无障碍清单  | 语义 token、非颜色状态、键盘 |
| 6. 研究      | 任务脚本、记录模板、修订日志    | 观察与推断分开，未执行项标出    |
| 7. handoff | 组件/字段/事件/验收场景     | API 假设和工程未知项      |
| 8. 作品      | 案例页、90 秒答辩、下一步    | 不把示意结果写成上线结果      |

### 教学量规

- 0：只有屏幕或风格描述，无法判断用户任务。
- 1：能说明主流程，但缺少异常、来源或实现边界。
- 2：主流程、状态、组件和交接较完整，仍有关键假设未验证。
- 3：能用证据解释取舍，明确失败信号和复验方法，交付包可由产品/工程继续核对。

这是课堂量规，不是招聘评分、能力认证或行业先进性证明。至少找一名没有参与制作的人按任务走一次，记录真实阻塞；这次内部演练也不能代替正式用户研究。

### 综合失败模式

- 只做高保真首页，没有内容模型和返回关系。
- 把 AI 结果写成肯定答案，来源失配时仍给主按钮。
- 只画成功状态，工程上线后 loading、超时和无权限变成空白。
- 用自评“看起来更清晰”代替任务观察和版本记录。
- 作品集展示虚构的用户数、转化率或模型调用。

完成综合实作后，读者应能清楚区分“我设计了什么”“我测试了什么”“系统实际支持什么”和“还需要谁提供证据”。真正的入行能力、用户价值和产品上线结果要通过后续真实岗位、项目和独立评审取得。

## 附：作者使用的术语边界

- **用户目标**：用户希望改变的状态；不等同于页面上的点击。
- **任务**：在特定情境下可观察的一系列动作及结果。
- **界面状态**：系统或用户当前可观察、会影响可操作性的条件。
- **设计系统**：共享的语义 token、组件、规则和治理方式；不只是组件截图。
- **AI 交互**：包含模型或检索候选的不确定交互；不默认等于聊天。
- **来源**：能定位、核对和说明版本的依据；“模型说”不是来源。
- **可用性**：在给定用户、任务、环境和时间条件下完成目标的证据；不由审美或自测自动推出。
