# 软件工程师长期记忆条目格式

## 用途

此格式用于记录可跨项目复用的编码偏好或软件工程协作约定。它把用户明确偏好、项目局部决定和待验证假设分开，避免把一次性技术选择当成永久风格。

## 必填字段

| 字段 | 要求 |
| --- | --- |
| `id` | 稳定唯一标识，例如 `ENG-MEM-0001`；内容变更不复用旧 ID，除非只是文字修正且保留审计记录。 |
| `title` | 简短描述记忆内容，不把推测写成事实。 |
| `statement` | 用可执行、可观察的句子写偏好或约定；区分“用户偏好”和“项目约束”。 |
| `kind` | `coding-style`、`architecture`、`frontend`、`testing`、`tooling` 或 `collaboration`。 |
| `evidence` | 用户原话、明确决策、跨项目重复行为或可定位记录；至少包含来源和日期。 |
| `scope` | 适用的项目类型、客户端层、技术环境、阶段或其他边界；跨项目必须写清条件。 |
| `confidence` | `confirmed`、`strong`、`tentative` 或 `unknown`。只有用户直接确认或达到团队规定的重复证据才可用 `confirmed`。 |
| `confirmation_status` | `user_confirmed`、`awaiting_user`、`inferred`、`superseded` 或 `rejected`。 |
| `version` | 语义版本，例如 `1.0.0`；内容变化时递增并保留变更原因。 |
| `recorded_at` | ISO 日期，注明首次写入时间。 |

## 推荐字段

| 字段 | 用途 |
| --- | --- |
| `constraints` | 例外、依赖、不能越过的边界和需要重新确认的条件。 |
| `non_inferences` | 明确列出没有从证据推断出的相邻偏好。 |
| `last_reviewed_at` | 最近复核日期；长期未复核的条目应降级或重新确认。 |
| `related_projects` | 仅列证据所在项目；项目名称本身不等于跨项目推广授权。 |
| `supersedes` | 被本条目替代的旧条目标识；冲突不得静默覆盖。 |
| `change_log` | 版本、变更原因、证据和确认人/来源。 |

## Markdown 模板

```markdown
### ENG-MEM-XXXX — 标题

- **偏好/约定**：
- **类型**：`coding-style`
- **证据**：
  - 来源：
  - 日期：YYYY-MM-DD
- **范围**：
- **限制**：
- **未作出的推断**：
- **置信度**：`tentative`
- **确认状态**：`awaiting_user`
- **版本**：`0.1.0`
- **记录日期**：YYYY-MM-DD
- **最近复核**：YYYY-MM-DD
- **关联项目**：
- **替代条目**：
- **变更记录**：
```

## 状态与升级规则

1. 新观察先留在当前项目的交接文件或 `memory-proposals/`，状态为 `awaiting_user` 或 `inferred`，不得直接写入已确认区。
2. 用户明确说“这是我的长期编码偏好”或等价表述时，记录原话并可升级为 `user_confirmed`；单一项目的选型默认保持项目范围。
3. 多项目的一致行为可以提高置信度，但不能把软件工程师的猜测写成用户偏好，也不能替代用户确认。
4. 记忆冲突时创建新版本或新条目，标记旧条目为 `superseded`，说明冲突证据和适用范围变化。
5. 任何条目都不能改变 `AGENTS.md` 的岗位边界、用户授权、隐私要求、服务契约或测试独立性。
6. 删除或降级记忆时保留审计记录；被拒绝或过期的偏好不得继续影响新项目。

## 读取与写入协议

- 新项目开始：读取 `ROLE.md`、已确认 `MEMORY.md`、共享用户偏好和项目 `AGENTS.md`；仅应用与当前范围匹配的条目。
- 任务进行中：把新的观察写到项目记录，附来源、范围和不确定性；不把临时 workaround 当作长期偏好。
- 任务结束：提交记忆候选和证据，等待用户或项目经理确认后再更新 `MEMORY.md`。
- 跨岗位共享：只共享已确认且与对方职责相关的条目；软件工程师不替产品经理、设计师、AI 生成工程师或后端数据工程师创建专业记忆。
- 敏感信息：不得写入密码、令牌、密钥、私有客户数据或不必要的个人信息。
