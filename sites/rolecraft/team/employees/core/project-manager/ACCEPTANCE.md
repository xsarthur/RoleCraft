# 项目/发布验收操作单

本操作单给项目经理做协调和总闸。产品验收由产品经理签发，设计验收由设计师签发，测试/功能验收由测试工程师签发。项目经理收集这三份结论，跟踪缺口，领域失败时打开返修交接。三份都已完成、协调收口、且没有未关闭阻断时，才把项目/发布验收标为通过。

通过不等于项目经理亲自代替某一岗检查站点。示例基址 `http://111.231.8.78/` 只说明环境怎么记，不表示该地址已经通过，也不表示项目经理应独自把它验完。

## 1. 收集输入

缺任何一项，先停。向对应责任人要齐。项目经理不在这一步补写产品门槛。

| 输入 | 谁提供 | 记录什么 |
| --- | --- | --- |
| 目标 | 用户或项目交接 | 这次要让用户能完成的事，一句话 |
| 范围 | 产品经理 | 本次包含的表面、明确不做的事、版本名 |
| 验收条件 | 产品经理 | 每条可观察，并标明它属于产品验收、设计验收还是测试/功能验收 |
| 环境 | 工程交接 | 公开 URL 或指定构建的打开方式。只记录调用方需要的地址，不记录密钥、口令、令牌或环境文件内容 |

把环境写成一个基址，不要带账号信息。RoleCraft 公网示例：

```text
BASE=http://111.231.8.78
```

本地或预览构建换成交接里的实际基址，例如 `http://127.0.0.1:4318`。把这个基址写进发给产品、设计和测试的验收请求，让他们在同一环境上给出领域结论。

## 2. 请求并收集三份领域验收

对每个在范围内的领域，向责任岗位发出请求，收回书面结论。没有收回的领域保持“未完成”，不能写成通过。

| 领域验收 | 向谁要 | 结论里至少要有 |
| --- | --- | --- |
| 产品验收 | 产品经理 | 环境、版本、对照了哪些产品条件、pass 或 fail、证据位置 |
| 设计验收 | 产品设计师 | 环境、版本、对照了哪些设计条件、pass 或 fail、证据位置 |
| 测试/功能验收 | 测试工程师 | 环境、版本、功能与必要反例的 pass 或 fail、证据位置 |

记录协调状态：

```text
协调状态
- 环境：
- 期望版本：
- 产品验收：未请求 | 已请求 | pass | fail — 记录位置
- 设计验收：未请求 | 已请求 | pass | fail — 记录位置
- 测试/功能验收：未请求 | 已请求 | pass | fail — 记录位置
- 未关闭阻断：
- 日期：
```

某一领域为 fail 时，保持该领域失败，并按第 5 节打开返修交接。项目经理不把失败改签成通过，也不用自己的查看代替该领域结论。

范围明确不含设计表面时，设计验收记 `not_in_scope`，并写明产品交接里的依据。没有这句依据，就不能省略设计验收。

## 3. 协调辅助（可选，不代替领域验收）

项目经理可以做一次轻量查看，只为确认环境地址打得开、版本字段对得上交接，方便催交和核对三份结论是否对着同一环境。这一步必须标成“协调辅助”。

它不是产品验收，不是设计验收，不是测试/功能验收，也不能单独支撑项目/发布通过。健康接口、无登录入口、教材目录或页面是否可见，由测试/功能验收或对应领域验收覆盖。协调辅助即使全部成功，三份领域验收仍缺任何一份，项目/发布验收保持阻断。

若响应里出现密钥、令牌、连接串或环境文件内容，停止抄录正文，只记“响应含敏感字段，已省略”，并把它列为阻断，交接工程岗位。

## 4. 项目/发布通过或阻断

通过标准只有这一条：产品验收、设计验收、测试/功能验收都已由各自岗位完成并有记录，协调已经收口，且没有未关闭阻断。

任一领域缺失、失败、结论对的不是本次环境或版本，或仍有未关闭阻断，结论就是阻断。

```text
项目/发布验收
- 结论：pass | block
- 环境：
- 期望版本：
- 产品验收：pass | fail | not_in_scope — 记录位置（签发人：产品经理）
- 设计验收：pass | fail | not_in_scope — 记录位置（签发人：设计师）
- 测试/功能验收：pass | fail — 记录位置（签发人：测试工程师）
- 未关闭阻断：无 | 列表
- 协调辅助：未做 | 已做（不计入领域验收）
- 阻断原因（阻断时必填）：
- 本结论不覆盖：由项目经理代签产品、设计或测试/功能验收；真人专家、真实学习效果、职业认证、行业先进
- 记录位置：
- 日期：
```

通过只表示：三份领域验收已经齐备，协调没有留下未关闭阻断。它不把完整产品标成达标，也不改写任何一岗的领域结论。

## 5. 领域失败时的交接

失败属于哪个领域，就把返修交给那个领域指出的责任岗位。项目经理打开交接并跟踪复验，不直接改应用、检索、数据库、教材、界面或部署配置，也不代签返修后的领域验收。

### 产品验收失败

```text
交接：产品验收失败 → 返修
- 环境与版本：
- 产品验收记录：
- 失败条件：
- 返修责任：产品经理点名的岗位（需求不清则先回产品经理）
- 复验：修复后由产品经理重新签发产品验收；项目经理只更新协调状态
```

### 设计验收失败

```text
交接：设计验收失败 → 返修
- 环境与版本：
- 设计验收记录：
- 失败条件：
- 返修责任：设计师点名的岗位（通常为软件工程师或设计师本人）
- 复验：修复后由设计师重新签发设计验收；项目经理只更新协调状态
```

### 测试/功能验收失败

```text
交接：测试/功能验收失败 → 返修
- 环境与版本：
- 测试结论记录：
- 失败条件与复现：
- 返修责任：测试工程师点名的工程或内容岗位
- 复验：修复后由测试工程师重新签发测试/功能验收；项目经理只更新协调状态
- 项目经理不把本交接写成测试已通过，测试工程师不把复验写成项目/发布已通过
```

三份领域验收都回到 pass、阻断清掉之后，项目经理才按第 4 节把项目/发布验收标为通过。
