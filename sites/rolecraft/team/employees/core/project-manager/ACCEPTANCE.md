# 项目/发布验收操作单

本操作单给项目经理执行。对照已经交接的验收条件，实际打开指定交付面，写出通过或阻断。另一名代理次日可以按同一顺序检查 `http://111.231.8.78/` 这类公开地址。示例地址只说明步骤怎么落地，不表示该地址当前已经通过。

本结论叫项目/发布验收。它不签发测试工程师的独立质量验证，也不代替内容标准、反例或版本签核。

## 1. 开工前要拿到的输入

缺任何一项，先停。向对应责任人要齐后再测。不要在检查现场补写产品门槛。

| 输入 | 谁提供 | 记录什么 |
| --- | --- | --- |
| 目标 | 用户或项目交接 | 这次要让用户能完成的事，一句话 |
| 范围 | 产品经理 | 本次包含的表面、明确不做的事、版本名 |
| 验收条件 | 产品经理 | 每条都可观察：看到什么、请求什么、怎样算过、怎样算不过 |
| 环境 | 工程交接 | 公开 URL，或指定构建的打开方式。只记录调用方需要的地址，不记录密钥、口令、令牌或环境文件内容 |

把环境写成一个基址，不要带账号信息。RoleCraft 公网示例：

```text
BASE=http://111.231.8.78
```

本地或预览构建换成交接里的实际基址，例如 `http://127.0.0.1:4318`。后面的路径都相对这个 `BASE`。

同时记下交接里的期望身份：发布版本、教材/语料版本、单元数量。没有期望身份时，健康检查和目录检查只能记“已观察到”，不能记通过。

## 2. 冒烟步骤

按顺序做。每步留下第 3 节要求的证据。连接失败、超时、非约定状态码，该条为失败，项目验收为阻断。

### 2.1 健康

```bash
curl -sS -D /tmp/rc-health.headers -o /tmp/rc-health.json -w '\nhttp_code=%{http_code}\n' "$BASE/api/health"
```

核对：

- HTTP 状态为 200。
- 响应头 `X-Rolecraft-Release-Version` 或 JSON 里的 `releaseVersion` 与交接版本一致。
- `contentRetrieval.available` 为真，且教材/语料版本、哈希与交接一致。字段名以本次响应为准，原样抄下，不改写。
- `generation` 按响应原文记录。未配置就写未配置。未配置不是调用成功。

响应里若出现密钥、令牌、连接串或环境文件内容，立即停止记录正文，只记“响应含敏感字段，已省略”，并把该条判为失败，交接工程岗位。

### 2.2 访客 / 无登录入口

仅当验收条件要求未登录可用时执行。条件没有这条时，写 `not_in_scope`，不要为了测登录去注册或使用正式账户。

1. 使用没有本站登录态的会话（新隐身窗口，或清空该站点数据之后的窗口）。
2. 打开 `$BASE/`，再打开条件指定的入口。RoleCraft 学习入口为 `$BASE/#learn`。
3. 页面应直接进入约定的阅读或课程表面，而不是停在登录、注册或职业选择墙上。
4. 记录最终地址、可见标题，以及是否出现登录表单。不要输入口令，不要创建账户，不要读取或改正式用户库。

登录墙挡住了条件要求的无登录入口：该条失败。条件要求必须登录、而页面却在未登录时露出应保护的数据：该条同样失败。

### 2.3 教材与路径可见

1. 拉取目录：

```bash
curl -sS -D /tmp/rc-catalog.headers -o /tmp/rc-catalog.json -w '\nhttp_code=%{http_code}\n' "$BASE/api/content/catalog"
```

记录 HTTP 状态、单元数量、语料版本和哈希。数量和版本必须与验收条件一致。RoleCraft 当前 v12 交接若写明 30 个阅读单元，就按 30 核对；条件写的是别的数，以条件为准。

2. 在浏览器打开 `$BASE/#learn`。课程路线或目录中应能看到约定单元的标题，并且可以点进一节。
3. 打开条件指定的一节。没有指定时，从目录里取第一条真实 `href`（形如 `#learn/agent/<unitId>` 或 `#learn/agent/<unitId>/<sectionId>`），打开 `$BASE/` 加上该片段。
4. 该节须显示单元或小节标题，以及来自教材的正文，而不是空白、错误页或其他单元的内容。

浏览器打不开时，不要用目录 JSON 代替“可见”。目录请求可以保留为部分证据，可见性这条记为未执行，项目验收为阻断。

验收条件还要求检索或对话时，再发一次条件里的固定问句，例如：

```bash
curl -sS -D /tmp/rc-recommend.headers -o /tmp/rc-recommend.json -w '\nhttp_code=%{http_code}\n' \
  -H 'content-type: application/json' \
  -d '{"query":"<条件中的原句>"}' \
  "$BASE/api/content/recommend"
```

只确认 HTTP 状态、返回是否指向目录里真实存在的小节，以及摘录是否能在该节原文中找到。不问出教材之外的答案。无匹配、歧义或未覆盖按条件中的期望状态记录；期望是“有出处的推荐”却返回编造小节，该条失败。

## 3. 证据怎么留

写在本次项目记录里，不写进本角色档案。每条证据包含：

- 时间（UTC）和执行人岗位（项目经理）。
- 基址、步骤编号、请求方法、最终 URL、HTTP 状态。
- 版本身份：发布版本、教材/语料版本、哈希、单元数。只抄非敏感字段。
- 页面证据：关键可见文字。有截图时写文件路径；没有截图时抄标题和正文首段的短摘录，并注明摘录位置。
- 与验收条件的逐条对照：`pass`、`fail` 或 `not_in_scope`。
- 本轮没有做的检查。没做的检查保持未验证，不能写成通过。

证据里不放密钥、口令、Cookie、令牌、环境文件、正式用户数据或私人记录。

## 4. 通过 / 阻断结论

全部“范围内”的条件都有本轮直接证据且为 `pass` 时，结论才是通过。有一条失败、环境不可达、版本不一致、该见的教材或路径不可见，或可见性没有在浏览器里执行，结论就是阻断。

```text
项目/发布验收
- 结论：pass | block
- 环境：
- 期望版本：
- 观察到的版本：
- 条件对照：
  - AC-…：pass | fail | not_in_scope — 证据位置
- 未验证：
- 阻断原因（阻断时必填）：
- 本结论不覆盖：测试工程师独立质量验证、内容标准签核、真人专家、真实学习效果、职业认证、行业先进
- 记录位置：
- 日期：
```

通过只表示：在这次环境和这些条件上，交付面按约定可交。它不关闭质量缺口，也不把完整产品标成达标。

## 5. 交接

### 交给工程岗位（阻断且属于实现、部署或运行）

```text
交接：项目验收阻断 → 工程返修
- 环境与版本：
- 失败步骤：
- 期望：
- 实际（状态码、可见文字、版本字段）：
- 复现：
- 建议责任：软件工程师 | 内容检索 | 后端数据 | 部署维护（只填与失败步骤对应的一岗）
- 复验：修复后由项目经理对同一环境、同一条件重跑失败步骤及受影响步骤
- 项目经理不直接改应用、检索、数据库或部署配置
```

### 交给测试工程师（需要独立质量验证，或质量结论仍空着）

```text
交接：项目验收状态 → 独立质量验证
- 项目验收结论：pass | block（附第 4 节记录位置）
- 已核对的表面与版本：
- 请测试工程师独立核：内容标准、反例、版本证据，以及本次改动影响的原例
- 不要把本交接当作 QA 已通过，也不要把它写成项目验收本身
- 缺陷仍回原责任岗位；复验由测试工程师做独立记录，项目经理只追踪状态
```

条件本身不清楚时，交接产品经理补验收条件，并保持阻断，直到条件可观察为止。
