Q1 · 如何界定 LLM Agent？你会用哪些可观察行为区分它与普通聊天应用？

版本：interview-answers-v1 / Q1-r1。本文为完整参考解析；案例和验证方案除特别注明外均为教学构造，未在本次写作中执行。

LLM Agent 可以用一条可观察的控制关系来界定：系统围绕一个目标，读取环境观察，让模型据此提出下一步行动，再由宿主程序检查、执行和记录结果，直到满足验收、等待补充或停止。关键在于新观察能够改变业务路径，而不在于界面像聊天、调用了多少工具，或名字中有没有 Agent。宿主仍掌握权限、预算、状态与完成判定。

用同一任务看差别

设目标是“解释构建失败并形成有证据的缺陷说明”，最初只有失败报告 R71。

系统可看到的运行轨迹路径由谁决定
普通聊天用户粘贴报告→模型解释；缺实现时请用户补材料当前输入决定一次回答，没有自行取证闭环
固定流程读报告→按固定字段读实现→读规则→生成说明→校验程序预列步骤和合法分支
动态 Agent读报告发现依赖加载失败→选读配置→配置显示动态注册→改读注册模块→证据不足则等待模型结合每次新观察提议调查对象，宿主准入

最后一种系统中，应能找到目标版本、每次行动参数、实际观察、选择改变的依据以及停止原因。如果报告改成退款边界失败，下一步应可能从依赖配置改为退款函数；这才是观察影响行动的证据。工具执行结果还要进入下一轮，否则工具只是一个输出通道。

容易混淆的边界与检验

代码让模型固定“思考三次”，即便输出越来越长，也未必形成动态 Agent；如果它不读取新观察，下一轮只是机械重复。一个应用虽能按按钮搜索，但搜索结果不影响后续路径，也不能凭“有工具”证明动态性。反过来，只读 Agent 可以有完整反馈闭环，不必授予写权限；短任务也不必有长期记忆。

检验时给两个只有关键观察不同的输入，检查实际工具轨迹是否作出合理改变；再给无法补齐的规则冲突，预期保存冲突并等待，而不是多问几轮后编造裁决。还应把相同任务交给固定流程：如果固定路径完全覆盖且质量相同，保留较简单方案合理。这里提供的是行为定义和教学检验方法，不声称已经测得某产品的自主能力。
