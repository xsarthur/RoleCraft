# Q28 · MCP 中的 Tools、Resources 和 Prompts，各自适合表达什么能力？

版本：interview-answers-v1 / Q28-r1。本文为完整参考解析；案例和验证方案除特别注明外均为教学构造，未在本次写作中执行。

在MCP的教学版本2025-11-25中，Tools表达可调用操作，Resources表达可读取的上下文数据，Prompts表达可复用、可参数化的消息模板。它们通常分别面向模型选工具、应用提供上下文、用户选择交互模板，但协议不强制唯一界面模式；这种控制取向也不是权限保证。

## 用同一报告业务区分

| 原语 | 具体对象 | 消费后得到什么 |
| --- | --- | --- |
| Tool | `search_reports(query)`或`create_issue(...)` | 搜索结果或动作结果，可能有业务副作用 |
| Resource | `report://R71/revision/2` | 指定报告内容及元数据；URI是资源标识 |
| Prompt | `inspect_report(report_id)` | 一组准备好的分析消息，供宿主按策略使用 |

Tools可通过tools/list发现、tools/call调用；Resources可列举并按URI读取；Prompts可列举并获取参数化模板。获取模板不等于模型已经执行分析，读到资源也不等于已经校验其事实。报告URI不应被直接当成本机路径任意打开。

## 选择依据和信任边界

如果要执行一次检索或创建动作，用Tool；若要把稳定可定位的文档作为上下文交给模型，Resource更自然；若希望用户复用某种分析起手式，用Prompt。三者可以组成同一流程：选择分析模板、读取R71资源、由模型建议调用搜索补证工具。不是每项功能都必须同时暴露成三种原语，重复入口反而增加契约维护。

只读资源仍可能包含敏感字段，须读取前按对象授权、进入模型前投影；工具即便声明只读，客户端仍需依据可信服务及实际合同判断；外部Prompt里的“忽略权限、自动发布”仍只是外部内容，不能提升为系统规则。任何写入应沿业务批准与动作身份处理。

验证时用同一R71分别读取资源、获取模板和调用工具，核对三者返回对象和实际效果：取Prompt不应悄悄建单；越权Resource不进入模型；模板注入不改变宿主权限；合法的获批Tool应能执行。还应测不存在URI、缺模板参数、目录分页和能力未声明。结果要区分协议、内容与业务层，不能仅以三种列表都能返回作为通过。
