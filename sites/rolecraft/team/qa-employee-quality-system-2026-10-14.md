# 员工质量与能力赋能系统（测试工程师交接）

日期：2026-10-14（Asia/Shanghai）  
责任岗位：测试工程师/质量负责人  
适用岗位：产品、课程、编辑、设计、软件工程、AI生成、后端数据、测试及研究岗位  
状态：方案交接，尚未作为当前产品版本的通过证据

## 目的与边界

当前反馈是各岗位都出现低级错误。先把“能力不足”“交接不完整”“验证缺失”和“环境/工具问题”分开，才能知道该培训、该补合同、该换复核，还是该修实现。本方案建立一条可追溯的质量链：

> 目标与验收合同 → 岗位交付 → 作者自查 → 独立复核 → 缺陷修复 → 原案例复验 → 交付复盘

方案不把测试通过数、文稿字数、任务完成率或员工自述当成职业胜任证据；也不替代真人专家、真实用户、生产运行或行业比较证据。

## 一、低级错误的根因分类

每个缺陷至少标记一个**直接原因**和一个**系统原因**，不得只写“粗心”。

| 类别 | 可观察表现 | 应修复的系统问题 |
|---|---|---|
| 合同不清 | 交付物看似完成，但范围、版本、失败路径或通过条件不同 | 产品经理先交验收ID、范围、输入/输出和不做事项；冻结后变更留版本 |
| 责任越界 | 作者自审、开发改需求、测试代修正文、设计和代码各自解释不同 | 每项产物有唯一责任岗位和接收岗位；冲突交项目经理协调 |
| 先修不足 | 直接套模板、误解术语、把未知当已知 | 任务前置诊断；先修不足时进入补学/指导，不允许以格式完成代替理解 |
| 盲目复制 | 复制旧答案、旧接口或旧设计，未核对当前版本 | 交付必须绑定版本/来源哈希；旧结论不能自动继承 |
| 边界遗漏 | 正常路径可用，空态、拒绝、超时、取消、重复、过期、权限或错版本出错 | 以风险矩阵强制列出正常、异常、恢复、并发和未知变体 |
| 语义错误 | 文字流畅但机制、因果、来源或状态含义错误 | 领域审校与测试分离；审校核论证，测试核实际行为和证据 |
| 假证据 | 自查脚本、模拟数据或截图被写成真实运行/专家审核 | 证据分层：静态、VM、HTTP、浏览器、真实外部、真人；报告明确不能推出的结论 |
| 环境漂移 | 在不同Node/Python、浏览器、数据版本下结果不一致 | 记录环境、依赖、命令、输入、输出和哈希；锁定可复现夹具 |
| 交接丢失 | 设计状态未交给开发，开发假设未交给测试，编辑来源未交给审校 | 使用结构化交接单，接收人先复述关键条件并标记未知 |
| 反馈循环缺失 | 同类错误反复出现，修复后删掉首次失败记录 | 缺陷台账保留首轮失败，必须有原因、责任、修复和原案例复验 |
| 激励失真 | 为了“通过”删断言、降低门槛、隐藏缺陷或堆无效测试数 | 评价复现质量、缺陷发现率、重复缺陷下降和证据完整度，而非单一通过数 |
| 认知负荷过高 | 长任务中漏步骤、混淆多个版本或岗位要求 | 拆小批次；每批有停止点、交接点和短清单；高风险项双人复核 |

## 二、统一质量门禁

任一门禁未满足，产物只能标记为“待补证/返修”，不能进入下一门禁。

### G0：目标与风险合同（Definition of Ready）

产品经理或任务发起岗位交付：目标用户/场景、范围、版本、输入输出、验收ID、已知不做事项、风险等级、唯一责任岗位、接收岗位和复验方法。高风险任务（账户权限、模型调用、数据删除、对外发布、核心教材论断）必须列至少三个反例。

### G1：岗位方案可消费

责任岗位提交最小可审阅方案。接收人不看作者口头解释，先用自己的话复述：要解决什么、哪些条件不能假定、失败时应怎样呈现。复述不一致时退回，不进入实施。

### G2：作者/开发自查

自查只证明“责任岗位按清单检查过”，不冒充独立结论。自查必须包含成功、失败、边界、恢复/回滚和错版本案例；每个断言记录预期、实际、环境和证据位置。禁止为通过而改写或删除原失败断言。

### G3：独立复核

由不同岗位或不同代理执行，使用冻结版本和独立夹具。复核人不得修产物、修改需求或替作者补正文。结论只能是：`pass`、`pass_with_limitations`、`fail`、`insufficient_evidence`。评审发现的问题先建缺陷，再由原责任岗位返修。

### G4：返修与原案例复验

返修记录新版本/哈希、修改范围和影响评估。测试必须保留首轮输入与失败输出，先复验原案例，再跑受影响回归；失败记录不覆盖为“从未发生”。

### G5：交付包与版本复盘

交付包包含目标/范围、版本或哈希、环境、命令、输入输出、失败与限制、责任/复核身份、未关闭缺陷和回滚/下一步。项目经理只在交付包完整且风险结论明确时更新状态；“报告已写”不等于缺陷已关闭。

## 三、岗位交付前检查清单

### 编辑/教材研发

- 每个事实、机制和版本敏感断言都有来源、版本/日期和适用边界。
- 围绕核心问题说明机制、实现、关键权衡、失败模式、何时不适用和替代方案；不能用术语堆叠替代解释。
- 代码、命令、API名称和输出格式经实际运行或明确标记为未运行；不把示意伪代码写成可执行保证。
- 案例有输入、过程、预期结果、异常结果和证据位置；参考答案包含多角度分析而非三条口号。
- 先修、读者、学习目标和练习难度相互一致；未知、待专家核对和未实测项显式标出。
- 审校只检查论证、来源和边界；作者不得自称独立审校通过。

### 软件工程/AI生成/后端数据

- 先冻结接口、数据模型、状态机、版本兼容、权限和失败语义，再写实现。
- 至少覆盖正常、空输入、非法输入、重复、超时、取消、重试、并发、权限拒绝、旧版本和服务不可用路径。
- 自查含语法/类型/单元/契约/集成检查及可复现命令；真实外部调用、模拟调用和本地夹具分开报告。
- 不硬编码假成功、不吞错误、不输出密钥或隐私、不把未知映射成成功；迁移有备份、回滚和幂等说明。
- Diff 只涉及授权路径；改动影响到其他岗位时先交接，不顺手重定义需求。

### 设计

- 先交可审阅视觉稿和状态图：正常、空态、加载、错误、拒绝、离线、过期、恢复和完成反馈都可见。
- 每个状态有动作、结果、下一步和无障碍名称；不依赖长文字解释才能理解程序意图。
- 标明响应式尺寸、键盘路径、焦点、对比度、禁用态、长文本和本地化溢出；组件状态与工程字段一一对应。
- 设计评审核的是意图，QA核的是实际渲染与行为；原型演示不等于真实服务可用。

### 测试

- 每个用例绑定一个验收ID、风险和责任岗位，明确测试层级（静态/VM/HTTP/浏览器/真实外部）。
- 先设计反例和未知变体，再补正常路径；覆盖边界、并发、恢复、权限、版本和数据隔离。
- 独立使用未被作者修改的夹具；保留首次失败、环境、哈希、命令、原始输出和复验差异。
- 不修代码、不改需求、不删除失败；发现夹具问题时单独标记，不把夹具失败写成产品缺陷。
- 报告说明已验证范围和不能推出的结论，不能以测试数量代替质量判断。

## 四、独立复核与缺陷台账

每条缺陷字段固定为：`缺陷ID`、产物/版本/哈希、触发输入、预期、实际、严重级别、直接原因、系统原因、逃逸门禁、责任岗位、修复版本、原案例复验结果、受影响回归、证据链接、状态。

严重级别：

- **P0**：安全、隐私、数据损坏、不可恢复或错误对外承诺；立即阻断交付。
- **P1**：主流程错误、教材核心事实错误、权限/版本隔离失效；未修复不得交付。
- **P2**：重要边界、可理解性、可维护性或证据缺口；需责任人和复验日期，不能无记录带过。
- **P3**：局部视觉、措辞或低风险便利性问题；可排期，但保留用户影响和期限。

每周复盘三类指标：重复缺陷率（同一系统原因再次出现）、缺陷逃逸率（在更晚门禁才发现）、证据完整率。辅助指标为首轮接收率、返修重开率、未知变体成功率和复验周期。不要用“员工写了多少、测试跑了多少、通过多少”单独评价能力。

根因复盘采用“五问 + 逃逸分析”：错误是什么、哪一条件触发、哪一门禁本应发现、为什么该门禁没发现、应增加什么合同/训练/夹具/工具；最后指定一个系统改进行动和责任岗位。连续三次同类缺陷，必须升级为流程或能力专项，不得继续归为个人粗心。

## 五、员工赋能与能力升级

先为每个岗位建立三层能力卡：知识（能解释）、执行（能按新任务完成）、判断（能发现未知和权衡）。每层只用可观察作品与独立证据评定：

1. **受指导**：按模板完成熟悉变体，必须逐项解释原因。
2. **可独立交付**：在冻结合同下完成未见小任务，经同岗独立复核通过。
3. **可处理未知**：复核者临时给新领域与冲突约束，员工先澄清、建风险模型、选择验证，再交作品。
4. **可做跨岗判断**：能把自己的假设、证据和限制交给下一岗位，且在真实反馈后修正方案。

赋能动作不采用泛泛讲座，改为每周一次“失败实验室”：挑一条真实缺陷，员工先独立复现，再解释漏检门禁，随后改清单/夹具/交接模板并在相似新变体复验。每人维护个人错误账本（触发条件、误判、修复动作、下一次预防证据），连续两周无重复同类缺陷才关闭训练项。高风险任务执行结对设计/结对复核；低风险任务逐步撤掉指导，避免永远依赖检查表。

## 六、30/60/90天落地

- **0–7天**：冻结G0–G5模板、缺陷字段和严重级别；为编辑、开发、设计、测试各选5个历史缺陷建立基线；不改历史结论。
- **8–30天**：所有新产物按门禁运行；每周失败实验室；建立黄金夹具、错版本夹具和未知变体；项目经理只接收有证据包的交付。
- **31–60天**：每岗位完成一次未见任务；统计重复缺陷率、逃逸率和证据完整率；对重复缺陷最多的系统原因开展专项改进并由QA复验。
- **61–90天**：在隔离的生产近似环境完成跨岗位闭环；对高风险路径做双人盲复核；依据连续三轮证据决定谁可从受指导升级为独立交付，不以一次成功升级。

## 当前限制与复验要求

本方案是质量系统设计，不证明现有员工已经具备上述能力，也不替代当前应用、教材、用户效果或生产系统的独立验收。落地首轮必须保留基线缺陷、未通过项和复验结果；新门禁本身也由测试岗位在实际交付中检查是否被执行。
