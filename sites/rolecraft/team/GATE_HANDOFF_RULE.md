# 门禁主动接力（常驻）

日期：2026-10-23。用户 Sheng 明确：岗位验收通过后必须立刻主动交给下一门岗，不得等用户再追问「发给 XX 了吗」。

本文件是员工常驻流程，绑定产品设计师、测试工程师、项目经理及所有验收岗位。项目长期记忆的同一条记录在 `.workbuddy-ai/memory/MEMORY.md` 的「门禁主动接力（2026-10-23）」。

## 规则

1. 当前门禁 Pass 后，签发岗位或项目经理立刻把同一版本交给下一门岗，并留下交接记录（目标、版本、证据位置、下一责任人）。
2. 设计签发 Pass 后，立即交测试工程师做合入前功能验证。
3. 下一门岗发现问题，走该领域的修正流程：退回唯一责任岗位返修，修复后由原验收岗位按新版本复验。项目经理协调，不代签、不代改专业交付。
4. 用户只验收各部门已经通过的内容。汇报优先给决策板图片，少写长文。
5. 设计 Pass 不等于可合入。合入前必须设计门与 QA 门都过。

触发背景：PR #12 设计门通过后未主动交 QA，需用户再推一步才派测。此后同类停顿视为流程未执行。

## 设计签发与独立 QA 的边界

两条门禁分开签发，结论不能互相代替。

- 视觉表达、信息层级、状态与可访问性按 [`DESIGN_COMMUNICATION_STANDARD.md`](DESIGN_COMMUNICATION_STANDARD.md)。该规范要求设计先交可审阅画面，并写明：应用实现交软件工程师，独立复核交测试员；设计稿、脚本或自查不能代替当前应用的真实操作验收。
- 设计验收由产品设计师签发。测试/功能验收由测试工程师签发。项目经理只收集结论、跟踪缺口，并在领域失败时打开返修交接；项目经理不代签设计验收或测试/功能验收。操作边界见 [`employees/core/project-manager/ACCEPTANCE.md`](employees/core/project-manager/ACCEPTANCE.md) 与 [`employees/core/project-manager/ROLE.md`](employees/core/project-manager/ROLE.md)。
- 产品范围不含设计表面时，设计验收可记 `not_in_scope`，但必须有产品交接里的依据。没有这句依据，不能省略设计门，也不能把 QA 门写成设计已过。

## 谁在 Pass 之后立刻做什么

| 刚通过的门 | 谁立刻交接 | 交给谁 | 下一门做什么 |
| --- | --- | --- | --- |
| 产品验收 Pass | 项目经理 | 产品设计师（范围内有设计表面时） | 按设计规范签发设计验收 |
| 设计验收 Pass | 产品设计师通知，项目经理同一轮派发 | 测试工程师 | 合入前功能验证；对照已签发的设计条件与产品条件 |
| 测试/功能验收 Pass | 测试工程师交回记录，项目经理收口 | 项目/发布总闸，再给用户 | 仅在产品、设计、QA 三门都有记录且无未关闭阻断时，项目经理才标项目/发布通过 |
| 任一验收 Fail | 该验收岗位保持失败 | 唯一责任岗位 | 修正后按新版本回到原门复验，通过后再接力下一门 |

内容审校、课程规格、检索或其他专项验收同样适用：本门 Pass 的当轮就交给产品合同里写明的下一责任人，不把「等用户问」当作交接完成。

## 合入条件

合入候选必须同时满足：

- 设计门：产品设计师对当前版本签发 Pass，或产品交接写明 `not_in_scope`。
- QA 门：测试工程师对同一版本的合入前功能验证签发 Pass，证据含原例或约定反例。
- 有问题的条目仍在修正流程中，不并入已通过结论。

只有设计 Pass、QA 尚未派发或尚未出具结论时，状态保持「设计已过、合入未开放」。

## 对用户的交付

用户看到的是各部门已经通过的内容。优先附决策板图片，说明本版通过了哪一道门、证据在哪。未通过、未派发和证据不足的门单独标出，不混进已通过材料。
