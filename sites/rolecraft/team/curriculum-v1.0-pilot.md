## 1. 试点目的与边界

学习者要在一个固定、可核对的缺陷快照上，冻结一条足以检验价值假设的最小任务：分开事实、推断和未知；给出允许动作、验收计划、停止条件与替代方案；说明为什么当前方案没有扩大成多 Agent 或自动改代码。练习训练的是“用证据冻结 MVP 决定”的能力，不是把一个构造问题包装成真实客户需求，也不是证明模型、工具或产品已经在生产中可靠。

1.0 试点只允许在本地隔离目录中阅读输入、写入练习文件和运行静态检查。不得改真实业务代码、访问正式数据库、创建真实工单、部署、发通知、连接外部模型或把构造结果写成真实用户反馈。没有真实学习者、真实任务、真人专家或真人学习者评审时，记录必须保持 `证据不足`/`未开始`，不能显示“已掌握”“已通过”“可录用”或职业认证。

## 2. 问题与输入

### 2.1 给学习者的问题

> 你收到一个固定的退款边界失败快照。请设计一个最小、可停止、可复验的 Agent/MVP 方案来整理证据、形成可审初稿并在准确意图获批后创建唯一工单。你必须说明什么已经知道、什么只是推断、什么仍需验证；不能修改退款实现、重跑生产测试、自动发布或外发通知。请让非作者能按你的文档复现正常路径和至少一条缺证/权限失败路径。

### 2.2 固定输入快照

输入来自 v12 `p01-mvp` 的 `task_contract_id: defect-mvp-contract-01`。在实现层应作为只读 fixture 绑定版本和 hash；以下内容是规格摘要，不能代替实际来源文件。

```yaml
input_snapshot:
  snapshot_id: defect-mvp-contract-01
  repo: repo@8e12
  source: src/refund.py
  source_ref: repo@8e12:src/refund.py:1-2
  report: test-report-71
  failure_ref: report-71:failure-1
known_facts:
  - 源文件 refund(days) 返回 days < 7
  - test_refund_day_7 输入 7，报告 expected=True、actual=False
allowed_actions: [read_source, read_test_report, create_issue]
trusted_scope:
  tenant: tenant-dev
  writable_project: refund-maintenance
excluded_work: [修改应用代码, 新业务规则决策, 自动发布, 外发通知]
```

`expected=True` 是报告给出的事实，不是已确认的退款业务规则；`days < 7` 与断言不一致只支持“边界行为存在差异”。学习者不能单凭此片段把 `<` 改为 `<=`，也不能写成“退款规则已确认”。若输入缺失、版本不一致或权限不明，应在作品中停止并列出补证要求。

## 3. 产出与作品包

学习者提交一个带清单的 `P01-MVP-EvidenceBundle`。Markdown、YAML 或 JSON 均可，但字段语义不可省略；每个文件都要有 `artifact_version`、`practice_id`、`created_at`、`source_refs` 和内容哈希。

| 作品项 | 必须回答的内容 | 最小要求 |
| --- | --- | --- |
| `problem-evidence` | 观察到的事实、推断、待验证问题、每项来源 | 三类分开；不得把构造输入写成真实用户证据 |
| `task-contract` | 目标、输入版本、允许/禁止动作、可信范围、产出契约、有效停止 | 至少包含缺资料、无权限、无批准、结果未知四类停止 |
| `acceptance-plan` | 主指标、护栏、比较基线、任务集合/分配、失败分母、停止条件 | 不能只写“完成工单”或“用户满意”；说明如何保留退出/失败 |
| `adr` | 问题、约束、至少两个可行方案、证据、选择、代价、反例、复查条件 | 至少解释为何当前不增加多写入 Agent，何时缩回普通程序 |
| `reproduction-notes` | 非作者复现步骤、输入/依赖/版本、预期正常与失败结果 | 只允许本地隔离；命令未运行时明确 `not_run` |
| `evidence-index` | 每项证据的 ID、路径/引用、来源版本、hash、采集方式、状态 | 能从入口定位到原始文本、日志或截图；不以结论替代原证据 |
| `reflection` | 当前假设、可证伪信号、已放弃取舍、下一次最小实验和停止/升级条件 | 选择下一步是修订当前合同、补证或进入 `e03`，并说明理由 |

作品的候选结果只表达“当前任务的设计是否可审”，不表达真实产品价值、职业能力或行业先进性。AI 生成的文字若被使用，必须保留原始输入/输出、引擎模式、版本和人工核对标记；没有配置时不得伪造调用收据。

## 4. 完成条件

提交前，学习者和接收岗位共同核对下列条件。全部满足才进入 `已提交`；这些条件只说明作品包结构完整，不自动授予能力结论。

1. **边界清楚**：所有关键主张都能回链到输入、正文或明确标为推断/未知；没有把 `expected=True` 当作业务真相。
2. **范围可执行**：目标、允许动作、排除动作、可信租户/项目和唯一写入边界一致；没有隐含改代码、部署、通知或扩大权限。
3. **验收可复核**：接受条件、失败分母、护栏、停止条件、缺证处理和结果未知处理均有具体描述。
4. **方案可解释**：至少比较一个普通程序/固定流程和一个含模型或动态补读的方案；选择说明收益、代价、反例和复查条件。
5. **复现可交接**：非作者可根据输入版本、命令、环境和预期输出重走正常路径及一条关键失败路径；未执行项逐项写 `not_run`。
6. **证据可回链**：作品清单能定位源文件、运行日志、截图或未取得证据；证据缺口有责任人和下一步，不用空白字段掩盖。
7. **安全停止**：遇到缺资料、无权限、无批准或结果未知时暂停，不创建第二个身份、不扩大动作、不声称完成。

## 5. 正常路径

1. **确认任务**：从当前任务卡进入 `V1-PILOT-P01-MVP-001`，看到教材版本、先修、产出和证据要求。
2. **锁定来源**：打开 `p01-mvp` 的“预定义公平实验”“MVP 契约”“架构决定”“练习与参考分析”，记录来源路径、章节标题和正文 hash。
3. **整理输入**：读取固定快照，逐项标注事实、推断、未知，登记 `source_ref`；不补写未给出的业务规则。
4. **冻结契约**：定义目标、输入、允许/禁止动作、可信范围、结果契约和有效停止；让缺证和未知效果成为显式结果。
5. **设计验收与 ADR**：先写比较基线、任务分配、失败分母和停止条件，再说明固定流程、动态补读或普通程序的取舍；解释不增加复杂度的理由。
6. **生成证据包**：按复现说明在本地隔离目录做结构/哈希检查（若未运行则标 `not_run`），保存日志/截图/manifest；提交前填写本人自述和未验证项。
7. **提交并回链**：点击提交后，作品、来源和版本进入 `已提交`，系统生成独立复验队列；任何 AI 建议单独显示，不覆盖学习者原文。

## 6. 关键失败路径与预期反应

| 失败 ID | 触发条件 | 学习者/系统必须记录 | 不得发生的结论或动作 |
| --- | --- | --- | --- |
| `P01-F01-FACT-INFERENCE-MIX` | 把测试报告的 `expected=True` 写成真实退款规则，或把边界差异直接定为代码缺陷 | 标出主张、来源和缺失业务规则；将验收结论改为未知并停止扩大范围 | 自动改 `<` 为 `<=`；声称规则已确认 |
| `P01-F02-MISSING-EVIDENCE` | 源文件、报告、版本或失败引用打不开/不一致 | 记录缺失项、hash/版本冲突、补证责任人和恢复动作；作品状态可为 `证据不足` | 用记忆、模型猜测或一张无来源截图补齐事实 |
| `P01-F03-AUTHORIZATION-BOUNDARY` | 试图访问正式项目、创建真实工单或使用未授予权限 | 记录拒绝、目标范围和停止时间；保留未执行状态 | 改用更大权限、换项目或创建第二个 action ID |
| `P01-F04-NO-APPROVAL` | 准确意图尚未获批准 | 保留候选、等待条件和批准人字段；状态为等待/未提交 | 把草稿当批准；把模型输出当用户批准 |
| `P01-F05-UNKNOWN-EFFECT` | 写入/下游结果未知、回执丢失或证据未读回 | 保留原 action/operation 身份、核对计划和未决效果；不重建新动作 | 写“已创建”“已完成”或静默重试造成重复 |
| `P01-F06-OVER-ENGINEERING` | 为展示 Agent 而加入规划、检索、批判、写入多个角色，却无额外可接受结果证据 | 与普通程序基线同条件比较，写出停止扩大范围条件 | 以角色数量、提示词长度或一次演示代替价值证据 |
| `P01-F07-CONSTRUCTED-AS-REAL` | 将教材构造结果、作者自查或 AI 建议写成真实用户/专家反馈 | 标明 `constructed_fixture`、`self_report` 或 `ai_suggestion`，保留真实证据缺口 | 声称试点成功、用户认可、真人审核或岗位胜任 |

任何失败路径都允许保存草稿；若未满足完成条件，不能进入“独立复验完成”或能力相关结论。

## 7. 运行、截图与日志证据

作品包至少声明以下证据项。实现方可提供字段或上传入口，但不得把字段存在当成证据已经取得。

| 证据 ID 类型 | 内容 | 取得规则与限制 |
| --- | --- | --- |
| `source_receipt` | 教材路径、单元/小节、版本、正文 hash、fixture ID | 由当前教材绑定生成；来源失配进入 `stale_version`/`证据不足` |
| `artifact_receipt` | 每个作品文件路径、字节 hash、创建时间、作者/修订号 | hash 用于定位收到版本，不证明论断正确 |
| `run_receipt` | 命令、工作目录、运行时版本、stdout/stderr、退出码、网络/外部写状态 | 本地隔离；未运行必须 `not_run`，不得补写期望输出 |
| `failure_receipt` | 失败 ID、首失败输入、实际反应、停止/恢复动作 | 至少覆盖一条缺证/权限/未知效果失败；作者自查不等于独立复验 |
| `screenshot_receipt` | 当前任务卡、产出字段、提交状态、版本徽章和结果反馈的截图 | 仅作为界面可见证据；不替代源文件、日志或真人理解 |
| `review_receipt` | 评阅者身份、角色、rubric 版本、逐项意见、时间、回链 | `professional_review`/`human_review` 必须由独立角色填写；1.0 当前均未取得 |

工程交接应让每条证据回链到 `practice_id`、`submission_id`、`artifact_version` 和 `source_sha256`。版本升级创建新提交，不覆盖旧作品、旧意见或首失败。

## 8. 评分维度（诊断量规，不是录用或认证量规）

每个维度使用 0–3 级描述，评阅者必须引用作品位置和证据 ID。加权分可用于定位补学，不得自动转换为“通过”“已掌握”或岗位概率；未有独立评阅时只显示未评估。

| 维度 | 权重 | 0 级 | 1 级 | 2 级 | 3 级 |
| --- | ---: | --- | --- | --- | --- |
| 证据边界与可追溯性 | 25% | 缺失/虚构来源 | 有来源但事实、推断、未知混杂 | 关键主张逐项可回链，缺口显式 | 在新限制下仍能保留证据边界并解释冲突 |
| MVP 范围与任务契约 | 20% | 无目标或越权 | 有目标但允许动作/结果不完整 | 目标、输入、允许/禁止和停止可执行 | 能根据约束缩小/扩大范围并解释业务代价 |
| 验收、失败分母与停止 | 20% | 只有“成功”描述 | 有检查项但无护栏/失败处理 | 正常、缺证、权限和未知效果均可复核 | 能识别分母偏差并提出下一次可证伪实验 |
| 方案比较与 ADR | 15% | 只有框架/口号 | 列方案但没有证据或代价 | 有基线、选择、取舍、反例和复查条件 | 能在结果不支持时缩回普通程序或停止复杂化 |
| 复现与证据包质量 | 10% | 无步骤/无法定位 | 步骤存在但版本或输出不全 | 非作者可重走限定范围路径，未执行项明确 | 能解释环境差异、重放边界和证据失效原因 |
| 安全边界与岗位交接 | 10% | 扩大权限或外部副作用 | 仅口头写安全 | 目标、授权、批准和接收人清楚 | 失败时保留身份/效果并把问题交给唯一责任岗 |

最低交接要求是六个维度均有作品位置和状态；某维度缺原始证据时，评分写 `insufficient_evidence`，不以文字质量补齐。

## 9. 记录类型、流程状态与反馈层级

### 9.1 记录类型

| `record_type` | 谁写 | 允许内容 | 不能推导 |
| --- | --- | --- | --- |
| `draft` | 学习者 | 可编辑作品、版本、草稿证据和未验证项 | 不能推导提交、掌握或审核 |
| `self_report` | 学习者 | 自述完成动作、困难、证据链接、下一步意图 | 不能推导独立正确、能力或真人认可 |
| `ai_suggestion` | 本地规则/模型适配器（如有） | 依据当前教材和作品字段提出缺项、来源或反例建议 | 不能覆盖原稿、签署批准或产生评分结论；无配置则 `not_run` |
| `professional_review` | 独立课程/实训/技术评阅者 | 按本规格和 rubric 逐项核对、指出问题和补证 | 不能冒充真人行业专家或真实用户反馈 |
| `human_review` | 真实、有资质且身份可记录的行业/教学专家 | 依据作品和限制给意见、质疑或认可范围 | 1.0 当前没有真人评审，不得填造姓名、意见或结论 |

所有记录带 `review_scope`、`source_version`、`evidence_refs` 和 `created_at`；AI/自述/专业/真人内容在界面和导出中分层展示。

### 9.2 作品流程状态

| 状态 | 进入条件 | 可执行动作 | 对外语义 |
| --- | --- | --- | --- |
| `未开始` | 没有该试点的草稿或提交 | 开始、查看输入和先修 | 还没有作品证据 |
| `已提交` | 作品清单、版本和最小字段齐全，学习者主动提交 | 查看、补充下一修订；不得覆盖旧提交 | 已收到作品包，尚未独立复验 |
| `待独立复验` | 提交已锁定，已分配独立复验者/队列 | 等待或查看范围；作者不能改写评阅结论 | 不是通过，也不是已掌握 |
| `发现问题` | 独立复验发现事实、契约、证据、边界或复现问题 | 查看问题、创建新修订、保留原失败 | 需要返修和原例/受影响范围复验 |
| `证据不足` | 关键输入、运行、独立评阅、真人意见或必要来源缺失 | 补证、标记未运行、缩小结论或停止 | 不能形成能力/通过结论 |

若独立评阅在限定 rubric 内全部满足，系统可另存 `review_outcome=met_within_scope`，但产品面仍保留提交版本、评阅范围和局限；不得把它改写为“已掌握/职业胜任”。`human_review` 在 1.0 没有真实记录，相关状态保持 `未开始` 或 `证据不足`。

## 10. 反馈与下一步复盘

反馈必须逐项回链作品和证据，不用“答案不够好”作为唯一意见。评阅者至少回答：

1. 哪一项事实、推断或未知被正确/错误分类？来源是否可读回？
2. 哪个范围、停止或批准条件会导致真实风险？是否有越权或重复动作风险？
3. 哪个正常/失败路径没有证据？需补什么输入、日志、截图或独立复验？
4. 选择的普通程序、固定流程或动态方案是否有同条件基线和可证伪理由？如果没有收益，何时缩回？
5. 下一次应当修订当前合同、补证、重跑原例，还是进入后续 `e03`？负责人、版本和复验动作是什么？

学习者在 `reflection` 中完成一次复盘：

- 写出一个会推翻当前 MVP 假设的观察（例如缺证路径占比高、普通程序已同样满足目标）；
- 说明尚未验证的真实问题、用户/专家/运行证据及不能取得的原因；
- 选择一次最小后续动作并保留原作品；若 `发现问题`，先修原问题再按原例与受影响范围复验；若 `证据不足`，先补证或缩小主张；若限定范围复验完成，阅读 `e03` 并把安全授权/停止条件接入下一任务；
