# Q23 · 工具参数的 JSON 格式正确，为什么不等于调用安全、业务合法？

版本：interview-answers-v1 / Q23-r1。本文为完整参考解析；案例和验证方案除特别注明外均为教学构造，未在本次写作中执行。

JSON正确只说明语法能解析；即使符合Schema，也通常只说明字段结构符合要求。安全与业务合法性还取决于字段意义、对象归属、当前授权、准确批准和任务状态，必须由宿主及资源服务强制检查。

## 一份合法JSON怎样仍然非法

教学例中模型返回：

```json
{"project":"another-tenant","title":"退款缺陷","body":"已证实应改为小于等于7天","evidence_ids":["E999"]}
```

这是可解析的字符串和数组，但目标项目可能越权，E999不属于本次证据包，正文也可能把未知政策当事实。若模型再塞入 `approved:true`，这不仅是未知字段，更不能成为批准来源。靠“模型一般听话”不能消除这些问题。

校验按层进行：先拒绝未知字段、缺字段、空值、超长与错误类型；再核引用ID和版本、数量与业务前提，例如一条工单目标不能变成多条；再由可信会话主体核项目归属与任务范围；再检查批准是否绑定当前动作、工具版本、目标revision和准确参数指纹，且未过期/撤销。通过后保存不可变参数，发送前复查动态约束与预算，不能让模型补正文后沿用旧批准。

## 拒绝之后怎样做

无效引用可返回明确缺项让模型重取允许证据；正文中根因未获规则支持，可降为待核假设或等待规则，这取决于原任务允许的产物，不能擅自降低目标。越权项目不应被静默替换成默认项目以掩盖错误；拒绝并说明允许范围。批准过期需重新获得有效批准，不能简单重试函数。

读取也要在数据进入模型前核权限与投影范围。最终答复没有泄漏，并不能补救先把另一租户资料送进上下文的错误。哈希只检查内容一致性，不证明来源可信或用户批准。

验证时同时给合法对照和结构合法的恶意例：跨租户项目、不存在引用、错数量、过期批准、批准后改正文、并发重复请求。检查发送次数与外部对象，而非只看提示中的拒绝文字；拒绝例应无新增效果，合法例应真实可执行。本题给的是分层检查方法，任意根因主张仍需相应专业证据。
