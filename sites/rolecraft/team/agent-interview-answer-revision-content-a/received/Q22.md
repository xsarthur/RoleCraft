# Q22 · 如何设计工具名称、描述和参数 Schema，减少错选工具与错误参数？

版本：interview-answers-v1 / Q22-r1。本文为完整参考解析；案例和验证方案除特别注明外均为教学构造，未在本次写作中执行。

好的工具接口让模型区分“何时选、需要什么、会得到什么、何时不要选”，并让宿主独立验证参数。名称只写 `process_data` 会混淆查找、读取和写入；应按业务动作与对象拆分，例如 `search_reports`、`read_report`、`create_issue`。

## 把三个近邻工具说明清楚

| 工具 | 使用前提与输入 | 返回及不负责的事 |
| --- | --- | --- |
| search_reports | 不知道确切ID，只有现象；query非空 | 候选ID、摘要、版本；不保证全文，不创建 |
| read_report | 已有当前范围内确定ID | 报告正文、修订、来源；不接受任意本机路径 |
| create_issue | 有经核草稿且准确内容获批 | 动作回执或结构化失败；有副作用，超时可能未知 |

描述需要单位、必需前提、否定边界和错误含义，避免只写“智能处理报告”。例如“看看报告，先别建单”应匹配只读行为；出现“建单”两个字不是选择写工具的充分条件。

## Schema表达结构，程序补业务约束

以下为宿主校验用的教学Schema，不声称所有模型API支持完全相同子集：

```json
{"type":"object","properties":{
  "report_id":{"type":"string","minLength":1,"maxLength":80},
  "format":{"type":"string","enum":["text","structured"]}
},"required":["report_id","format"],"additionalProperties":false}
```

对数值注明单位并设范围；对互斥字段明确只允许其一，可用宿主校验或所用Schema子集表达；可省与可空分开定义，不靠模型猜默认值。缺report_id应搜索或询问，而非用空串装作完整参数。身份、租户、令牌和批准不开放给模型填写，资源ID虽由模型选择，也须核对象权限。

结果合同同样重要：输出稳定ID、版本和状态；参数错误、无权限、无匹配、暂时不可用、未知效果分别编码，给上层正确的修复分支。普通文字“成功”不足以证明业务结果。

验证集应包含已知ID、只有现象、否定写入、双意图、拼错ID、未知字段、边界长度和范围错误。分开测候选召回、工具错选、参数无效和正确等待，观察无效提议是否在发送前被拒绝。描述改得更长不必然更好，只有错选减少且上下文代价可接受才保留。
