# Q16 · 面对带前置依赖的复杂任务，如何生成和验证可执行计划？

版本：interview-answers-v1 / Q16-r1。本文为完整参考解析；案例和验证方案除特别注明外均为教学构造，未在本次写作中执行。

可执行计划要从验收产物反推前置条件，而不是把自然语言待办编号。每个节点必须说明输入从哪里来、输出怎样判定、依赖谁、用什么能力、需要哪些权限和预算；计划只是候选，执行前与执行后还要分别校验。

## 从目标建立依赖图

教学目标需要报告事实 F、适用规则 P、源码观察 S 和带引用说明 D。已知报告ID，但规则ID从报告取得，可构造：

```text
read_report R → F、rule_id、source_path
R → read_rule P
R → read_source S
F + P + S → draft D → verify
```

`read_rule` 与 `read_source` 只有在R提供合法标识后才可进入执行前沿；两者可并行，但D必须显式依赖三份产物。节点记录 `node_id/deps/inputs/expected_outputs/tool_version/scope/estimated_budget/status/evidence_refs`，计划记录目标和计划版本。某产物没有允许的生产者时应报缺口，不能让模型发明工具。

## 六个检查层

首先核ID唯一、依赖存在、输入输出名一致；其次用拓扑排序检测环。第三，输入必须来自初始材料或祖先节点，不能偷用并行节点尚未产出的内容。第四，所有必需验收产物都有生产者，且未弱化标准。第五，核工具版本、资源权限、估计资源与硬预算；能排程不代表有权执行。第六，写节点走独立动作账本与准确批准，不能因为计划通过就提前开放写权限。

执行时前沿是“依赖已完成且证据仍有效”的节点，再应用并发和互斥限制。工具返回只算一次观察；只有输出经过节点验收才标完成。若P失效，D也失效；S仍有效就保留。已发生的写效果不能通过删节点撤销，须单独核对或更正。

## 反例和验证

给R增加依赖D就形成环，预期执行前拒绝；移除rule_id的来源，预期报告缺输入；让D读取不在祖先链中的P，预期拒绝隐式依赖；配置无权的read_rule或超预算，预期不发请求。正常图则先R，再P/S，最后D，并有对应版本产物。再让P在运行中变更，应使相关后继失效并重新验收，不能只检查初始JSON。以上为教学计划与测试方案，未代表真实规划模型能稳定生成正确图。
