# 职造当前产品设计复盘（视觉与交互）

- 角色：设计师
- 日期：2026-10-15（Asia/Shanghai）
- 范围：只读检查 `dist/index.html`、`dist/learning-workbench.css`、`dist/learning-workbench.js`、`dist/auth-career-v15.js` 与 README；未修改应用代码，未进行真实浏览器/读屏/真人理解测试。
- 依据：`team/DESIGN_COMMUNICATION_STANDARD.md`（视觉先表达意图），以及职造当前目的：帮助学习者从个人起点理解职业能力、阅读有出处教材、通过项目实践形成可展示证据，并能按自然语言问题定位对应内容。

## 总体判断

当前产品已形成“路线—目录—正文—项目—记录—内容问答”的骨架，视觉风格统一、操作目标大多可见，也明确区分自述与独立验证。但主任务仍被多个平行入口、历史/当前版本和固定底部问答同时争夺；用户能看到很多内容，却不总能快速回答“我现在应完成哪一步、完成的证据是什么、下一步为何是它”。优化优先级应先收敛主路径，再补状态与证据反馈，最后扩展探索入口。

## 优先级问题与建议

### P0：首屏目标与入口过多，学习路线未成为唯一主行动

**证据**：`index.html` 的侧栏同时放置首页、课程学习、学习记录、个人设置；脚本还保留标准、地图、作品、复盘、历史、生成等更多工具入口。学习工作台首页又以“学习路线/课程目录”双标签、工程全景、自然语言问答并列。视觉上没有一个明确的“当前任务卡”把职业目标、当前阶段、可交付证据和下一步绑定起来。

**风险**：新用户先在入口之间选择，而不是开始一次可完成的学习任务；“阅读”容易被误认为已经形成能力或作品。

**建议**：首页只突出一个主卡：`当前阶段 → 当前任务 → 产物/证据 → 开始`；课程目录、工程全景和问答降为次级探索。侧栏将低频工具收进一个“更多”分组，并显示当前所在位置。每阶段卡用同一视觉结构表达“输入、动作、输出、验证”，不要只呈现章节列表。

**验收**：首次进入无需解释即可指出下一步；从首页到首个可执行任务不超过一次主操作；目录/问答不与主行动使用相同视觉权重。

### P0：固定底部问答条持续占据视线并可能遮挡正文

**证据**：`.lw-assistant` 使用 `position:fixed`，桌面固定在底部，移动端 `left/right:8px`；正文、分页、项目表单没有为其留出语义上的避让区。问答打开后面板最高占 `60–65dvh`，且点击外部会收起；输入框始终贴近底部。

**风险**：阅读、保存笔记、分页等主任务被遮挡或被意外收起；用户难以区分“查教材”与“当前阅读动作”。

**建议**：默认折叠成不遮挡内容的“问教材”入口；打开时采用右侧/内嵌面板，或为正文增加明确的底部安全间距并锁定面板内滚动。打开后保留当前查询和结果，明确显示“基于当前章节/全书”；关闭不应清空上下文。移动端优先使用全屏工作表而非悬浮卡。

**验收**：正文末段、保存按钮、分页在问答打开时仍可见和可聚焦；键盘焦点不会跳出面板；面板关闭后回到触发按钮。

### P1：阶段关系表达仍偏“列表”，未充分展示可选、前置和完成证据

**证据**：`STAGES` 以六张卡和章节链接呈现；`.lw-stage` 采用编号、标题、输出和链接，但没有明确区分必修、推荐、可选、已完成、未知。首页文字说明“组件按需求采用”虽存在，视觉上仍像线性流程。

**风险**：学习者把章节数量/阅读动作当作阶段完成，把可选组件误解为必经链。

**建议**：阶段卡增加可辨状态条：`未开始 / 阅读中 / 已提交证据 / 待独立验证`，状态同时使用形状、标签和边界；在阶段之间使用短连接线或“可选分支”标记，仅当课程数据提供正式先修时才画箭头。把“阶段输出”改成具体证据示例（如运行记录、评估表、复盘结论）。

**验收**：不看长段文字也能辨认当前阶段、必经先修、可选分支和完成证据；状态不依赖颜色。

### P1：版本与历史身份虽有文字提示，但视觉层级不足

**证据**：正文通过 `历史教材 v10`、`当前教材 v12` 提示区分；记录页同时显示当前与历史记录；导航仍使用相似的章节卡和链接样式。

**风险**：用户可能把历史笔记、旧章节或旧问答当作当前可用内容。

**建议**：在页面标题区域增加版本徽标和只读图标；历史页面采用稳定的暖灰/虚线边界与“只读历史”标签，当前内容使用主色边界。问答结果每张卡固定显示 `内容版本 / 来源小节 / 是否当前职业`，避免只在正文深处说明。

**验收**：仅看标题、卡片和按钮即可区分当前/历史；历史页面没有与当前“开始/保存”同样的主按钮。

### P1：自然语言推荐结果的“为什么”和“下一步”层级不够清晰

**证据**：结果卡同时呈现匹配理由、原文证据、来源、操作按钮；`.lw-result-actions` 将详情折叠与主按钮并列，检索上下文、问答主题、会话历史都堆在同一面板。

**风险**：用户看到很多证据但不知道应打开哪个小节，或误以为推荐答案就是能力结论。

**建议**：结果卡固定采用三层：`推荐去哪里`（主按钮）→ `为什么匹配`（一句话）→ `原文依据/版本`（折叠详情）。无匹配、歧义、模型不可用、过滤非职业问题使用不同插图/图标和恢复动作；不要只靠状态文字区分。

**验收**：用户能在 5 秒内指出首选章节和下一动作；证据与建议不混为“已解决”。

### P1：项目工坊把自述进度做成进度条，容易产生完成错觉

**证据**：项目卡显示 `x / y 项自查完成` 和 `.mini-progress`；同时用小字说明“不自动授予职业资格”。

**风险**：视觉进度条仍会被理解为能力进度或项目通过，和产品标准中“自述不等于独立评价”冲突。

**建议**：将进度条改为“资料收集状态”，旁边并列三个状态槽：`自述已填`、`运行证据缺失/已有`、`独立评价：未开始`。仅当真实记录存在时显示对应状态，不用百分比作为主视觉。保存成功、保存失败和导出动作在表单附近反馈。

**验收**：不读说明文字也能看出自查、自述、运行证据和独立评价是不同对象。

### P2：可访问性和响应式仍需真实验证，存在可见风险

**静态证据**：键盘跳转基础已存在（skip link、标题 `tabindex=-1`、dialog 关闭后恢复焦点、`aria-live`）；但教学图放大、问答面板、移动导航均为动态区域，尚无浏览器/读屏证据。移动端问答按钮使用 `⌃/⌄` 形状，含义依赖上下文；表格要求横向滚动，代码块和长标题可能造成横向压力。颜色变量如 `#53675e`、`#7a927b`、`#66836d` 需在真实背景上做对比度核查。

**建议**：补做 320/375/768/1280 CSS px 键盘、缩放 200%、读屏和减少动态效果测试；为问答打开/关闭、加载中、无结果、错误、歧义、版本切换分别记录焦点与公告；为图标按钮提供文字或稳定 `aria-label`；检查焦点环、链接下划线、表格列标题和移动端底部安全区。

**验收**：QA 提供真实浏览器截图/操作记录；不以静态代码存在 `aria-*` 作为通过证据。

## 建议的下一轮视觉交付

1. 先交首页“当前任务卡”与六阶段状态卡视觉稿，标明当前/可选/待验证状态。
2. 再交问答面板的折叠、打开、加载、无匹配、歧义、失败和有依据结果共七个状态。
3. 交版本/历史身份和项目证据状态的视觉稿。
4. 由产品经理确认主路径与验收条件，软件工程师实现，测试工程师按上述验收独立复核；真实用户理解由用户研究员取证。

## 领域自查与未验证项

- 已观察：静态入口、工作台结构、阶段卡、正文阅读器、问答结果卡、项目档案、记录页、版本提示、响应式 CSS 和焦点相关代码。
- 未观察：真实浏览器布局、真实移动设备、键盘完整路径、读屏、对比度工具、用户完成任务时间、用户是否误解进度/推荐。
