# 数字员工专业负责与持续成长 · 产品需求与流程

日期：2026-10-14  
岗位：产品经理  
状态：产品方案草案，待项目经理协调后由测试工程师独立核验

## 1. 目标

让每个数字员工在完成交付的同时，持续积累可复核的职业技能和专业知识证据。交付结果和成长结果必须分别记录，不能用任务完成率、自评、学习时长、提示词数量或文档字数替代能力判断。

本方案适用于产品、课程、设计、软件、测试、内容、研究、运营及新增专项岗位。岗位的专业标准仍由对应岗位负责；本方案只规定共同的任务、交接、证据和复盘流程。

## 2. 双轨结果模型

每项任务同时维护两个状态：

- **Delivery（交付）**：按任务合同完成了什么，是否通过该岗位的交付门槛。
- **Growth（成长）**：本次工作是否产生了能力提升的独立证据，能力处于跟随、独立交付或设计/优化阶段。

一条轨道不能覆盖另一条轨道。例如，交付通过不代表员工已具备稳定职业能力；课程完成或自我总结也不代表交付可靠。没有真实用户、同行、专家或生产证据时，要明确标记为未验证。

## 3. 任务职责合同

每项工作进入执行前必须有一张任务合同，至少包含：

| 字段 | 要求 |
| --- | --- |
| 任务 ID 与版本 | 变更时升版本，不覆盖旧合同 |
| 用户问题与预期结果 | 描述谁在什么场景遇到什么问题 |
| 唯一责任岗位 | 只能有一个最终交付责任人 |
| 协作者与独立复核人 | 写明输入、依赖和复核权限 |
| 范围与不做项 | 防止越界和隐性扩张 |
| 交付物 | 文件、接口、研究记录或可观察结果 |
| 验收条件 | 可观察、可复现、与版本绑定 |
| 预算、时间与风险 | 超出边界时的升级条件 |
| 证据路径 | 产物、运行记录、来源、反馈和审校位置 |
| 交接对象与截止时间 | 明确接收人和接收格式 |

责任岗位可以自检，但只有指定的独立复核人能够给出复核结论。范围变化必须形成新版本，保留原失败和原复核记录。

## 4. 任务生命周期

1. **提出（Intake）**：产品经理记录用户问题、价值假设、现有基线和未知项。
2. **定界（Scope）**：产品经理确定范围与不做项；专业岗位补充领域约束。
3. **拆解（Plan）**：项目经理按职责拆成互不重叠的子任务，注明依赖和交接顺序。
4. **执行（Execute）**：责任岗位只写授权路径，保存版本、环境、决策、失败样本和成本记录。
5. **交接（Handoff）**：提交目标、输入、产物、接口/来源、已验证、未验证、风险和复验步骤。
6. **独立复核（Independent Review）**：测试、内容审校、用户研究等按各自门槛检查，不替责任岗补做工作。
7. **关闭（Close）**：项目经理分别汇总 Delivery 和 Growth 结果，登记差距、责任、下一步及复验条件。
8. **复盘（Retrospective）**：只选择一至三个高影响偏差，生成有负责人、截止时间、证据和回归方法的改进行动。

状态建议为：`draft → scoped → in_progress → handoff → independent_review → rework → retested → closed`。`closed` 只表示对应门槛已由独立复核确认。

## 5. 成长循环与能力等级

每个岗位维护自己的能力矩阵，至少包括专业知识、机制/方法、实践执行、风险判断、协作交接和复盘改进六类能力。每项能力使用三档：

- **L1 跟随**：能在明确示例、边界和复核下完成练习。
- **L2 独立交付**：能在真实任务中独立完成，并通过反例或第二种情境复验。
- **L3 设计/优化**：能提出方案、解释取舍、改进流程，并让他人复用。

没有跨情境、独立评审或真实反馈时，不自动升阶。

每个周期每人最多设一至两个成长目标，统一用以下格式：

> 在【真实任务/受控练习】中，独立完成【可观察动作】，产出【证据】，通过【指定门槛】。

学习内容、受控练习、真实任务、独立评审、复盘和下一目标形成闭环。练习可以失败，但必须与生产交付分开标记。

## 6. 证据账本

每条能力或交付主张都应能追到证据条目。建议字段：

`claim_id`、主张、任务/版本、岗位、证据类型、文件链接或哈希、执行环境、日期、独立复核人、状态、局限、下一步和复验条件。

证据类型按强度区分为自述/学习记录、任务产物与运行记录、独立审校/测试、真实用户/同行结果。必须保留首次失败、修复版本和复验结果。合成数据、离线模拟、代码静态检查不能写成真实用户或生产证据。

## 7. 复盘与校准

每周进行一次 15–30 分钟异步复盘，只看阻塞、高风险和重复缺陷；每月做一次能力矩阵校准。复盘卡固定记录：

- 事实：目标、基线、实际结果、版本和环境；
- 偏差：哪个验收条件未满足，首个失败样本是什么；
- 根因：需求、知识、实现、协作、验证或资源；
- 决策：修复、降级、暂停或保留及理由；
- 学习：要补的知识和下一次受控实践；
- 行动：唯一责任人、截止时间、证据和回归用例；
- 状态：`open / in_progress / retested / closed`。

复验完成前，改进行动不能标记为 `closed`。项目完成、报告写完或自评通过都不能替代复验。

## 8. 产品验收条件

- **AC-01**：每个新任务均有唯一责任岗位、范围、不做项、验收条件和证据路径；缺项不能进入执行。
- **AC-02**：交付状态和成长状态分栏显示，任何一栏未验证不会被另一栏覆盖。
- **AC-03**：交接包可按步骤复现，并注明环境、版本和限制；缺口会退回并登记。
- **AC-04**：独立复核保留首次失败、修复版本和复验结果，历史记录不可覆盖。
- **AC-05**：每个成长目标绑定真实任务或受控练习及至少一项独立证据；未通过不得自动升阶。
- **AC-06**：每条复盘行动有负责人、截止时间、证据和回归验证；未复验不能关闭。
- **AC-07**：抽查时能从主张追到任务、版本、证据、复核和局限；断链状态为 `insufficient`。
- **AC-08**：报告区分本地/离线/模拟、真实用户、真人专家和生产证据。
- **AC-09**：版本更替保留旧合同、旧审校、失败记录与新结果的关联。
- **AC-10**：至少一项真实反馈或实训作品用于校准成长目标；没有时保留证据缺口。

## 9. 一人公司的最小落地方案

首轮只选一个高频岗位和三项真实任务，运行两周：

1. 在仓库 `team/task-contracts/` 保存 Markdown/YAML 任务合同；
2. 在 `team/evidence-ledger.jsonl` 追加证据条目；
3. 在 `team/retrospectives/` 保存复盘卡；
4. 使用任务合同、交接包、证据条目和复盘卡四个模板；
5. 每周异步复盘一次，每月校准一次能力矩阵；
6. 首轮只观察三个指标：按合同交付率、复验后缺陷率、成长目标独立证据率。

实现只依赖现有 Git、Markdown、JSON 和本地脚本，不新增数据库、付费服务或外部上传。两周后依据证据断链、重复返工和岗位越界情况调整模板，再考虑接入学习工作台。

## 10. 责任与限制

产品经理维护范围、用户场景、验收条件和指标；项目经理维护依赖、状态、交接和复盘；各专业岗位维护本领域标准和产物；测试工程师独立验证。流程落地最多证明“本轮可追踪”，不能单独证明职业胜任、用户满意、行业先进或生产可持续。
