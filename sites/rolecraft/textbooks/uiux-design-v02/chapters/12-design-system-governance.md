## 本节要学会判断什么

1. 设计系统升级有没有**可核对的公共合同**（对象身份、版本、事件分层、风险/焦点语义），而不只是「新画了一个弹层」。  
2. 五个真实调用点里，哪一步必须**阻断写操作**、哪一步只允许**只读例外**、回滚时哪些业务事实**绝不能清空**。

**成立条件**：有可盘点的调用方、可核对的版本字段、权限/批准/外部效果分开、独立 QA 用原反例复验。  
**边界**：本章**不实现**支付服务，**不证明**真实发布或回滚已成功；所有编号、时间、记录均为合成。  
**决定权**：设计负责人提出变更；产品与风险责任者决定业务暂停或例外；发布负责人协调回退；QA 按原例复验。设计师不能私自决定忽略金额或权限。

> **先记住**  
> - 组件整齐 ≠ 系统有效；旧调用者能否保持正确含义才算有效。  
> - `submitted`（批准请求已提交）≠ 退款成功；不得被文案翻成「已退款」。  
> - 例外不能用来绕过「必须绑定当前版本」这类不变量。

## 例子：一次会翻车的点击

主管**许然**打开待批列表里的退款申请 **R-81**。摘要显示订单 **O-7819**、金额 **CNY 268.00**、政策 **P-07@v3**、申请版本 **v4**。她还没点确认，后台有人把同一申请改成了 **v5**。她点下旧页面上那个叫「批准」的按钮。

**正确可观察结果（教学预期）**：界面报告**版本冲突**，保留她刚看过的旧摘要与差异，**禁止**按旧内容发送批准；页面**不得**立刻显示「已退款」。

如果旧组件只传了申请 ID、旧页面又把 `approved` 当成退款成功——上面这场点击就会装成成功。用合同、盘点、门禁、例外和回滚拦住这类假成功，就是上面机制块要你学会的判断。

## 1. 用可复现失败开提案，而不是用「样式不统一」开提案

### 1.1 本节要学会判断什么

提案输入必须是**可复现、会伤语义**的失败，而不是「看起来不齐」。若三条 DEF 未被五个 CALL 暴露，变更范围会假缩小。

### 1.2 概念对照（先看）

**读图/读表任务**：指出哪一条 DEF 会直接制造「假已退款」文案；哪一条会用主题盖住风险与焦点。（无权角色批准入口见 §3 CALL-01 盘点，不在本 DEF 表内。）

| 原始失败 | 暴露调用点 | 用户侧可观察伤害 |
| --- | --- | --- |
| **DEF-01** 旧组件只传 R-81，不知用户批的是 v3 还是 v4 | CALL-01 / CALL-02 | 批错版本；冲突时无法证明「当时所见」 |
| **DEF-02** 旧页面监听 `approved` 后立刻显示「已退款」 | CALL-02 / CALL-03 | **假成功**（撞 PF-COPY / 诚实反馈底线） |
| **DEF-03** 租户主题把危险状态和焦点盖成品牌色 | CALL-04 | 风险不可辨、键盘焦点丢失 |

### 1.3 小案例：输入 → 动作 → 可观察结果

| 步骤 | 内容 |
| --- | --- |
| **输入** | DEF-01–03 + CALL-01–05 盘点；目标合同 2.0 |
| **动作** | 写下 CR-08：批准意图绑定当前摘要与版本；提交/批准结果/外部退款结果分开；品牌不覆盖风险与焦点 |
| **可观察结果（教学）** | 提案写清**非目标**（本轮不实现支付、不改退款政策、不自动迁移真实历史批准）与**成功条件**（每调用点必要字段齐、事件消费正确、未决可保持、同一组异常轨迹可复验） |

### 1.4 练习 / 常见翻车

- [ ] 用一句话区分「样式债」和 DEF-02。  
- [ ] 指出：CALL-03 把一个 `approved` 当整批成功，属于哪类语义伤害？  
- **翻车**：把「加一个二次确认弹层」写成已修复 DEF-01——若仍无 `refundRevision`，确认的仍是不稳定对象。

> **新手常做 vs 专业做法**  
> - 新手：先画新弹窗，迁移「以后再说」。  
> - 专业：先冻结合同与反例，再让看得见的 UI 跟着合同走。

## 2. 先改合同与身份，再改按钮长相

### 2.1 本节要学会判断什么

1.x → 2.0 表示**调用合同不兼容**；组件包版本、申请版本、政策版本是三种对象，互不替代。没有公共合同，就无法判断「能不能无修改替换」。

### 2.2 合同差异图（先看 diff，再读说明）

**读图任务**：圈出被删的隐式成功语义；写出 `submitted` 允许证明什么、禁止暗示什么。

```diff
 ApprovalAction
- input: requestId, title?, body?, brandColor? // 仅1.x旧名；值是申请ID；下称 legacyRequestId
- event: approved(requestId) // 旧调用者常误当退款完成
+ input: tenantId, ticketId, refundId, refundRevision
+ input: orderId, amount, currency, reason, policyVersion
+ input: permissionState, approvalState, effectState
+ event: reviewRequest(refundId, refundRevision)
+ event: confirmApproval(refundId, refundRevision, reviewedFields)
+ event: submitted(refundId, refundRevision, requestId) // 本次批准请求已提交，不是退款成功
+ outcome: 独立接收授权服务批准结果与外部效果结果
- visual: theme.brand 直接覆盖所有强调状态
+ visual: action.primary 可随主题；status.danger/pending 与 focus.ring 独立
```

> **何时别用**  
> - 不要把历史 1.x 的 `requestId`（本例曾错误命名的申请字段）原样当成 2.0 的 `requestId`。核实值为 R-81 后映射到 `refundId`，旧名标作 `legacyRequestId`。  
> - 不要拿发送尝试 ID（如 `send-01`）填 `refundId`。  
> - `reviewedFields` 只记录「用户确认了哪份摘要」，**不是**前端拥有审批权的证明。

### 2.3 小案例：同一申请，两次尝试

| 步骤 | 内容 |
| --- | --- |
| **输入** | 申请仍是 `R-81@v4`；先发退款尝试 `send-01`，失联后再发查询尝试 `query-02` |
| **动作** | 每次尝试各自记尝试 ID，但始终关联同一 `refundId` 与申请版本 |
| **可观察结果** | 查询**不**创建 R-82；`submitted` 只证明该次批准请求已提交；实际退款发送另有自己的尝试 ID |

### 2.4 练习 / 常见翻车

- [ ] 把「组件升级到 2.0 包」与「旧批准自动获得新业务版本」打成对错题——后者为错。  
- [ ] 若消费者只认识 `success`，能否由适配层把 `submitted` **编造**成成功？——不能；必须迁移消费者。  
- **翻车（假开通/假成功）**：结果区写「已退款」但外部效果仍是未知/待核对 → 违反内容诚实（PF-COPY）。

迁移顺序由**风险与依赖**决定，不由「谁用量大」决定。批量缺逐项结果会放大未知，不应最先切换。

## 6. 回滚恢复可接受状态，不假装时间倒流

### 6.1 本节要学会判断什么

已经批准、已发送或结果未知的 R-81，**不能**随组件库回到 1.x 而消失。回滚 UI 与修数据是不同决定。

### 6.2 回滚决策表（先看）

**读表任务**：找出两行「禁止动作」若违反，会分别造成假成功或假失败。

| 触发 | 可执行回退 | 必须保留 | 禁止动作 |
| --- | --- | --- | --- |
| 新布局严重遮挡确认字段 | 停 2.0 写入口，恢复能完整查看摘要的兼容页 | 当前版本、未决结果、原审计 | 恢复缺摘要的一键批准 |
| `t-maple` 主题覆盖危险/焦点 | 回退主题映射到安全默认值 | 租户身份与业务状态 | 以品牌为由去掉风险文字 |
| `submitted` 被消费为退款成功 | 冻结受影响显示/写操作，恢复分层结果适配 | 实际请求与结果记录 | 批量把 success 改成 failure |
| 外部查询服务不可用 | 保持结果待核对，转人工 | R-81、批准 v4 与发送尝试 | 给所有未知项自动重试 |
| 2.0 某浏览器焦点异常 | 回退到页面式确认或经验证的对话框 | 用户输入与当前任务 | 用隐藏焦点环掩盖问题 |

> **先记住**  
> 没有实际回滚执行时，只能称**回滚设计**，不能写「已验证可恢复」。

### 6.3 小案例：误显示「未批准」

| 步骤 | 内容 |
| --- | --- |
| **输入** | 发布后发现新组件把旧**已批准** R-81 显示成未批准 |
| **动作** | 先冻结误导写操作 → 读原记录与版本 → 区分「字段映射缺失」与「真实未批准」→ 恢复只读正确显示 |
| **可观察结果** | 外部结果保留；对无法映射的历史标「范围不完整」并人工核对；**不**重复批准或退款。复验至少含：一笔成功、一笔未知、一笔历史缺字段 |

### 6.4 练习 / 常见翻车

- [ ] 「清空数据重建」可否作为首选？——否。  
- **翻车**：回滚后重新打开一键批准且无摘要。

## 7. 第二个例子：来源卡 v1→v2（语义迁移常比换皮难）

### 7.1 本节要学会判断什么

旧 `verified=true` 可能只检查「链接存在」。迁到带 `claimSupport` / freshness 的 v2 时，不能用旧核验填满所有主张。

### 7.2 改前改后对照（先看｜visual_downgrade）

| | SourceCard v1 | SourceCard v2 适配 |
| --- | --- | --- |
| 字段 | `url, title, verified` | 来源 ID/版本/范围、freshness、每条 claimSupport |
| 错误迁法 | 用 `verified=true` 填所有主张 | —— |
| 正确迁法 | —— | 保留原链接与历史标签；新 support=`not_checked`，freshness=`unknown`；文案：「历史来源已登记，当前主张待核对」 |

## 8. 度量治理成效，不要只报采用率

**先记住**：5/5 调用点接入，只能得到「接入率」，**推不出**「退款更安全」。

同时看：合同完整率、迁移缺陷（误消费）、例外存续、重复适配成本、因迁移阻断的功能、以及由真实评价取得的任务成功与操作负担。合成盘点不能冒充生产成效。

## 9. 分层练习（短、可勾选）+ 参考要点

**基础**  
- [ ] 为什么「新弹层 + 二次确认」仍可能不够？  
  **要点**：若输入仍无版本，确认的是不稳定对象；若事件仍叫 `approved` 且被当退款成功，文案仍错；若主题盖警告、焦点丢失，用户无法正确检查。须修对象合同、事件消费与可达性；弹层只是表达之一。

**迁移**  
- [ ] CALL-03 本期无逐项版本怎么处理？  
  **要点**：冻结批量批准写入口；保留筛选、预览、跳转单项；不填全局假 version。产品记降级范围；工程补逐项版本/结果；QA 用部分成功与旧版本反例复验后再恢复。若业务必须当期批量，只能另寻**已有可靠服务路径**，不由设计虚构能力（禁假开通）。

**综合**  
- [ ] 新组件把旧已批准显示成未批准，能否清空重建？  
  **要点**：不能。冻结误导操作 → 读原记录 → 区分映射缺失与真实未批准 → 只读恢复 → 保留外部结果；缺字段标范围不完整；复验含成功/未知/历史缺字段。回滚 UI 与修数据分责。

### 基础补学（可跳过）

贡献=提出变更；评审=合同是否成立；发布=新消费者采用；迁移=旧消费者正确适配；弃用=结束旧承诺；回滚=恢复可接受状态。任一步都不能靠「组件已画完」自动完成。
