# Q8 · 你会如何评估自研 Agent 运行时、开源框架和低代码平台？

版本：interview-answers-v1 / Q8-r1。本文为完整参考解析；案例和验证方案除特别注明外均为教学构造，未在本次写作中执行。

我会先写出运行时必须兑现的合同，再用同一小任务比较自研、开源框架和低代码平台，而不是按功能列表或流行度评分。重点是发生故障后还能否解释并恢复正确状态，以及团队能否长期维护和迁出。

## 先列必须通过的合同

任务需要哪些状态：持久目标、工具动作身份、等待审批、未知效果、取消、预算、版本迁移？谁拥有数据、能否接入现有权限服务、日志能否关联任务到每次尝试？模型协议、工具和数据是否可替换？这些有的是当前必要条件，有的是未来扩展，不能因为平台宣传支持“记忆”就推断支持本业务的恢复。

| 方案 | 潜在收益 | 重点代价/核查 |
| --- | --- | --- |
| 自研显式状态机 | 稳定少量状态可贴合现有库和运维，审计直接 | 调度、并发、恢复、迁移均由自己实现和维护 |
| 开源框架 | 复用图调度、暂停、状态合并和观察接线 | 固定版本语义、持久后端、序列化兼容、升级及错误定位 |
| 低代码 | 集成和操作界面可能较快 | 能否表达自定义权限/补偿、导出完整状态、恢复在途任务、迁出日志与数据 |

## 做一次能暴露边界的验证

统一小任务：“读报告、形成草稿、等准确批准、创建唯一工单”。每种方案依次执行正常路径、批准后改正文、写成功但回执丢失、两个工作者同时恢复、旧版本任务在升级后继续。观察是否真正拒绝旧批准、是否核对同一动作、能否保留未决事实；再实际导出一项暂停任务，在另一实例恢复。只展示画布连线或一次绿灯不够。

记录实现与排错时间、需要绕过框架的部分、日志完整性、测试证据及迁出步骤。若平台无法提供动作稳定身份和外部效果核对，可缩成只读草稿工具，也可不选；不应靠提示模型“不要重复”补齐运行时合同。若团队已有成熟任务库且状态很少，自研可能更经济；动态分支和复用子图很多时框架可能省工，但须对选定版本实测。没有完成上述比较，就只能给候选和风险，不能宣布某平台最可靠。
