# 产品经理 D0 诊断与学习者执行合同 v0.1

- `contract_id`: `PROD-D0-001`
- `contract_version`: `product-manager-d0-v01`
- `role_id`: `product-manager`
- `owner`: 学习者本人（匿名 `learner_id` 必填）
- `independent_reviewer`: 测试工程师（执行与证据完整性）；课程架构师/内容审校员（机制与来源）；项目经理（交接完整性）
- `status`: `planned`
- `assessment_status`: `not_assessed`
- `learner_owned_evidence_required`: `true`

本合同只定义产品经理 D0 的起点诊断，不授予 L0、L1 或 L2。代理、作者、静态计划、产品原型和既有 QA 不能替学习者提交答案或证明学习者能力。

## 1. 责任边界

产品经理负责把用户问题转成可交付、可验证的产品范围，定义用户场景、价值假设、版本边界、验收条件、失败/歧义状态及跨岗交接。不得编写界面、教材、模型服务、数据库、检索实现或独立 QA，不得把自查、原型、模拟用户、一次成功或营销材料写成真实用户、专家、生产或行业先进证据。

学习者必须在每题中标出：自己负责的判断、明确不负责的实现或验收、需要哪一岗位接手、缺证时的停止/升级条件。任何需要外部写入、付费调用、真实用户联系、生产数据库或上传发布的动作一律停止，除非另有授权合同；本 D0 默认只使用隔离合成夹具。

## 2. 五项诊断

### D0-01 边界复述题

给定场景：学习工作台需要新增一个“按自然语言推荐教材小节”的功能。请学习者提交一页岗位合同，至少说明目标用户、产品经理负责的范围、非目标、设计/检索/工程/QA 的交接点、未验证假设、拒绝越权请求和升级条件。

夹具：`fixtures.product-recommendation-v01.json`（合成用户场景、不得访问正式数据库），固定 hash 由执行包记录。

通过观察：能区分需求与实现、产品验收与独立测试、原型与真实用户证据；对缺失用户证据或授权停止，不替工程岗位作答。

### D0-02 机制与专业判断题

解释“价值假设 → 指标/护栏 → 实验 → 结论”的因果链，并说明为什么功能存在、点击量或一次 Demo 不能证明用户价值。要求给出一个正常结果、一个失败结果和一个未知结果；绑定 `product-creation-curriculum.md`、`product-creation-standard.md` 的版本/路径，并区分用户原话、观察事实、作者假设与推断。

通过观察：解释可复核、能指出适用边界和未知；不得把课程或营销来源当作当前产品实测。

### D0-03 熟悉脚手架任务：版本化产品合同

在隔离夹具中，为“教材推荐入口”写 `W-PROD-D0-001` 产品合同，字段必须包含：目标用户与问题、场景、产品目标、非目标、版本范围、依赖、输入输出、正常/边界/失败预期、验收条件、来源与版本、未验证项、跨岗交接和回滚/停止线。不得写代码或教材正文。

执行收据必须包含实际命令或操作步骤、输入快照 hash、输出 hash、环境、开始/结束时间、stderr、退出码和首次失败（如有）。

### D0-04 失败识别题

给出一个故意缺陷包：产品合同声称“推荐命中即证明学习有效”，缺少版本、来源和用户验证；另有一条“前端已通过 QA”但没有独立报告。学习者需定位预期/实际差异、缺陷等级、受影响门槛、立即停止动作、责任岗位、返修和复验顺序。

预期识别：营销/功能数量不能替代价值证据；产品经理不能代 QA 宣布通过；缺版本或来源时结论应为 `unknown`/`insufficient_evidence`。

### D0-05 迁移预告题

未知变体将把用户目标从“推荐教材章节”改为“为新岗位选择补学路径”，并加入一个关键约束（来源版本冲突或预算上限）。学习者只提交计划，不执行：需要先确认什么、如何冻结范围、怎样定义指标与护栏、何时停止/升级、需要哪些跨岗接收和证据。不能引用本题未公开答案。

通过观察：能迁移产品判断原则，明确输入、假设、证据分母、未知与停止条件。

## 3. 隔离夹具与执行限制

所有夹具使用虚构用户、教材、版本和数据；可使用本地只读文件与离线脚本。不得访问真实用户记录、正式数据库、外部服务、付费模型、真实用户或生产系统。夹具应包含正常、边界、失败三类输入，并至少注入一次缺失来源/版本冲突、一次不明用户价值和一次跨岗责任混淆。夹具版本和 SHA 必须在合同、执行收据和 EvidenceCard 中一致；夹具变更须新版本，不覆盖首失败。

## 4. 学习者原始提交和 EvidenceCard

每项 D0 原始证据必须由学习者本人提交，至少包含：

- `diagnostic_id`, `exercise_id`, `exercise_version`, `role_id`, 匿名 `learner_id`
- 原始回答/产品合同/失败判断/迁移计划，未经代理改写
- `fixture_id`, `fixture_version`, `fixture_sha256`, 输入快照和输出路径/hash
- 实际环境、命令或操作、开始/结束时间、stdout/stderr、退出码
- 事实、来源、假设、推断、未知与停止/升级决定
- 首次失败、返修版本、原例回归、受影响回归和留出变体（尚无则标 `pending`）
- 学习者声明：本人执行、未访问禁止数据、未执行外部动作；签名/时间戳
- `learner_execution=true` 才能作为学习者执行证据；QA 派生文件必须标 `derived_by=QA`

EvidenceCard 至少记录：`card_id`, `claim`, `evidence_level`, `source_id`, `source_version`, `source_location`, `artifact_path`, `artifact_sha256`, `environment`, `observed_result`, `expected_result`, `failure_first_seen`, `reviewer`, `review_status`, `unknowns`, `next_action`。没有原始收据、来源定位或独立复核时为 `insufficient_evidence`。

## 5. 独立复核、交接和接收条件

测试工程师独立复核输入/夹具 hash、原始收据、缺陷识别、停止动作、输出可重现性，并使用非作者冻结的一个短变体检查迁移预告是否没有代答。内容审校员核产品机制、来源版本、事实/假设/推断分类；产品岗位复核由另一名产品责任人或项目经理按合同检查范围与验收字段，但不能由学习者自审晋级。接收岗位从交接包重建最小命令/步骤，签署 `accepted` 或填写有据 `rejected`，包括版本、依赖、已验证/未验证、风险和复验命令。

交接包必须含：输入/输出路径、版本与 hash、验收状态、未关闭缺口、责任人、接收方、停止线、复验顺序（原例 → 首失败/停止 → 修复 → 原例回归 → 受影响回归 → 留出）和签收时间。没有接收签名不能关闭 D0-03。

## 6. 停止线与 D0 结论

首个无法确认岗位范围、用户目标、来源版本、夹具 hash、权限/数据边界、原始收据或学习者归属时，停止受影响路径，标记 `unknown`、`blocked` 或 `forbidden`，不得猜测或把 QA 派生文件改标为本人证据。任何越权访问、真实外部动作、证据覆盖首失败、伪造用户反馈或把自查写成独立通过，均为 P0 阻断。

D0 只能输出 `not_assessed`、`insufficient_evidence`、`fail` 或有限的观察记录；五项原始回答、隔离执行收据、独立 QA、内容/产品复核和接收签收齐全后，项目经理才可评估 L0 起点。D0 通过不等于 L1；L1 还需两个不同沙箱夹具、返修回归、未知迁移和独立交接证据。
