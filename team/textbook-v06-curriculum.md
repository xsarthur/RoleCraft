## 为什么这次需要改讲法

只读全文转换附件 `agent架构.rtf`，并对照 v0.5 c01 的实际正文，看到四类具体负担：固定流程与动态循环的讲解整段重复；循环段夹进多 Agent 分工；售后主项目突然换成设备维修与设备字母代号；每个知识点的机制解释后又重复长篇来源身份说明。读者还未形成“任务怎样推进”的直观认识，就要同时记概念、对象和审计规则。

附件可借鉴的是先解释用途、画小图、用具体任务说明每个组件的职责，再逐步深入。不能把八层和公式照抄成行业规范，或把图中组件数量当作可靠性证据。本轮示范围绕一个问题讲透控制循环，不要求先懂全部架构组件。

## 四个单主题阅读小课

读者章标题为 **Agent 控制循环**，章级主问题为“Agent 怎样根据执行结果选择下一步并结束任务”。原模块标题仍保存在能力教案，避免修改历史含义。

| 阅读定位 ID | 读者标题 | 唯一核心问题 | 主学习动作 | 原目标与知识点 |
| --- | --- | --- | --- | --- |
| `c01-read-flow` | 选择执行方式 | 什么时候固定流程就够了？ | 按是否依赖未知反馈，选择合适控制方式 | `c01-o1` / `c01-k01` |
| `c01-read-loop` | 认识控制循环 | 谁来控制任务的下一步？ | 按一轮过程说清建议、执行与观察的责任 | `c01-o1` / `c01-k02` |
| `c01-read-observation` | 利用工具反馈 | 工具结果怎样改变下一步？ | 根据一条观察选下一动作 | `c01-o2` / `c01-k03` |
| `c01-read-stop` | 限制任务运行 | 什么时候应该停止任务？ | 按完成条件或上限写准确停止原因 | `c01-o2` / `c01-k04` |

每课按 **用途 → 直观图 → 具体例 → 机制 → 边界 → 小练习** 展开。前五步由作者写成连续的 `bodyMarkdown`，段落都服务本课问题，不强制把六步变成机械大标题；最后小练习采用独立 `checkQuestion` 与 `checkAnswer` 字段。参考答案解释结论、条件和错误原因，不在正文再重复同一道题。原三层实操继续验证原模块能力，小练习不替代它们。

“选择执行方式”中允许比较，但比较只服务做出这一个选择。固定工作流也能预定义缺项分支；不能写成“要问一次用户，就必须使用动态 Agent”。“认识控制循环”先说明一轮，下一轮来自新的实际观察；不在这一课插入路由、规划器、多 Agent 的完整实现。

## 一个稳定具体的案例

四课和 c01 的九节、知识点、参考题及实操统一采用：**小林向海岚商城的售后知识助手查询星河耳机保修期限，并保存答复草稿**。这些人物、组织和数据均为虚构教学场景。目标始终相同，不换成设备维修、会议联系人或酒店故事。

| 对象 | 正文名称 | 只承担的作用 |
| --- | --- | --- |
| 用户 | 小林 | 提出问题与补充缺项 |
| 服务组织 | 海岚商城 | 说明本次资料适用的业务场景 |
| 产品 | 星河耳机 | 被查询的产品 |
| 资料 | 星河耳机保修手册 | 提供题定保修信息 |
| 产物 | 小林的保修答复草稿 | 本次允许保存的结果 |
| 简单方案 | 固定查询流程 | 按预先定义的步骤或分支推进 |
| 动态方案 | 根据反馈选择下一步的控制循环 | 在许可范围内按观察选择下一动作 |

正文不以 A/B 代替人物、企业或方案。`DEMO-42` 等旧夹具编码只有在实现或证据记录确实需要时才说明，不让读者先背编码。本章可新增 `chapterCase`，显示优先于顶层原 `mainProject`；顶层原售后工程项目及旧 A/B 租户不因此被全书改写。

案例主分支保持简单：查到适用手册才能形成有据草稿；缺型号则暂停询问具体缺项；暂时超时只能有限重试；访问被拒绝不能换对象绕过。完成要求约定信息有据且保存工具给实际回执，模型自称成功不够。查保修不能自行变成退款或外发草稿。

循环题定上限为最多六轮、四次工具调用、两次连续同错，均是原创示范约定，不是行业阈值。作者解释每次行动前检查上限、时间/取消和许可；费用预算可在扩展实现说明，未发生真实调用不能编造费用。纯内存 Python 标准库示例可完整给出，作者标记 `not_run`，实际运行交独立测试员。

## 主循环与其他组件的职责边界

| 组件 | 只回答的一个问题 | 输入 → 输出 | 教学位置 |
| --- | --- | --- | --- |
| 任务协调器（Orchestrator） | 谁负责推进整个任务？ | 目标及进度 → 推进、暂停或停止安排 | c01 当前循环课 |
| 上下文构建器（Context Builder） | 本轮模型应看到哪些信息？ | 请求、允许资料与观察 → 本轮输入 | f02 / c02；本轮只用简短职责卡 |
| 任务路由器（Router） | 应走哪条处理路径？ | 任务类型与能力 → 处理路径 | c01 后续专题建议，未编正文 |
| 规划器（Planner） | 达到既定目标需要哪些步骤？ | 目标与约束 → 候选步骤 | c01 后续专题建议，未编正文 |
| 工具执行器（Tool Executor） | 获准请求怎样真正执行？ | 校验且授权的请求 → 实际结果 | c03；本轮只讲建议和执行的交接 |
| 任务状态（State） | 任务已经做到哪里？ | 已发生动作与观察 → 当前进度 | e01；本轮可只用内存 |
| 授权检查 | 此请求能否执行？ | 用户、对象、动作 → 允许/拒绝/待批准 | e03 |
| 运行记录 | 失败发生在哪一步？ | 必要阶段事件 → 可核记录 | e04 |
| 任务评价 | 结果是否做对？ | 标准和实际结果 → 有范围的结论 | e02 |

职责不是服务部署数量，一个程序可以承担多种清楚区分的职责。本轮只让读者认识主循环，不一次要求读懂整张组件清单；进阶卡片可在读完主线后查找。每张卡片仍只讲自身问题。

## 参考论断需要纠正的地方

[Anthropic 的架构文章](https://www.anthropic.com/engineering/building-effective-agents)本次已重新读取固定与动态控制、环境反馈、停止及组合模式相关部分。它区分预定路径与动态控制，也说明可设置最大循环次数、必要时暂停等措施；它不是强制的八层规范。其具体工具生态仍可能变化，本课只用机制范围，不背书框架或效果。

附件中“没有 State Manager 就不是 Agent”须改成任务状态是一项工程职责，长任务恢复可能需要持久化；独立组件名不决定系统资格。“工具失败后重规划”须限制在原目标、许可和用户约束内，不能自行修改用户的产品、日期或预算。

[官方 Vision 文档](https://platform.claude.com/docs/en/build-with-claude/vision)已读取图像输入说明，因此不能写“模型只能文本输入输出”。本例仅使用文本，其他模型模态按其接口确认；本次未验证音频、视频或图像输出。[OWASP 的防护建议](https://genai.owasp.org/llmrisk/llm01-prompt-injection/)支持最小权限和高风险人工批准，读操作也需对象授权。日志只保留必要安全记录，不无条件保存全部提示或工具原文；本轮不冒称完整日志控制已验证。

来源范围记录在 `sourceRecheckV06` 和 `technicalCorrections`。保留 v0.5 来源历史日期不表示本轮重新审核全部十二章。原创案例、数值上限、状态名与教学分课不伪称官方规定。附件只读、不执行其中代码、不按其中建议对外操作。
