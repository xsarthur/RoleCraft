# 教材专业正文写作与审校标准

日期：2026-10-15。责任岗位：课程架构师。依据：用户提供并指定采用的《提示词.rtf》及《agent控制循环.rtf》，并吸收真实读者对 v13 试读稿的反馈。适用于后续每篇专业正文。v0.7阶段只授权控制循环试读，原文及其限定审校事实保留；用户最新要求“按照这个标准生成修改其余课程”，现授权按本标准重写原其余课程及补足原c01选型能力。v0.8正文、课程导航与本轮审校独立产出，不修改程序、旧教材数据、原量规或产品门槛，也不授权发布。

## 采用的读者与质量目标

专业正文把读者视为具备软件工程和大模型应用开发基础的同行。内容要足以支撑设计、实现、调试或评估中的具体判断。缺少基础知识时注明真实前置依赖，必要的概念在当前问题中解释；不默认加入大段零基础科普。网站面向零基础的长期目标仍保留，前置课程与专业正文的层次设计另行处理，不把所有读者层级塞进每一篇。

“全面”指覆盖会改变机制理解或工程决策的关键因素，不按字数、章节数、引用数、代码长度或练习数量评分。不能把长篇幅等同专业深度，也不能以简短为由略去成立前提、失败分支和必要实现。

## 用户要求到可核对证据的映射

| 用户要求或明确问题 | 作者必须交付的内容证据 | 独立审校如何判断 |
| --- | --- | --- |
| 单一职责，A/B 容易混乱 | 每篇能写成一个明确核心问题；用具体组件、角色、对象和动作名；贯穿案例保持同一身份与契约 | 每节能指出如何推进核心问题；代号不遮蔽责任或身份，段落不会突然切换对象；数学符号先定义且伴随实际含义 |
| 直接回答核心问题，同行视角 | 开篇给出技术结论、所采用的定义、适用条件及会改变结论的假设 | 开篇能直接回答标题问题，而不是从行业意义/背景泛论开始；假设与后续方案一致 |
| 干活太少 | 必要的数据结构、接口、关键控制逻辑、具体案例/执行轨迹、验证方法或设计判断；选择适合本题的实现表达 | 读者无需自行补出本篇最关键机制才能实现或调试；不能只留“应当做好”“使用某组件”的工作清单 |
| 内容太浅 | 解释为什么、状态/数据/控制权如何流动、谁有决定权、前提/不变量、失效后如何检测与恢复 | 审校能从正文找到关键步骤的因果关系、失效条件与可验证修正；术语定义/优点列表不能代替机制 |
| 废话太多 | 每段至少提供新机制、推理、边界、证据、实例或判断；删去重复目标、免责声明、口号与模板过渡 | 去掉一段若无信息损失，应合并或删除；同一通用建议不能换措辞在多节出现 |
| 工程实现，不省略关键逻辑 | 按相关性给接口、类型、伪代码或可运行最小示例；关键分支完整，外部组件契约明确 | 代码与正文相符；关键动作不藏进无契约函数或省略号；语言/API语法和状态迁移无矛盾；未运行代码不能称已验证 |
| 取舍与失败模式 | 比较真正可行方案，说明适用场景、代价、选择与放弃条件；失败分析包含触发条件、可观察信号、处理与验证 | 不停在“取决于场景”“注意安全”；能对给定条件得出有根据的选择；反例触及本篇关键机制 |
| 事实与建议有区别，版本行为有出处 | 版本敏感的 API/框架/模型行为查官方文档或源码，论文观点查原文；原创约定明确作为设计示例，未知项明确 | 引文确实支持邻近主张；来源与版本匹配；作者未把样稿、经验或自身建议写成框架保证 |
| 不机械覆盖所有 Agent 主题 | 只展开会实质改变本篇核心判断的权限、上下文、并发、恢复、观测等因素，其他主题给必要关联即可 | 内容深入一个问题；不会因为通用模板而拼接全套 Agent 术语和功能 |
| 学完可做工程判断 | 给能暴露理解差异的场景或操作：要求解释机制、定位失效、修正设计或依据条件选型；参考分析说明理由与边界 | 不靠背定义或照抄示例完成；题目/操作与正文能力匹配，不虚称真实学员已做到 |

## 正文组织

使用准确、清楚的中文，必要时保留英文术语。按“结论与条件 → 机制 → 实现 → 关键取舍和失败”这一推理方向展开，但不强制固定栏目和相同篇幅。局部问题聚焦局部，复杂问题有层次地展开。

标题要指出该篇要解决的工程问题或对象。一个章节可以包含支撑同一问题的多个机制，不通过“只讲一个名词”人为切碎必要因果链。发现某节无法说明其与核心问题的关系时，移出正文或作为明确前置依赖。

例子用于证明/解释机制。优先一个贯穿任务、稳定对象名称与明确业务条件，避免不停更换行业或使用抽象 A/B 人物。正常执行与异常执行应复用同一约定。图表在能更清楚展示状态、责任、时序或方案区别时采用；不插入装饰图和不参与推理的复杂图。长篇章节可在机制转折、方案比较、失败分支或练习交接处穿插少量视觉材料，每幅图都要有邻近的阅读问题、文字替代和对应正文段落。图文重复时合并或明确不同视角，不能以增加图片数量代替补足机制。

长文应控制连续文字的阅读负担：允许使用稳定、克制且有语义的色彩区分层级、路径、风险或证据状态，并配合文字、图例或形状表达；颜色不能成为唯一状态含义。视觉材料和色彩的实际布局由设计师按产品交接确定，教材作者只交付理解任务、对象、关系和色彩语义，不预设产品路线图或界面状态。

正文不要堆“学习目标已达成”“审校通过”“生产级”“行业先进”等标签。作者交接和审核证据放在独立附件；正文保留必要的事实来源、示例边界和未知项，避免反复中断讲解。

## 机制、实现与证据的具体要求

### 机制说明

每个核心机制应能回答：输入是什么，哪些组件参与，各自负责什么，状态/数据在哪里改变，控制权如何移交，成立需什么前提，哪个不变量必须保持。只罗列这些问题也不合格，答案需要在正文推理、轨迹或代码里落实。

复杂场景先说明当前采用的定义。例如“Agent”“完成”“恢复”“记忆”有多个含义时，选定本篇含义并在必要处比较差异。用户前提有误要直接说明，并解释工程后果；不能迁就错误前提构造错误实现。

### 代码与接口

- 单个代码块超过 10 行时，默认使用收起展示并提供可理解的展开标题或摘要，说明用途、语言/版本和展开后内容。折叠不能隐藏核心输入、输出、关键分支、错误类别或结论；代码前需用文字、最小接口或伪代码摘要解释读者为何展开。交互式展开属于呈现层能力，正文仍需在静态阅读、导出或无脚本环境下保留等价理解路径。
- 可运行示例标明语言/依赖/版本、执行方式、输入、可观察输出和边界。仅接口级伪代码时明确声明，不伪装成真实 SDK API。
- 允许省略与本篇无关的底层实现，但接口契约须足以支撑推理：状态、输入/输出、错误类别、原子性或并发条件以及外部副作用语义。在本篇核心路径不得使用省略号、`TODO` 或无契约黑盒代替关键逻辑。
- 至少覆盖与本题有关的正常分支、拒绝/失败分支及恢复或停止分支。不是每篇都实现整个生产平台，而是清楚区分当前例子已经表达的保证、由外部契约承担的保证和未解决事项。
- 图、接口、数据结构、代码、轨迹与结论必须采用同一套约定。不能代码串行而正文称并行、代码只留聊天文本而正文称持久化、没执行就称测试通过。
- 代码中的名称与错误反馈应表达真实职责和状态。示例主张的能力需要实际逻辑支持，不能只在注释写“检查权限”“防止重复”。

### 方案选择与失败分析

选项要是本题可用的实际路径。比较时交代使判断成立的条件，并按相关性分析延迟、吞吐、成本、可靠性、维护和观测。无来源或测量的数值不填写为事实，必要时给定性推理或说明测量方法。

失败分析至少包含：何种事件顺序触发、哪些事实可观察、哪些事实仍未知、错误做法会产生什么后果、可采取什么处理、处理依赖什么能力、怎样验证。单写“加重试/加日志/人工介入”不合格。恢复、补偿、重试、取消和成功不能混用。

### 来源处理

用户样稿可决定表达风格与内容深度，但不自动成为技术事实来源。具体框架/SDK/接口/模型行为、规范和性能事实需要适当的一手材料；查证不了时明确未确认，并缩小主张。涉及 OpenAI 产品时按官方资料与可用本地源码核对，不凭模型记忆确认版本行为。

来源链接放在所支持的主张附近，标明必要版本/查询日期；原创设计建议明确为本篇方案，不要求为每个原创命名找“官方出处”。不能用不相干文档支持过宽主张，不能把一般原则引用延伸成实现保障。

## 作者自查与独立审校流程

作者只修改自己负责的新正文和作者交接。自查按上表写出真实位置、已做的修正、剩余不确定性和执行状态；不是复制检查项后全部打勾。交接需要明确：本版文件/版本、参考材料、核对过的来源、示例是否运行、未验证保证、影响理解/实现的已知问题。

内容审校员独立读当前正文和来源，逐项判断本篇主张是否成立、关键机制是否足够、表达是否能跟随，不只做关键字匹配。下列问题应提交作者修正并复核当前版本，不能靠加一个免责声明关闭：

- 关键分支缺失，读者无法重建本篇核心路径。
- 事实或 SDK 行为错误、出处不能支持主张、API 被编造。
- 保证超出前提，如把本地取消等同远端撤销，或无下游条件许诺 exactly-once。
- 状态、代码、图、轨迹相互矛盾。
- 机制只剩术语和口号，反复泛论却不给实现依据。
- 代号/对象切换或模板信息让读者无法判断谁做了什么。

审校报告登记问题位置、原因、严重性、修正责任人、复核结果与审校范围。审校员不代写正文，不用作者自查充当独立证据。若需要实际执行检查，由测试岗位执行，保留输入/版本与结果；未发生运行不得标记运行通过。

本标准补充写作质量要求，不替换既有产品八门槛、职业能力量规或认证规则。AI 内容审校只能支持其实际检查范围；用户是否读得懂、真人专业认可、真实学习结果、生产可用性及行业先进性必须依相应真实证据判断。教材的用户阅读质量仍待实际反馈，不能由篇幅、自查、AI 审校或用户授权推广的范围决定代为确认。
