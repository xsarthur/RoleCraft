## 原理与方案取舍

### f01-k01 · 输入类型与非法输入

工单输入用字典表示，例如{"title":"打印机卡纸","priority":"normal"}。字符串长度不是内容是否有效的充分条件，空格也占长度。校验函数先判断输入类型，再取字段、规范化空白、检查允许值；顺序让错误定位清楚。不要用一个巨大try包住全部逻辑后返回成功。情景题：title为空格且priority为urgent，先应得到什么？本章契约选择invalid_title，修正标题后才能发现invalid_priority。这是原创错误优先级，不是Python规定。迁移到金额字段时，要额外区分数字、布尔值与单位。

JSON是交换数据的文本格式，解析后才得到程序对象。字段缺失、值为null、空字符串和空列表代表不同状态，应在契约中分别定义。能被解析只证明语法可接受，不能证明字段存在、数量为正或对象属于用户。情景题：{"title":null}解析成功，应直接交给模型补全吗？不应；缺项先返回可操作错误或请求补充。JSON中的true/null与Python中的True/None写法不同，用json.loads解析而不是复制后eval。

解析与条件：按编号字符串契约拒绝列表，返回invalid_order_id，不把列表转成任意字符串再查询。 结合本点的输入、观察与适用条件逐项核对；机制讲解中已给失败原因和反例，不能只背结论。

### f01-k02 · HTTP请求与失败分类

HTTP请求由方法、地址、头部和可选消息体组成；响应有状态、头部和消息体。POST常用来提交，GET常用来读取，但业务副作用和幂等性仍需看接口契约。连接失败时可能没有HTTP响应；收到4xx/5xx时也要保留安全的错误证据。超时表示调用方未及时知道结果，不等于对方没有执行。情景题：创建工单超时后再点一次，会不会重复？先保留“结果未知”，后续c03/e01用幂等标识和核对解决。

## 示例与环境

示例身份：可运行示例（未执行）。将代码保存为f01_demo.py，使用Python 3.10+标准库运行python3 f01_demo.py。本书作者未执行该示例；打印内容是预期，并非本次测试记录。正常和边界用断言比较完整对象；失败用异常类型和代码比较，不能只看屏幕有没有红字。再把title改为数字、加入未知priority、删去title，逐项写预期后复验。若导入失败先看解释器和文件名；若断言失败先打印安全的输入、实际值和类型，不直接放宽规则。

```python
import json

def normalize_ticket(raw):
    if not isinstance(raw, dict):
        raise ValueError("invalid_object")
    title = raw.get("title")
    if not isinstance(title, str) or not title.strip():
        raise ValueError("invalid_title")
    priority = raw.get("priority", "normal")
    if priority not in {"low", "normal", "high"}:
        raise ValueError("invalid_priority")
    return {"title": title.strip(), "priority": priority}

assert normalize_ticket({"title": "  A  "}) == {"title": "A", "priority": "normal"}
obj = normalize_ticket({"title": "打印机卡纸"})
assert json.loads(json.dumps(obj, ensure_ascii=False)) == obj
try:
    normalize_ticket({"title": "   "})
except ValueError as exc:
    assert str(exc) == "invalid_title"
else:
    raise AssertionError("blank title must fail")
print("expected: local contract checks passed")
```
