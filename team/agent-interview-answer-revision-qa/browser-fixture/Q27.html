Q27 · MCP 解决哪一层集成问题？它与模型的 Tool Calling 有什么关系？

版本：interview-answers-v1 / Q27-r1。本文为完整参考解析；案例和验证方案除特别注明外均为教学构造，未在本次写作中执行。

MCP解决宿主应用与外部能力服务之间的发现和消息交互；Tool Calling解决模型如何提出结构化工具建议。典型路径是模型提议→宿主校验→MCP客户端调用服务端→宿主关联结果回传模型。模型不因此直接持有服务令牌，MCP也不替应用决定业务目标或自动批准动作。

一次具体交互

本题固定使用MCP 2025-11-25 教学版本，不声称它是所有实现当前支持的版本。宿主建立client-server连接，先用initialize协商协议和能力；客户端确认后发送initialized通知。版本不兼容则停止连接，不继续猜格式。成功后用tools/list发现能力，处理所需分页，并把允许工具适配到模型的Tool Calling格式。

教学例中模型选择 read_report(report_id=R71)，宿主检查当前主体、R71范围和参数，再发tools/call；请求ID关联协议响应，业务结果另带报告版本与来源。结果返回后宿主核验内容、保存观察，再与原模型调用ID关联。若R71不在允许范围，宿主可在调用前拒绝；服务端也应按具体资源授权，不能只相信客户端。

协议成功和业务成功分开

JSON-RPC成功表示收到合法协议结果；工具结果可能是业务错误，正文也可能不是所需版本。协议错误如方法不存在，应修适配或能力配置；工具内的无报告、权限拒绝、暂时失败按业务类别处理。写超时仍保留未知效果，不因MCP请求ID改变就成为新业务意图。

MCP并不保证模型选对工具、报告是真的、数据可交给当前模型、幂等窗口永久有效或外部任务只执行一次。这些仍由能力描述、权限、内容投影、动作账本与下游合同解决。只有几个本地函数时，直接适配也可能足够；统一接入的收益要与协议、认证和运维成本比较。

验证最小轨迹应覆盖兼容/不兼容初始化、未协商能力、工具分页、合法调用、越权对象、工具错误和超时。检查拒绝层、消息关联及业务效果，而不是只看到连接成功就宣称集成完成。真实客户端/服务端互操作仍需按具体版本运行验证。

3 MCP 位于模型外部的连接层

宿主 host 是运行应用、管理会话和策略的主体；client 维护与 server 的协议连接；server 暴露工具、资源与提示。典型路径是宿主把工具描述适配给模型，模型返回 Tool Calling 提议，宿主校验后通过 MCP client 发送请求，server 调用具体业务能力并回传结果。模型不直接获得 OAuth 令牌或任意网络连接。
