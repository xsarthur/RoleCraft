Q21 · Function Calling 从模型输出到函数真正执行，中间经过哪些步骤？

版本：interview-answers-v1 / Q21-r1。本文为完整参考解析；案例和验证方案除特别注明外均为教学构造，未在本次写作中执行。

Function Calling 是模型输出结构化工具提议的方式，真正调用函数的是应用宿主。完整链路应包含“提供契约→取得完整提议→逐层校验→持久化动作→受控执行→关联结果→继续或结束”；模型输出函数名不等于执行，更不等于授权。

从一次提议走到结果

宿主先只提供当前任务可用的工具名称、用途、参数Schema与结果含义，并给模型必要任务证据。收到输出后，适配器按具体协议等到完整结束：流式出现半个JSON或一个看似完整对象，只能预览；整轮可能还会被截断或追加冲突动作。

随后依次检查：调用ID与分支是否合法；工具/版本是否存在；参数字段、类型和范围；业务前置条件及引用；可信主体对目标资源的当前权限；准确内容批准和预算。若模型同时给最终完成与待执行工具，应按明确合同拒绝混合决定，不能随意选一半。

通过后，运行时为新逻辑意图事务性保存动作ID、不可变参数、指纹、下游幂等键及调用关联。每次发送前再检查会变化的权限、批准、取消和额度，保存尝试后由执行器调用。结果分为成功、确认无效果、不可重试失败和未知，按尝试归约到动作账本，再用本轮对应调用ID回传工具观察。模型据此继续或给最终候选；最终仍由业务验收决定。

一个完整的教学例

模型建议 read_report({report_id:"R71"})。宿主发现R71在允许范围，取回报告及修订并核对后回传；模型再建议 create_issue。若缺批准，先保存提议并返回等待，而不是调用后补批。批准后发送，若远端成功但回执丢失，记录未知并按原动作核对，不能把新模型调用ID作为新建单键。

参数错误应返回具体可修反馈；无权限则拒绝相应动作；缺资料则等待；流截断不执行；写超时走核对。批量提议预检通过也不代表远端原子成功，实际结果须逐动作保留。

验证要收集原模型响应、调用绑定、准入记录、发送次数及外部效果：合法例可走通，半流无发送，非法参数无发送，重复提议只关联已有动作，未知结果不变成“失败后重新创建”。具体SDK格式须按所选服务适配；本题流程是应用控制合同，不是某个通用API事件名。
