Q7 · 单 Agent 多工具与多 Agent 协作，在架构上有什么区别？

版本：interview-answers-v1 / Q7-r1。本文为完整参考解析；案例和验证方案除特别注明外均为教学构造，未在本次写作中执行。

单 Agent 多工具是一个主要决策上下文调用多种能力；多 Agent 是多个各自有上下文、状态和决策循环的执行者，通过任务合同交接。十个工具不是十个 Agent，十次模型调用也未必形成十个独立角色。两种架构都需要一个明确的整体结果责任者。

控制和状态放在哪里

单 Agent 中，宿主保存一份权威任务状态，模型从同一上下文选择搜索、读文件或拟建单。工具通常返回结构化结果，不自行持续追求子目标。优点是上下文和完成条件集中；缺点是任务广、工具多时选择负担增加。

多 Agent 中，协调者拆成可独立验收的子目标，每个子代理有自己的输入、允许资源、预算和输出。交接至少带子任务ID、目标版本、证据清单/哈希、允许范围、主张及逐项引用、缺项、消耗与状态。协调者核版本和权限，再整合结果；子任务“结束”不等于整体目标通过。

关切单 Agent 多工具多 Agent
状态集中保存观察和动作账本子状态加明确交接，整体权威状态仍有所有者
并发可并发独立工具读，不必另建角色可并行独立调查，但增加通信和合并成本
冲突同一决策过程中的证据冲突还须处理不同版本、遗漏、子任务失败和意见冲突
副作用宿主准入和执行应明确唯一写者，防止子代理各写一份

什么时候分工有意义

教学例：一位调查代码控制路径，一位调查测试夹具；两者使用同一 repo@8e12，独立交出引用，由协调者核两条证据是否真正支持同一原因。若第二位用 repo@9a01，即使结论一致，也先拒绝合并并重取同版本资料。若一位超时，结论是子证据缺失，不是“没有发现问题”。两个模型共享错误资料后达成一致，也没有创造新的事实。

比较时固定总预算与任务，分别测漏证、冲突漏报、错误完成、总费用和端到端等待。并行可能缩短墙钟时间，但所有子调用都计入总费用。若子任务互相等待、上下文反复转述，或瓶颈只是一个不可并行的写请求，分工反而没有价值。检验还要注入重复交接、迟到结果和子任务取消，确保不会覆盖当前版本或重复执行。
