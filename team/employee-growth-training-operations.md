# 数字员工培训实施与运营计划

日期：2026-10-15（Asia/Shanghai）  
版本：`employee-growth-training-operations-0.1`  
责任岗位：产品经理（范围、任务合同、验收条件、指标和推广门槛）  
状态：`plan_not_executed`

本文件把现有的员工成长产品流程、课程规格、两周 MVP 模板和状态交叉映射组织成可执行的培训实施计划。它是产品运营合同，不是课程正文、岗位专业标准、员工能力认证或试点效果报告。真实员工能力、用户结果、真人专家结果、生产结果和行业先进性在证据取得前均保持 `not_assessed`。

## 2. 实施目标与结果分层

每个训练任务同时维护两条互不覆盖的轨道：

- **Delivery**：当前合同版本的交付物是否满足验收条件。
- **Growth**：是否有独立证据显示某项能力在变体或未知情境中出现可观察进步。

课程阅读、练习数量、学习时长、提示词数量、文档字数、模型评分或一次正常成功不能单独升级 Growth。流程关账也不能推出职业胜任、用户满意、专家认可、行业先进或生产稳定。

首轮产品目标是验证“培训流程能否让一个岗位完成三项真实形状任务并留下可追溯证据”，而不是同时培养十五岗或宣布员工达标。目标顺序为：

1. 形成可填写、可复核、可复验的合同和证据链。
2. 通过 `T1`、`T2`、`T3` 暴露边界、迁移和失败恢复缺口。
3. 依据失败和复验结果修正合同、夹具、先修或交接方式。
4. 只有达到推广门槛后，才把同一流程复制到下一岗位或跨岗切片。

## 3. 分组与责任边界

十五个岗位按培训依赖分三波；波次是执行顺序，不改变各岗位唯一责任领域，也不要求所有岗位同时常驻。

首轮两周 MVP 的锚点岗位是 **Agent 开发者**。这是一个产品样例场景，不新增或混合岗位：每项任务仍只绑定一个唯一责任岗位（例如 AI 生成工程师、软件工程师或内容检索工程师），跨岗协作者只按合同提供输入，不能代替责任人或独立复核人。只有这个锚点周期完成独立复核，才评估向其他岗位复制流程。

| 波次 | 岗位 | 首要训练产物 | 独立复核与接收 | 明确边界 |
| --- | --- | --- | --- | --- |
| A 核心产品与系统 | 项目经理、产品经理、设计师、软件工程师、后端数据工程师、AI 生成工程师、内容检索工程师、测试工程师 | 产品/工程切片、状态/接口/数据/来源合同、反例和复验记录 | QA 或对应专业复核岗；跨岗由项目经理接收 | 工程岗只改授权路径；产品岗不代写实现；QA 不修代码、不降门槛 |
| B 内容与学习 | 课程架构师、教材研发员、内容审校员、实训评估员、用户研究员 | 能力—练习—证据映射、专业正文/审校单、评价量规、研究包 | 内容审校、实训评估或 QA 按各自门槛独立复核 | 作者与审校分离；研究员不伪造访谈；评估员不代学员作答 |
| C 研究、经济与迁移 | 竞品研究员、运营分析员，配合用户研究员、实训评估员和项目经理 | 可比矩阵、运营账本、敏感性分析、未知任务及产品创造复盘 | 产品经理核决策用途，QA 核口径、证据和复现 | 不以营销声称代实测；不虚构账单；不把内部模拟写成市场或生产结果 |

共同责任如下：

- **产品经理**：定义用户/内部问题、范围与不做项、唯一责任岗位、验收 ID、指标、停止条件和推广门槛；不编写岗位专业产物，不担任该产物的独立复核人。
- **项目经理**：排依赖、维护周期和状态、协调交接、组织周复盘和两周关账；不代替产品、课程、设计、工程或测试结论。
- **课程架构师**：安排共同基础、岗位先修、练习规格和能力映射；不替教材作者写正文或替员工给能力结论。
- **责任岗位**：按合同完成产物，保存环境、来源、首次失败和返修；不改变门槛，不给自己的交付最终复核。
- **独立复核岗位**：使用冻结版本和独立夹具复现，记录通过、缺陷或缺证；不修产物、不删除失败、不替作者补写。
- **接收岗位**：按交接包检查版本、边界、已/未验证和复验步骤；可有据签收或退回，不扩大合同范围。

## 4. 排期与每周节奏

采用 90 日路线，但前 14 天只运行一个岗位的 MVP；后续波次必须由门槛决定，不按日历自动扩张。

### 4.0 D0/D30/D60/D90 里程碑

| 检查点 | 计划活动 | 必须留下的运营证据 | 允许的结论 |
| --- | --- | --- | --- |
| **D0（入组）** | 为 Agent 开发者冻结三项任务、合同、夹具、环境、独立复核人和停止条件；完成边界/机制/失败识别诊断 | 原始诊断、基线快照、补学路径、合同版本和阻断清单 | 仅记录起点；未执行字段为 `not_assessed` 或 `insufficient_evidence` |
| **D30（首岗复验）** | 完成两周 MVP 与一次同岗复验，修正合同、夹具和交接模板 | T1–T3 全套交接、账本、复盘、原例回归和返修记录 | 只有满足“Agent 开发者 → 下一岗位”门槛才可启动下一波 |
| **D60（第二波）** | 分批试点一个相邻工程/产品岗位和一个内容/学习岗位；各自独立记账 | 每岗独立合同、变体/未知任务、复核和缺陷闭环 | 可判断流程是否可复制；不得合并岗位结论 |
| **D90（跨岗切片）** | 仅在前两波证据连续且无阻断时做最小跨岗产品切片和一次获授权内部迭代 | 问题证据、跨岗交接、失败/回滚、内部反馈与变更映射 | 只报告限定范围的 Delivery/Growth 结果；L4、真实用户、专家和生产结果仍需另证 |

D30、D60、D90 是复盘点，不是自动晋级日；若门槛未满足，继续当前岗位返修并保留失败、缺证和 `not_met`，不按日历换岗。

### 4.1 0–7 日：配置和 D0

产品经理冻结首个岗位、`T1/T2/T3`、验收 ID、非目标、权限和停止条件；课程架构师给出共同基础和岗位先修；项目经理建立周期目录；测试工程师冻结收到版本并执行 D0 诊断计划。D0 至少覆盖边界、机制、熟悉任务、失败识别和迁移预告，原始回答和夹具哈希保留。

本阶段的可执行出口是三份 `scoped` 合同和一张诊断/补学记录；没有合同版本、唯一责任、复核人或验收条件的任务不得执行。

### 4.2 第 1 周：T1 基础真实形状任务

- **周一**：冻结合同、基线、输入版本、预算和证据路径；责任岗位复述范围和不做项。
- **周二至周四**：执行 `T1` 正常路径，记录环境、来源、决策、耗时和首次失败；使用隔离数据，不写入真实账户或生产数据。
- **周五**：提交交接包；独立复核复现主路径和至少一条边界；周复盘记录首个偏差、根因假设和行动。

若 `T1` 失败，进入 `rework`，保留原产物和失败证据；不得为赶排期删除失败或改写验收条件。

### 4.3 第 2 周：T2 变体、T3 未知/反例与关账

- **周一至周三**：执行 `T2`，至少改变输入、版本或约束之一，说明方案差异和取舍。
- **周四**：执行 `T3`，由非作者预先冻结缺证、歧义、冲突、超时或危险输入中的至少一种；责任岗位须停止、澄清、升级或回滚，而不是猜测成功。
- **周五**：独立复验三项任务，填写两周复盘卡和能力快照；检查首次失败、返修、原例回归和留出变体是否均可追溯。

两周关账只报告三项任务各自的 Delivery、Growth 和课程检查点状态。即使三项 Delivery 通过，也不能自动把 Growth 写为 `stable` 或把员工提升到产品 L2。

### 4.4 第 3–4 周：首个岗位复验与模板修正

项目经理汇总证据断链、重复缺陷、越界和复验周期；产品经理只修正下一周期合同/指标，保留旧版本。QA 对受影响模板和新夹具做增量复核。若未达到推广门槛，继续同岗位返修，不启动下一波。

### 4.5 第 5–8 周：波次 A/B 的分批试点

先从波次 A 选择一个相邻岗位，再从波次 B 选择一个内容/学习岗位；每个周期仍只选一个岗位和三项任务。波次 B 必须额外绑定来源、论证、先修和专业审校；工程岗必须额外绑定运行时、接口、权限、恢复和版本证据。两个岗位的结果分开记账，不以一个岗位的通过结论覆盖另一个岗位。

### 4.6 第 9–12 周：波次 C 与跨岗产品切片

只有前两波有连续证据且无推广阻断，才组建最小跨岗小队，从真实问题证据开始完成一个可运行或可审阅切片、独立验证、少量获授权的内部反馈和一次迭代。任何外部发布、付费模型、上传或真实生产写入仍需单独授权。L4 产品创造扩展需要真实问题、可比行业证据和外部反馈，不能由 90 日训练自动授予。

### 4.7 固定周节奏

每周均采用以下**异步**节奏，节奏不改变岗位职责；状态以账本和交接包为准，不以口头同步替代证据：

- 周一：产品经理冻结本周问题、验收和非目标；项目经理核依赖、风险和版本。
- 周二至周四：责任岗位执行；每天追加产物、失败、环境和证据账本，不把口头同步当交接。
- 周五：相邻专业岗先做接收检查，独立复核岗位按门槛复现；项目经理进行 15–30 分钟异步复盘。
- 两周末：完成 T1–T3 关账、指标计算、未关闭缺陷清单和下一周期一至两个成长目标。
- 每月：产品经理与课程架构师校准合同、课程检查点和层级映射；QA 复核状态使用和保护范围。

## 5. 任务合同、交接与状态执行

每项任务必须复制 [任务职责合同模板](employee-growth-mvp/task-contract-template.md)，不得三项任务共用一份合同。合同至少填写：

- `task_id`、合同版本、生命周期状态、周期和截止时间；
- 用户/内部使用者、触发场景、当前基线和价值假设；
- 唯一责任岗位、协作者、独立复核人、接收岗位；
- 范围、不做项、前置输入、依赖、禁止权限和升级条件；
- Delivery 交付物、环境、验收条件、证据账本 ID 和限制；
- Growth 目标、T1/T2/T3 情境、前后基线、独立门槛和不能推出的结论；
- 风险、预算、停止/回滚条件和交接截止时间；
- 版本变更原因及旧证据保留方式。

责任岗位完成后使用 [交接包模板](employee-growth-mvp/handoff-template.md)。交接包必须写最短复现步骤、已验证/未验证、失败与返修历史、复核结论和接收确认；交接包本身不是通过证明。

证据写入 [证据账本模板](employee-growth-mvp/evidence-ledger-template.jsonl)，一行只支撑一个主张。每条至少有任务/版本、轨道、主张、证据类型、产物路径或哈希、环境、执行时间、责任人、独立复核人、状态、局限、下一步和复验日期。返修必须新增行，用 `supersedes_evidence_id` 关联；首次失败不得覆盖。

状态严格按 [状态交叉映射](employee-growth-mvp/status-crosswalk.md) 使用：

| 字段 | 允许状态 | 本计划的操作规则 |
| --- | --- | --- |
| 任务生命周期 | `draft → scoped → in_progress → handoff → independent_review → rework → retested → closed` | 允许退回但不得跳过独立复核；`closed` 仅表示本版本关账，不表示能力或产品目标达成。 |
| Delivery | `not_started`、`in_progress`、`passed`、`failed`、`insufficient` | 只判断当前合同交付；失败/缺证必须保留原因、责任人和下一步。 |
| Growth | `not_started`、`emerging`、`independent_candidate`、`stable`、`unverified` | 至少有跨情境或未知任务的独立证据才可考虑升级；课程完成或一次正常任务不够。 |
| 课程检查点 | `pass`、`pass_with_limitations`、`fail`、`insufficient_evidence`、`not_assessed` | 只属于课程检查点；`pass_with_limitations`、缺证和未评估不得汇总为 `pass`。 |

产品层级仍用 L1–L3：课程 L1/L2/L3 分别是学习映射，不能自动晋级；课程 L0 是入组准备，不对应产品级别；课程 L4 是需另取外部证据的产品创造扩展。生命周期变化、Delivery、Growth 和课程结果必须分别填报。

## 6. 证据、复盘与缺陷闭环

### 6.1 证据分层

证据按主张和强度分开：学习/自述、任务产物、运行记录、独立复核、未知任务、真实用户反馈、真人专家复核、生产结果。沙箱、离线、模拟、静态检查和隔离临时数据必须显式标注，不能写成真实用户或生产证据。任何未运行代码、未访问外部契约、版本失配或输入输出缺失均保持 `insufficient` 或 `not_assessed`。

### 6.2 每周复盘

使用 [复盘卡模板](employee-growth-mvp/retrospective-template.md)，只挑一至三个高影响、重复或高风险偏差，记录：事实/基线/版本/环境、预期与实际、首次失败、影响、直接和系统根因、修复/降级/暂停/退回决定、要补知识、唯一责任人、截止时间、证据、原例回归和留出变体。行动在复验前只能是 `open` 或 `in_progress`；报告写完不等于行动关闭。

### 6.3 两周和月度复盘

两周关账计算三项 MVP 指标并登记未完成项；月度校准只调整下一周期的合同、夹具、先修和目标，不覆盖旧报告。连续三次同一系统原因缺陷，升级为流程/能力专项；不得继续记录为个人“粗心”。

## 7. 指标口径与试点门槛

以下指标先用于发现流程和训练缺口，不构成职业认证或产品八门槛的替代。首轮必须记录分母、版本、环境和缺失数据。

| 指标 | 公式/口径 | 首轮使用 |
| --- | --- | --- |
| 合同交付率 | 到期且已独立复核的 Delivery 门槛中，`passed` 的比例 | 观察正常交付是否可关账；不得把未复核算通过 |
| 复验后缺陷率 | 复验门槛中仍为 `failed` 的比例 | 识别返修质量；保留首轮失败 |
| 成长独立证据率 | 有指定独立证据的成长目标 ÷ 本周期成长目标 | 只说明证据存在，不等于 Growth `stable` |
| 证据完整率 | 含合同、版本/哈希、环境、产物、复核、限制和复验的账本条目 ÷ 抽查条目 | 缺任一关键字段则不能声称完整 |
| 首轮接收率 | 首次交接被接收的交接包 ÷ 到期交接包 | 分析合同清晰度和交接质量 |
| 返工重开率 | 经复验后再次进入 `rework` 的任务 ÷ 已返修任务 | 识别根因未解决情况 |
| 重复缺陷率/逃逸率 | 同一系统原因再次出现；或在更晚门禁才发现的缺陷占比 | 进入月度根因专项 |
| 未知迁移通过率 | T3/留出变体中满足指定停止、升级、修复和复核条件的任务 ÷ 已复核未知任务 | 不用原题成功替代 |
| 越界/数据安全事件 | 未授权改应用、真实数据、权限或外部副作用的事件数 | 任一 P0/P1 或未授权事件直接阻断推广 |

产品计划中的 `首轮可接受率不低于70%`、`返工次数相对基线下降30%`、`关键缺陷为0`、`交接字段完整率不低于90%`可作为后续观察目标；它们不是单次任务的能力晋级阈值，必须先取得本周期基线并保留未达标原因。

### 试点启动门槛（从配置到 T1）

1. QA 已确认当前模板、状态映射、层级映射和保护范围在配置口径内可用。
2. 已选定一个岗位和三个不重叠任务，三份合同均为 `scoped`，唯一责任、独立复核、验收、预算、停止条件和证据路径齐全。
3. D0 原始记录、岗位边界复述和补学路径已保存；阻断性边界错误未被隐藏。
4. 任务使用隔离数据或已授权内部数据；没有默认真实数据库写入、外部调用、付费、上传或发布。

### 试点推广门槛（从一个岗位到下一岗位/波次）

全部满足才可推广；否则继续原岗位返修并保留 `not_met` 或 `insufficient`：

1. `T1/T2/T3` 均有合同、交接包、证据账本和复盘卡，生命周期未跳过独立复核；首次失败、返修和原例复验可追溯。
2. 三项任务的 Delivery 结论分别为 `passed`、`failed` 或 `insufficient`，与实际证据一致；没有把缺证静默改成通过。
3. 至少一个变体或未知任务有独立复核；若 Growth 仍为 `emerging`/`unverified`，必须明确下一周期，而不能授予更高层级。
4. 无未关闭 P0/P1；任何权限、隐私、数据损坏、版本错配或未授权外部副作用事件均阻断推广。
5. 证据链抽查可从主张追到合同版本、产物/运行记录、复核、限制和下一步；关键字段完整率达到观察目标或已登记明确的修复责任与日期。
6. 两周复盘至少关闭一项经原案例复验的系统改进；未复验行动保持开放。
7. 项目经理、产品经理和独立复核人共同确认“流程可追踪”的限定结论；不写职业胜任、真实用户满意或行业先进。

### Agent 开发者两周 MVP → 其他岗位的专用门槛

这是 D30 前的首个扩展闸门，必须全部满足：

1. Agent 开发者的 `T1/T2/T3` 各有独立合同，且至少覆盖一次正常交付、一次输入/版本/约束变体和一次未知/反例处理；每项都保留首次失败、返修和按原条件复验。
2. 三项任务均完成独立复核并分别记录 Delivery；Growth 至少有一项跨情境或未知任务的独立证据，证据不足仍写 `emerging` 或 `unverified`。
3. 不存在未关闭 P0/P1、未授权应用/数据库/用户数据改动、外部发送、上传、付费调用或权限越界；发现即冻结推广。
4. 抽查可从每个主张追到合同版本、产物/运行记录、环境、复核、限制和下一步；缺证不通过，不以报告完成替代。
5. 至少一项系统改进已按原例回归并由独立复核确认；未复验行动保持开放，并指定责任人和日期。
6. 产品经理、项目经理和独立复核人签署“流程可复制到一个下一岗位”的限定结论；这不等于 Agent 开发者或下一岗位已获得职业能力认证。

下一岗位仍须从 D0 重新诊断、建立三份新合同和独立证据账本；不得把 Agent 开发者的结论、课程完成或旧版本 QA 自动继承为新岗位通过。

### 进入跨岗产品切片的追加门槛

在至少两个岗位周期都有上述证据后，才可进入 P2 跨岗切片：问题有真实或可核验的内部证据、非目标和停止条件清楚；跨岗交接可复现；失败与回滚有证据；至少一次获授权的内部反馈和一次迭代可追溯。没有外部用户、同行、专家或生产证据，完整产品和 L4 仍为 `not_assessed`。

### 停止、回滚与降级

出现未授权数据/应用改动、密钥或隐私泄露、P0/P1、复核人兼任责任人、版本/夹具不可复现、为通过而删除失败、或需要未授权外部调用时，项目经理立即将任务退回 `rework` 或 `insufficient`，冻结推广，保留原证据并由产品经理重新定界。修复后必须按原合同复验；不得通过删除任务、降低门槛或覆盖历史记录来恢复排期。
