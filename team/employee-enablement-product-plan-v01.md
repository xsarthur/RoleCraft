# 员工赋能产品框架与 90 天行动计划

日期：2026-10-14（Asia/Shanghai）  
责任岗位：产品经理  
状态：产品方案交接；不代表现有员工已经达到任何能力级别，也不改变原有产品门槛。

## 1. 产品问题

当前岗位多数可以在范围明确时完成小型交付，但从项目记录看，以下能力证据不足：

- 从真实问题和用户证据定义范围、非目标和成功条件；
- 在歧义、冲突、未知和失败状态下做专业取舍；
- 绑定版本、来源、环境、反例和复验步骤，区分计划、自查、实际运行、真人和生产证据；
- 将假设、依赖、风险和未验证项完整交给下一岗位；
- 把一个问题推进到实现、独立验证、真实使用反馈和迭代，而不是停在文稿、演示或自述；
- 将已验证的方法沉淀为可复用的角色记忆、夹具、模板和反例。

赋能目标是逐步增加可验证的独立判断和决策权。增加提示词长度、任务数量或报告篇幅不能单独证明能力提升。

## 2. 通用能力分层

每个岗位使用同一底座，专业深度和作品类型按岗位不同。能力级别与任务难度分开记录。

| 级别 | 可观察能力 | 交付证据 |
| --- | --- | --- |
| A0 受指导 | 能按示例和逐步指令完成熟悉变体，能解释关键步骤；遇到范围、权限或证据不明会停下升级。 | 受指导任务、原因说明、未解决问题 |
| A1 独立小任务 | 能读懂契约，在冻结范围内完成小交付，附来源/版本/反例/验证记录并完成一次返修；不越过唯一责任边界。 | 完整产物、证据包、独立复核和原案例复验 |
| A2 独立中型任务 | 面对歧义先澄清，比较方案和取舍，处理至少一个失败分支，完成跨岗交接，并能根据反馈改进。 | 方案记录、风险矩阵、交接包、返修前后证据 |
| A3 产品切片负责人 | 从真实问题假设推进到可运行或可审阅切片、独立测试、少量真实使用和迭代复盘，能协调依赖和停止条件。 | 用户证据、版本交付、QA、真实反馈、迭代记录 |
| A4 领域导师 | 在两个不同场景复现结果，形成经验证的模板/反例库，带教他岗并改善团队质量指标。 | 第二场景证据、带教记录、指标变化和复验 |

统一交付必须包含：目标与非目标、输入版本、产物、决策和取舍、失败/边界、来源与验证、独立复核、返修版本、限制和下一步。自评不能替代专业审校、QA、真人专家或真实用户证据。

## 3. 十五岗能力地图

共同底座先行，再按唯一责任领域练专业判断：

| 岗位 | 优先培养的专业判断 | 首个可观察作品 |
| --- | --- | --- |
| 项目经理 | 依赖、交接、状态、复盘和升级 | 一份带责任人与复验条件的交付复盘 |
| 产品经理 | 问题、范围、验收、优先级和价值假设 | 一份完整产品契约与未决决策清单 |
| 课程架构师 | 能力序列、先修、练习和量规 | 一份能力到作品/证据的映射 |
| 设计师 | 视觉优先流程、状态、可访问性和响应式 | 正常/空态/错误/恢复的视觉稿与状态说明 |
| 软件工程师 | 状态、接口、错误处理、恢复和客户端证据 | 一个隔离切片及可复现验证命令 |
| 后端数据工程师 | 权限、持久化、版本迁移和恢复 | 数据契约、迁移/回滚方案与夹具 |
| AI 生成工程师 | 模型协议、来源关联、预算和失败降级 | 生成服务接口、失败矩阵和来源绑定 |
| 内容检索工程师 | 分节索引、意图、召回/排序、出处和版本 | 可定位推荐及无匹配/歧义处理记录 |
| 测试工程师 | 风险、反例、独立夹具和证据边界 | 绑定验收ID的测试矩阵与原案例复验 |
| 教材研发员 | 机制、实现、权衡、失败模式和完整参考解析 | 一篇绑定来源的完整正文与练习 |
| 内容审校员 | 论断、来源、边界和不确定性 | 独立审校意见与缺陷/返修记录 |
| 用户研究员 | 不诱导访谈、原始证据和用户价值分析 | 访谈/观察记录与证据分层结论 |
| 竞品研究员 | 可比条件、研究基线和差异证据 | 一份可复现的对比矩阵 |
| 实训评估员 | 量规、作品证据和未知任务评价 | 一次盲测评价及证据链 |
| 运营分析员 | 成本、耗时、质量和维护数据 | 一份带口径和不确定性的运营账本 |

作者、审校和QA必须分离；产品经理定义门槛，不能代替专业写作、实现或独立验收。

## 4. 90 天产品路线

### P0：第 1–30 天，可信小交付

为每岗补齐能力卡（职责、输入、输出、禁区、常见失败、示例、验收），冻结统一任务契约、交接包、证据包、升级规则和记忆写入规则。建立隔离样例、反例、错版本夹具和来源注册表。每岗完成两个 A1 小任务。

验收：产物可复现、版本与来源可定位、状态表述诚实、关键职责零越界，QA可以按记录复核；历史通过/失败结论不自动继承。

### P1：第 31–60 天，独立处理中型任务

每岗完成正常、歧义/冲突、失败恢复三类练习，至少一次方案比较、失败分支、跨岗交接和返修复验。选择未见任务验证“能处理未知”，而非只重复练习题。

验收：相邻岗位可消费交付；首轮接收率、返工次数、关键缺陷、澄清轮次、证据完整度形成基线；未通过项建缺陷，不以补写报告关闭。

### P2：第 61–90 天，完成一个 0→1 产品切片

组建最小跨岗小队（按问题选 PM、设计、工程、数据/生成/检索和QA），从真实问题和用户证据开始，完成范围、视觉/实现、失败处理、独立验证、少量真实内部使用、反馈和一次迭代。涉及外部效果、付费模型、上传或发布仍需单独授权。

验收：问题假设有来源，非目标/停止条件清楚，版本可运行或可审阅，失败与回滚有证据，真实反馈和迭代记录可追溯；不能以内部演示推导职业胜任、市场成功或行业先进。

## 5. 波次与每周节奏

先跑核心产品波（PM、设计、软件、后端、AI生成、检索、QA），再把同一底座迁移到内容学习波（课程、教材、审校、用户研究、实训），最后由竞品、运营和项目经理完成比较、经济分析和复盘。十五岗不要求同时常驻或同时训练。

每周：周一冻结问题/契约与本周能力目标；周二至周四完成隔离任务；周五由相邻专业岗审校，QA抽取必要反例实测；周末由项目经理复盘目标、结果、差距、责任、下一步和复验。自评、专业审校、QA、用户反馈四类结论分栏保存。

## 6. 赋能组件与渐进授权

- **上下文**：角色卡、项目简报、术语/来源注册表、已确认用户偏好和明确的非目标；
- **工具**：隔离沙箱、固定输入、回放夹具、观测记录、版本控制和失败实验室；
- **反馈**：示例—反例—首轮失败—修复—原案例复验的闭环，每周至少一次失败实验室；
- **记忆**：每个岗位有独立跨项目角色记忆；项目事实、经证据确认的改进和待确认假设分层，含来源、版本、适用范围和置信度；
- **权限**：只读/本地隔离写入 → 内部真实数据 → 外部副作用，逐级放开。权限矩阵明确哪些决定可自行做、哪些必须交接或PM/用户批准，并保留停止条件、回滚和复验。

## 7. 初始指标与边界

先用 14 天任务建立基线，以下仅为可调整的产品目标：每岗两个 A1 和一个 A2 样本；首轮可接受率目标不低于 70%；返工次数相对基线下降 30%；关键缺陷为 0；交接字段完整率不低于 90%。这些指标用于发现流程和能力缺口，不构成职业认证，也不替代原有八项产品门槛。任何能力升级必须有未见任务和独立证据，不能只看任务数量、字数、测试数量或员工自述。

## 8. 主要风险

只堆提示词/教材、把所有岗位训练成同一模型、作者自写自审、把静态检查写成真实运行、把记忆存在写成能力掌握、在交接和验证未稳定前启用多Agent或生产外部效果，都会制造虚假进步。项目经理需把这些列入复盘和缺陷台账。

本方案与课程架构师的培养路线及测试工程师的 G0–G5 质量门禁配套使用；三者分别负责产品范围、教学结构和独立质量验证，不能互相替代。
