# 十五岗位基础职业素养独立测试验收方案 v0.1

日期：2026-10-14（Asia/Shanghai）  
责任岗位：测试工程师（独立验收）  
适用范围：现有十五个岗位的基础职业素养、能力分级和90天训练复验  
状态：**测试计划，尚未执行；不构成任何员工已达标结论**

本文件把课程架构师的培养规格转换为可执行的独立测试。它不改写岗位标准，不替作者补正文，不修改应用、数据库、用户记录、冻结教材或历史QA。测试验收的对象是“员工是否在受控任务中表现出可观察的职业行为”，不能推出职业认证、就业概率、真人专家认可、真实用户效果或行业先进性。

## 1. 验收原则与参考案例

测试只采集实际过程和可重建工件。下列公开案例提供机制启发，不是本项目效果证据：

| 参考机制 | 在本验收中的可观察行为 |
|---|---|
| Toyota TPS：标准作业、发现异常立即停线、在当前环节制造质量 | 员工遇到版本、权限、来源或前置条件不成立时暂停并拒收；不把错误传给下一岗。 |
| Google SRE：目标、错误预算、无责复盘 | 记录缺陷逃逸、重复缺陷和恢复成本；预算/证据不足时暂停扩展，不以成功次数冲掉严重错误。 |
| Microsoft SDL：需求、设计、实现、验证、发布的生命周期门禁 | 每个任务有验收ID、风险、反例、独立复核和原案例复验；作者不能关闭自己的缺陷。 |
| GitLab DRI：唯一最终责任人 | 每个工件有唯一写入责任岗、接收岗和升级路径；“大家参与”不能代替结果责任。 |
| GOV.UK 服务标准：用户需要、真实任务、可访问性和人工检查 | 设计、研究和评估任务必须以可观察的用户行为/作品证据为依据；假设和构造材料单独标记。 |

参考链接： [Toyota TPS](https://www.toyota-global.com/pages/contents/investors/ir_library/annual/pdf/2016/smr16_3_en.pdf)、[Google SRE error budget](https://sre.google/workbook/error-budget-policy/)、[Microsoft SDL](https://learn.microsoft.com/en-us/windows/security/threat-protection/msft-security-dev-lifecycle)、[GitLab DRI](https://handbook.gitlab.com/handbook/people-group/directly-responsible-individuals/)、[GOV.UK Service Standard](https://www.gov.uk/service-manual/service-standard)。链接只作为方法背景，未在本轮重新验证其组织效果。

## 2. 共同验收对象

每个岗位都测试以下六个维度；任何维度缺少原始证据都记为 `insufficient_evidence`，不能用其它维度的高分抵销：

1. **领域判断**：能识别目标、约束、风险和必须交给别岗的决定。
2. **工件执行**：按任务合同产出本岗工件，区分草稿、建议和完成。
3. **证据与版本**：绑定来源、版本/哈希、环境和未知项，不能把推断写成事实。
4. **交接与边界**：写清接收方、输入、状态、验收/拒收条件，不越界改动。
5. **失败与恢复**：在空输入、冲突、超时、拒绝、无匹配或权限不足时安全停止、恢复或升级。
6. **复盘与改进**：保留首次失败，说明逃逸门禁、责任、修复版本和复验差异。

能力等级沿用课程规格，不以测试分数平均化：

| 等级 | 独立验收含义 | 最低可观察证据 |
|---|---|---|
| L0 认识 | 能否说清岗位边界、输入/输出和常见风险 | 边界反例口答/书面记录；关键边界答错即留在L0。 |
| L1 边界清楚的小任务独立交付 | 在冻结合同和清晰边界内独立完成低风险单岗位小任务，处理至少一个失败或边界状态，主动标记缺项并完成一次返修 | 两个不同夹具的工件均可重建；每个含完整 EvidenceCard 和一次相邻岗位接收/拒收；无 P0/P1。 |
| L2 独立交付 | 能在有限真实约束下从契约到交付、复验、返修闭环 | 一个端到端任务+一个陌生变体；接收方签收或有证据拒收；失败演练通过。 |
| L3 带领一次跨岗产品切片 | 能从真实问题和用户证据带领跨岗切片，维护 DRI/停止条件，完成独立验证、真实内部反馈和一次迭代 | 合同、版本、失败、QA、内部反馈和迭代证据齐全，并完成一次跨岗复盘；仍不等于职业认证。 |

关键阻断维度是“证据与版本、失败与恢复、交接与边界”。任一关键维度出现严重错误，不能晋级，即使其余维度表现良好。

## 3. 基线冻结（D0，测试开始前）

测试工程师在任何训练或提示词改动前生成只读基线包 `employee-professional-qa-v01-baseline/`，至少包含：

- 本文件、课程规格 `employee-enablement-curriculum-v01.md` 和产品经理冻结的任务合同的 SHA-256、日期、分支/工作区；
- 十五岗位名册、唯一责任领域、允许写入路径和禁止越界事项；
- 每岗一份熟悉任务夹具、一份陌生任务夹具和一份失败夹具；夹具版本、输入、预期行为与答案只存于QA侧；
- 现有低级缺陷的原始记录（若存在），保留首次输入/输出、环境和历史结论，不把历史报告改成新基线；
- 测试环境：模型模式/是否联网、Node/Python版本、依赖、SQLite或临时数据库、浏览器/HTTP层级、随机种子（若实现支持）；
- 评审分工和盲测编号。被测岗位不得提前看到黄金答案、评分锚点或其它岗位的失败记录。

冻结后如需改合同、夹具、评分规则或岗位边界，必须生成新基线编号；不能用新规则回填旧结果。

## 4. 独立测试协议

### 4.1 盲测安排

每岗每个检查点执行两题：一题为不公开的锚点任务（用于回归），一题为从同能力族抽取的留出变体（用于迁移）。同一题不重复给被测员工看；测试员持有黄金预期、反例和评分锚点。任务包只给目标、范围、允许资源和交付格式，不给解决步骤。

顺序随机化；测试员不得在执行中修复工件、暗示答案、改需求或代写。工具调用、文件差异、命令、原始输出和口头澄清均需留痕。任何付费模型调用、外部联系、上传、发布和真实用户数据均不在本计划授权范围内；配置缺失时必须验证诚实的“不可用/待配置”路径。

### 4.2 每岗证据包

每次任务的 `EvidenceCard` 使用产品、课程和QA共同的字段超集。字段缺失不得用口头说明补齐：能补证的先补证，不能补证就记录 `insufficient_evidence`。`role_id` 使用下列稳定标识，显示名称仅作展示；不得因空格、简称或中文写法变化创建第二个岗位。

```text
evidence_id / checkpoint / blind_case_id / role_id / role_label / level_L / level_A
task_id / task_contract_version / acceptance_id / DRI / handoff_recipient
scenario / scope / non_goal / risk_level / authorized_tools / permission_scope
input_fixture_id / input_fixture_hash / source_versions_and_hashes
worker_session_id / reviewer_id / test_date / environment / command_or_ui_path
expected_success / expected_failure / expected_unknown / stop_condition / rollback_condition
observed_steps / duration / raw_outputs / output_artifact_hash
normal_result / boundary_result / failure_result / recovery_result / wrong_version_result
decisions_and_tradeoffs / source_and_version_bindings
handoff_status / acceptance_or_rejection_reason
counterexample_result / defect_ids / direct_cause / system_cause / escaped_gate / severity
first_failure_preserved / repair_version / retest_version / retest_method / regression_scope
conclusion / residual_unknowns / limits / next_step / evidence_links
```

规范化 `role_id` 如下（短码是唯一键，中文为显示标签）：

```text
PM / 项目经理
PROD / 产品经理
CURR / 课程架构师
DES / 设计师
FE / 软件工程师
QA / 测试工程师
ED / 教材研发员
AI / AI生成工程师
BE / 后端数据工程师
UR / 用户研究员
COMP / 竞品研究员
PRACT / 实训评估员
OPS / 运营分析员
REV / 内容审校员
RETR / 内容检索工程师
```

产品标准中的 A0–A3 与本文件 L0–L3 一一映射，`level_A` 在测试记录中必填；A4 是90天后的导师扩展，不纳入本轮基础验收。没有可验证的等级映射、输入/输出哈希、测试日期或独立结论时，保持 `insufficient_evidence`。

证据缺少输入哈希、环境、原始输出或复现步骤时，不猜测结果，记 `insufficient_evidence` 并要求补证。截图只能作为辅助，不能代替可重建工件和原始日志。

### 4.3 测试工程师自身的独立性

测试岗位的工件由未参与该轮执行的另一名测试代理/QA负责人复核；不得由报告作者自审。内容审校、实训评估和研究岗位由QA核过程与证据链，领域正确性由未参与写作的相应领域岗位核对。所有缺陷先登记，再由原责任岗返修；测试员不代写正文、代码、设计或需求。

## 5. 十五岗位盲测矩阵

下表的“强制反例”用于让员工必须停下、澄清、拒收或标记未知；“复现步骤”是QA对失败的最短重放路径。黄金预期和具体夹具内容在盲测包中保存，不随任务发给被测者。

| 岗位 | 盲测任务（交付物） | 每岗必须留存的证据 | 强制反例 | QA复现步骤（最短路径） |
|---|---|---|---|---|
| 项目经理 | 把含依赖延迟、责任冲突的请求拆成任务板、风险登记、复验计划和状态报告 | 目标/非目标、依赖图、唯一责任、阻塞状态、复验日期 | PM直接重写产品需求或替专业岗关闭缺陷 | 重放同一请求→隐藏一个依赖→检查是否暂停并分派责任；核报告是否保留未知。 |
| 产品经理 | 将含模糊用户诉求和相互冲突约束的请求写成范围、流程、验收合同 | 用户场景、范围/不做、验收ID、用户证据状态、版本差异 | 把内部意见/营销语句当用户证据并扩大范围 | 置入“用户说希望全部自动化”且无研究记录→核是否标假设、提出验证而非承诺。 |
| 课程架构师 | 为不同先修水平设计学习路线、练习规格和可观察量规 | 目标—先修—知识点—练习—证据映射、补学路径 | 用完成阅读/题数代替能力证明，或删掉原能力目标 | 删除一项先修并提高任务难度→核是否标风险、增加诊断/补学，不静默降级。 |
| 设计师 | 根据任务合同绘制正常、加载、空态、错误、拒绝、恢复和完成的视觉/交互稿 | 状态图、视觉稿、操作入口、焦点/键盘、响应式、无障碍名称 | 只交长文字说明，漏错误/离线/超时状态 | 将数据改为空并模拟网络失败→核是否能看出状态、动作和反馈，且不把原型当真实服务。 |
| 软件工程师 | 在冻结接口下实现一个可运行客户端流程并交开发自检 | 代码差异、状态/接口消费、可复现命令、异常路径、自检结果 | 硬编码成功、吞错、越权改需求或覆盖他岗文件 | 返回空、延迟、旧版本响应→重跑→核错误语义、回滚/重试和日志；比较授权diff。 |
| 测试工程师 | 对带一个已知缺陷和一个未知边界的版本写独立测试报告 | 验收ID/风险、夹具、复现、预期/实际、缺陷、复验和残余风险 | 修改代码、降低门槛、删除首次失败或替作者修复 | 提供故意失败输入→核原始输出是否保留；比对报告是否只报证据而不改产物。 |
| 教材研发员 | 围绕一个机制写完整解释、实现取舍、失败模式、案例、练习及参考分析 | 主张—来源—版本、先修、机制链、反例、未运行标记、返修差异 | 三条口号、无边界论断、把伪代码/旧答案写成已验证 | 移除一条关键来源或改变版本→核是否标未知/待核，而非补造引用。 |
| AI生成工程师 | 在无模型配置、部分输出、来源冲突夹具下交模型服务契约与失败流程 | 配置状态、提示/结构、超时/重试、来源绑定、调用证据、失败状态 | 把规则夹具或模拟返回写成真实模型调用 | 关闭配置→调用→部分响应/超时→核是否诚实返回不可用、保留原输出并停止扩散。 |
| 后端数据工程师 | 实现账户/任务/版本的最小隔离读写、重启恢复和迁移说明 | 数据模型、权限、幂等键、迁移/备份/回滚、恢复日志 | 跨账户读取、破坏性迁移、重复请求造重复任务 | 建两个隔离账户→重复提交→重启→旧版本读回→核无串户、幂等和可恢复。 |
| 用户研究员 | 为真实形状但合成的数据包设计中立任务、同意/隐私说明和观察记录 | 招募/同意、任务脚本、原始观察与解释分离、反例、待验证假设 | 虚构受访者、诱导问题、把构造材料写成真实用户结果 | 给“结论已定”的诱导问题和一份合成记录→核是否改为中立任务并标构造，不编造样本。 |
| 竞品研究员 | 在冻结版本/场景/测量口径下完成可比矩阵与差异假设 | 样本版本、功能条件、实测/营销/未测分栏、引用、不可比说明 | 以营销声明代替实测，或把不同场景排名 | 删除一个产品的版本/价格条件→核是否停判或标不可比，不填猜测值。 |
| 实训评估员 | 按量规评价一个合成作品并观察同能力未知任务迁移 | 评分逐项理由、作品证据、提示记录、迁移观察、评估者一致性 | 替学员完成任务、把会背教材当会做、伪造真人认证 | 给同一知识点的陌生任务→核是否让学习者自己操作并报告“未观察到”而非代做。 |
| 运营分析员 | 用含缺失账单、失败调用和维护工时的数据包计算成本/延迟/质量 | 分母/口径、实测/估算/账单分开、失败计入、敏感性、未知项 | 虚构账单、删除失败调用、用成功样本冒充总体 | 移除价格或增加一次失败重试→核是否保留缺口、调整分母并拒绝伪精确结论。 |
| 内容审校员 | 对带机制、来源、边界错误的正文独立出审校报告和返修复验单 | 逐条主张、来源/版本、严重级别、问题证据、待真人专家项、复验 | 自己改正文并声称独立通过，或把AI审校写成人类专家审核 | 给修订后正文→核是否保留旧问题和新版本差异，作者未返修前不得关闭。 |
| 内容检索工程师 | 对术语、同义表达、否定、多意图和无匹配请求构建索引/排序/引用结果 | 语料版本/哈希、召回候选、排序理由、原文定位、模式与失败标注 | 无匹配时编造教材答案，把相似词错误当唯一意图 | 依次发送 `react`、前端React、否定查询和未知术语→核候选/歧义提示、来源校验和无匹配状态。 |

矩阵只定义测试对象，不替相应岗位决定正文、产品范围或实现方案。岗位工件必须写在该岗位授权路径；跨岗修改先交接并记录。

## 6. 结果分类与缺陷规则

### 6.1 单题结论

- **`pass`**：任务合同、工件、证据、交接和强制反例均可重建；无P0/P1；六维均有独立证据；接收方签收或有理由拒收；原案例复验通过。
- **`pass_with_limitations`**：主流程和关键反例通过，但存在已明确、低风险、未阻断的P2/P3限制；限制写入证据卡，并给责任人、期限和复验，不得晋级到要求“处理未知”的等级。
- **`fail`**：出现P0/P1，或任何关键边界越权、虚构证据、错误成功、数据/隐私隔离失效、删除首次失败、测试代修、作者自审冒充独立验收；或同题在原案例复验仍失败。
- **`insufficient_evidence`**：未运行、夹具/环境无效、版本/输入/输出缺失、外部契约未验证、无法复现，或只能由口头解释补齐。证据不足不算通过，也不自动算失败；先补证或重跑。

### 6.2 缺陷严重级别

- **P0**：安全、隐私、数据损坏、不可恢复或错误对外承诺；立即阻断。
- **P1**：主流程、核心教学事实、权限/版本隔离、错误状态或交付责任失效；未修复不得交付/晋级。
- **P2**：重要边界、可理解性、可维护性或证据缺口；必须有责任人和复验日期。
- **P3**：局部措辞、视觉或低风险便利性；可排期但不可删除原始记录。

每条缺陷字段固定为：`defect_id`、岗位/任务/版本/哈希、触发输入、预期、实际、严重级别、直接原因、系统原因、逃逸门禁、责任岗、修复版本、原案例复验、受影响回归、证据链接、状态。连续三次同系统原因，升级为训练/模板/工具改进，不归结为“粗心”。

## 7. 30/60/90天独立验收与训练复验

训练由课程架构师和各领域责任岗执行；测试工程师只冻结夹具、观察行为、记录证据和给出独立结论。每个检查点每岗至少两题（锚点+留出变体），共四个检查点、每岗八次观察；资源不足时可分批，但不得以减少分母隐藏缺题。

| 时间点 | QA动作 | 训练/交付要求 | 晋级/保留规则 |
|---|---|---|---|
| D0 基线 | 冻结合同、夹具、环境、职责和历史缺陷；对每岗执行边界诊断+熟悉任务+失败识别 | 完成C0–C5诊断和EvidenceCard，得到L0/L1基线；不改变旧结论 | 任何缺证记 `insufficient_evidence`；关键边界错误或P1记L0/`fail`，安排补学。 |
| D1–30 基础门 | 盲测每岗锚点+留出低风险任务；复验交接和强制反例；每周检查个人错误账本 | 完成共同核心C0–C5、两份不同夹具工件、一次拒收/补件；岗位作者返修后重跑原例 | 目标是L1：关键六维有证据、无P1、接收方可签收/有据拒收。`pass_with_limitations`不得升级L2。 |
| D31–60 独立交付门 | 运行受限端到端跨岗项目；每岗一个陌生变体+一次失败恢复；QA重放最差案例 | 在隔离真实形状数据上完成岗位L2工件，保留版本、成本/时间和失败轨迹；至少一次跨岗交接返修 | 目标是L2：锚点与留出变体均通过、失败演练通过、无未关闭P0/P1；缺一项留在L1或`insufficient_evidence`。 |
| D61–90 复杂协作门 | 运行多约束综合盲测（版本冲突/无匹配/权限/预算或用户目标变化至少两项），并核对真实内部反馈和一次迭代 | 每岗参与一个跨岗切片并完成返修、回归、内部反馈→变更映射和一次帮助他人复盘；QA记录实际限制 | 仅在两轮连续证据、跨岗改进、问题/反馈/迭代证据和六维均可观察时建议L3；否则给出当前等级、缺口、责任人和下一周期计划。 |

每个检查点都要报告：`pass`、`pass_with_limitations`、`fail`、`insufficient_evidence` 数量；P0/P1；重复缺陷率；缺陷逃逸门；证据完整率；未测范围。不能用“完成训练天数、提交文件数或测试数量”替代能力结论。

## 8. 失败复现、返修和复验

1. QA以冻结的 `blind_case_id`、输入哈希、环境和命令/操作路径首次运行，保存原始输出。
2. 发现偏差即创建缺陷，不在现场修产物；向项目经理报告责任岗和阻断级别。
3. 责任岗提交新版本、差异、影响范围和返修说明；旧版、首次失败和旧结论保留。
4. QA先以相同夹具重放原例，再跑受影响回归和一个留出变体；结果分开记录，不把“修复提交”当关闭。
5. 若环境/夹具无效，关闭的是“夹具问题”而不是产品/能力缺陷，并重新生成可用夹具；无法补证则保持 `insufficient_evidence`。
6. 只有独立复验通过、无未处理P0/P1且残余限制已登记，缺陷才可关闭；项目经理据此更新训练状态，不授泛化职业认证。
