# 数字员工专业负责与持续成长 · 两周 MVP

状态：可执行产品流程模板（产品经理交付，尚待独立 QA 复核）  
版本：`mvp-0.1`  
适用范围：一人公司内任一专业岗位；首轮只选一个岗位和三项真实任务。

## 这套 MVP 要解决什么

两周内验证一件事：员工能否在不越界的前提下完成真实交付，同时留下可追溯、可独立复核的职业成长证据。每项任务始终维护两条互不覆盖的轨道：

- **Delivery（交付）**：本次任务的产物是否按合同和版本绑定的验收条件完成。
- **Growth（成长）**：本次工作是否证明了某项能力在新情境中提升；自评、课程完成、字数或调用次数不构成独立证据。

`Delivery=passed` 不等于职业能力已稳定，`Growth=emerging` 也不等于本次交付合格。没有真实用户、同行、专家或生产证据时，明确写 `unverified`。

## 两周最小范围

### 必做

1. 选定一个岗位和三项互不重叠的真实任务：`T1` 基础交付、`T2` 近邻变体、`T3` 未知/反例任务。
2. 每项任务创建一份 [任务合同](./task-contract-template.md)，执行中只按合同版本工作。
3. 交付后创建一份 [交接包](./handoff-template.md)，由合同指定的独立复核人检查。
4. 每条交付或成长主张追加一行 [证据账本](./evidence-ledger-template.jsonl)；首次失败、返修和复验各保留自己的行。
5. 每周一次、两周结束一次填写 [复盘卡](./retrospective-template.md)，将未复验的行动保持为 `open`。

### 不在 MVP 内

- 不接入数据库、学习工作台、付费模型、外部上传、发布或消息发送。
- 不改变岗位专业标准、教材正文、应用代码、用户账户或历史报告。
- 不以流程通过、任务数量或内部模拟推断职业胜任、用户满意或行业先进。
- 不让责任岗位同时担任自己的独立复核人；不删除失败记录或用新版本覆盖旧记录。

## 责任边界

| 角色 | 本轮负责 | 明确不负责 |
| --- | --- | --- |
| 产品经理 | 用户问题、范围、不做项、验收条件和三个任务的口径 | 不代写专业产物，不代替独立复核 |
| 项目经理 | 依赖、版本、状态、交接、复盘节奏和汇总 | 不改写专业标准，不宣布职业能力达标 |
| 责任岗位 | 按合同完成交付，保存过程、失败和来源证据，提交交接 | 不改验收门槛，不给自己的交付最终复核结论 |
| 独立复核岗位（测试/内容审校/用户研究等） | 按本领域门槛复现、记录通过或缺陷、要求复验 | 不替责任岗位补写产物，不删除失败证据 |
| 接收岗位 | 检查输入、版本、边界和复验步骤，确认可接收或退回 | 不扩大合同范围，不把未验证写成已验证 |

每个合同只能有一个 `owner_role`。协作者可以提出建议，但不能抢占唯一责任或改变他人授权路径。

## 状态和门槛

任务状态按以下顺序推进，允许退回但不能跳过独立复核：

`draft → scoped → in_progress → handoff → independent_review → rework → retested → closed`

- `draft`：字段不完整，不能执行。
- `scoped`：范围、不做项、版本、责任人和验收条件齐全。
- `in_progress`：责任岗位执行，持续追加证据和失败记录。
- `handoff`：交接包齐全，已写明环境、已验证/未验证和复验步骤。
- `independent_review`：独立复核人在合同版本上复现；结论只能是 `passed`、`failed` 或 `insufficient`。
- `rework`：有明确缺陷和返修责任；旧产物、旧证据和失败原因保留。
- `retested`：复核人按原验收条件复验返修版本，并链接首次失败。
- `closed`：只表示该版本对应门槛已复核；成长或完整产品目标仍可为 `unverified`。

### 双轨字段的最低要求

每项合同、交接、账本和复盘都要同时填：

| 轨道 | 必填内容 | 关闭条件 |
| --- | --- | --- |
| Delivery | 交付物、版本、验收条件、运行/来源证据、独立复核结论、限制 | 交付门槛通过，或明确 `failed/insufficient` 并登记下一步 |
| Growth | 一个可观察能力目标、前后基线、跨情境/未知任务证据、独立复核、局限 | 仅在指定独立证据足够时升阶；否则保留 `emerging/unverified` |

推荐的成长目标格式：

> 在【真实任务或受控练习】中，独立完成【可观察动作】，产出【证据】，通过【指定门槛】。

## 三项真实任务配置

在启动会填好下面三行，并把对应任务 ID 写进四份模板：

| ID | 任务用途 | 必须覆盖的成长情境 | 最低独立复核 |
| --- | --- | --- | --- |
| `T1` | 基础真实交付：验证职责、范围和正常路径 | 依照明确输入完成一次可复现交付 | 复现主路径和一条边界 |
| `T2` | 近邻变体：验证迁移与权衡 | 输入、版本或约束至少改变一项 | 复现变体并检查取舍理由 |
| `T3` | 未知/反例：验证负责地处理失败 | 缺证、歧义、冲突、超时或危险输入至少一种 | 独立复现失败，检查停止/升级/回滚判断 |

三项任务可属于同一岗位，但不得让 `T2` 或 `T3` 只是复制 `T1` 的文件。若任务本身不允许真实用户数据，使用隔离的本地数据并把证据标为 `offline`，不得写成生产结果。

## 两周执行节奏

| 时间 | 动作 | 产物/门槛 |
| --- | --- | --- |
| 第 1 天 | 选岗位、定 `T1–T3`、补能力基线和合同 | 三份 `scoped` 合同；每份有唯一责任与独立复核 |
| 第 2–4 天 | 执行 `T1`，记录版本、环境、来源和首次失败 | 交付物、交接包、账本行；不通过则进入 `rework` |
| 第 5 天 | `T1` 独立复核和周复盘 | 复核结论、失败保留、行动负责人/截止时间 |
| 第 6–8 天 | 执行 `T2`，说明与 `T1` 的差异和权衡 | 变体产物、独立证据、成长状态更新 |
| 第 9 天 | 执行 `T3`，刻意覆盖反例或缺证 | 失败样本、停止/升级理由、复验计划 |
| 第 10 天 | 三项复验、两周复盘和能力校准 | 三份最终状态、证据链、未完成差距和下一周期目标 |

## 证据与版本规则

- 文件命名建议：`{task-id}-v{major.minor}-{artifact}`；合同范围或验收变化必须升版本。
- 账本一行只支持一个主张；使用 `supersedes_evidence_id` 关联返修，不覆盖旧行。
- 证据类型至少区分 `self_report`、`artifact`、`run_log`、`independent_review`、`unknown_task`、`user_feedback`、`expert_review`、`production`。
- 每条证据写明执行环境、日期、操作者、独立复核人、状态和局限。缺失任一关键字段时，主张为 `insufficient`。
- 失败记录必须保留：首次失败输入/步骤、错误或偏差、影响、责任人、修复版本、复验结果和仍存局限。

## 关账检查

项目经理在两周末逐项检查并在复盘卡中链接证据：

1. 三份合同是否都有版本、范围、不做项、唯一责任、验收条件和独立复核人？
2. 每项是否分别填写 Delivery 与 Growth，且没有用一条轨道覆盖另一条？
3. 每项是否有交接包、环境/来源、未验证清单和可复验步骤？
4. 首次失败、返修、复验和旧版本是否仍可追溯？
5. 成长结论是否至少有一条独立证据和一次跨情境/未知任务？不足则标 `unverified`。
6. 复盘行动是否有唯一责任人、截止日期、证据和回归方法？未复验不得 `closed`。

MVP 的成功标准是“流程可追踪并能暴露差距”，不是宣布员工已经胜任。两周后只基于证据调整模板和下一周期目标。
